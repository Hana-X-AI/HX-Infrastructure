## Executive Summary

Deploy a unified vector search API gateway providing semantic search capabilities
across multiple vector databases (Qdrant, pgvector) with intelligent routing,
semantic caching, and OpenAI-compatible endpoints. Serves as the standard vector
search API for all Layer 5 applications.

**Key Benefits:**
- Single API eliminates application-level integration complexity
- Intelligent routing optimizes query performance across databases
- Semantic caching reduces redundant vector searches
- Extensible architecture supports future vector database additions
- Centralized usage tracking and performance monitoring

**Timeline:** 3-4 weeks (standard deployment with full feature set)

## Technical Scope

### Core Capabilities

1. **Unified Vector Search API**
   - OpenAI-compatible embedding endpoints
   - Similarity search across multiple vector databases
   - Hybrid search (vector + keyword filtering)
   - Batch query support for efficiency

2. **Multi-Database Support**
   - Qdrant (primary, deployed on hx-qdrant-server)
   - pgvector (PostgreSQL extension on hx-postgres-server)
   - Extensible plugin architecture for future databases (Weaviate v2.0)

3. **Intelligent Query Routing**
   - Feature-based routing (Qdrant for filtered queries, pgvector for simple)
   - Automatic failover to secondary database
   - Manual database selection override capability
   - Health-check based routing (exclude unhealthy backends)

4. **Semantic Caching**
   - Hybrid caching: text cache (Redis) + semantic cache (async)
   - Configurable TTL per query type
   - Cache invalidation on database updates
   - Cache hit/miss metrics for optimization

5. **Embedding Model Integration**
   - Integration with LiteLLM gateway (hx-litellm-server)
   - Support for all models available through LiteLLM
   - Default model: nomic-embed-text via Ollama (hx-ollama3-server)
   - Model selection per request with validation

### Integration Points

**Upstream Dependencies (Layer 1-3):**
- Layer 1: Kerberos SSO (hx-dc-server), SSL/TLS (hx-ssl-server)
- Layer 2: LiteLLM gateway (hx-litellm-server) for embeddings
- Layer 3: Qdrant (hx-qdrant-server), PostgreSQL (hx-postgres-server), Redis (hx-redis-server)

**Downstream Consumers (Layer 5):**
- Open WebUI (hx-webui-server) - RAG functionality
- LightRAG (hx-literag-server) - knowledge graph queries
- Custom applications - semantic search capabilities

### Performance Requirements

- **Query Latency:** < 200ms P95 (including cache misses)
- **Throughput:** 100-1000 queries/second with burst capacity to 2000 qps
- **Cache Hit Rate:** > 60% for production workloads
- **Availability:** 99.5% uptime (allows 3.6 hours/month downtime)

### Technology Stack

**Backend Framework:** FastAPI (Python 3.11)
- Async request handling
- Automatic OpenAPI documentation
- Pydantic V2 for validation

**Caching Layer:** Redis (hx-redis-server)
- In-memory text cache
- Async semantic cache population
- Cache invalidation pub/sub

**Vector Databases:**
- Qdrant (gRPC client for performance)
- pgvector (SQLAlchemy + psycopg3)

**Observability:**
- Prometheus metrics export
- Structured logging (JSON)
- OpenTelemetry tracing

## Risks & Mitigations

**Risk 1: Semantic Caching Complexity**
- **Impact:** May not achieve 60% cache hit rate
- **Mitigation:** Start with text caching, add semantic incrementally
- **Fallback:** Text-only caching (still provides value)

**Risk 2: pgvector Performance**
- **Impact:** pgvector queries may exceed latency budget
- **Mitigation:** Route heavy workloads to Qdrant, optimize indexes
- **Fallback:** Qdrant-only deployment (defer pgvector to v2.0)

**Risk 3: Multi-Database Routing Logic**
- **Impact:** Intelligent routing may not improve performance
- **Mitigation:** A/B testing with metrics collection
- **Fallback:** Simple round-robin or manual database selection
