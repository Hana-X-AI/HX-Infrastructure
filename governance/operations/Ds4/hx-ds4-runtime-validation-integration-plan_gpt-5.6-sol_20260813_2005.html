2. What DS4 is — and what it is not

It is

A vertically integrated inference/runtime project

  • Optimized first for DeepSeek V4 Flash.
  • Also supports GLM 5.2 and high-memory DeepSeek V4 PRO configurations.
  • Builds model loading, prompt rendering, tool calls, KV state, HTTP serving, and its native coding agent together.
  • Supports Metal, NVIDIA CUDA, and ROCm targets.
  • Contains extensive correctness, API, tool-use, cache, GPU, long-context, and release-QA material.
It is not

A zero-weight model simulator or general GGUF runner

  • The uploaded ZIP contains no model weights.
  • The source explicitly says arbitrary GGUFs are unsupported.
  • It is not a Qwen runtime.
  • It does not validate vLLM-specific scheduling, flags, memory behavior, quantization loading, or Qwen prompt/tool templates.
  • It should not replace the primary HX vLLM/Qwen plan.
Hardware implication. The snapshot documents ds4f-q2 as a model target for roughly 96/128-GB-RAM machines and larger variants for substantially larger systems. That is a poor fit for the current single-32-GB-VRAM hxs-1 target. Do not download DS4 weights merely to unblock hook/skill testing.

3. Why DS4 matters to HX anyway

The valuable part of DS4 for HX today is not its model. It is the way the project treats an AI runtime as an agent-facing protocol, state, tooling, and QA surface rather than only as a text-generation endpoint.

5. What Claude should implement now — without a model

5.1 Define an engine-neutral runtime contract

Create a canonical HX definition of the capabilities the local AI runtime must satisfy. Use current repository conventions and discover the canonical validation/test location rather than inventing a parallel hierarchy.

At minimum classify capabilities as:

  • REQUIRED for the primary HX local-agent runtime;
  • OPTIONAL but desirable;
  • PROFILE-SPECIFIC for vLLM/Qwen or DS4/DeepSeek.

Contract areas should include: model discovery/health; chat request/response; streaming; tool definitions; tool selection/result continuation; tool IDs; error semantics; cancellation; long system/context input; context continuity; usage/telemetry where available; reasoning-field separation where supported; and runtime identity/version evidence.

5.2 Build an offline fixture/protocol harness

Create a deterministic test mode that requires no model and does not pretend to test intelligence. The harness may use static fixtures and/or a minimal deterministic local HTTP stub compatible with the chosen HX contract.

Its purpose is to test:

  • HX client/config construction;
  • OpenAI-style request and response handling where HX uses it;
  • Anthropic-style request and response handling where HX uses it;
  • SSE framing and event sequencing;
  • tool-call ID, name, argument and result continuity;
  • multi-turn serialization;
  • malformed/error response handling;
  • timeouts/cancellation behavior;
  • runtime-profile selection;
  • evidence/report generation.
Boundary: offline mode must never claim to prove model reasoning, skill selection, correct tool choice, instruction-following, long-context recall, token throughput, VRAM behavior, or Qwen/DeepSeek quality.

5.3 Establish runtime profiles

Implement profiles/configuration rather than hardcoding one server into the tests.

ProfileStatusPurpose
offline-fixtureImplement nowNo-model deterministic protocol/client validation.
vllm-qwenImplement configuration contract now; execute laterPrimary HX runtime. Live behavioral/performance tests begin when hxs-1 has Qwen/vLLM installed.
ds4-deepseekDefine as experimental; execute laterSecondary backend to test runtime/model independence and Claude Code-style Anthropic compatibility.

5.4 Add a model/runtime evidence ledger

Every live acceptance run should record enough data to reproduce the result:

  • timestamp;
  • server/host;
  • runtime profile;
  • runtime/version or commit where available;
  • model identity and quantization;
  • endpoint/base URL;
  • context setting;
  • backend/GPU placement;
  • test set/version;
  • pass/fail/skip;
  • measured latency/throughput only when the test actually measured it.

Offline runs must be clearly labelled OFFLINE / NO MODEL.

7. DS4 patterns worth mining explicitly

7.1 Three API surfaces

The reviewed snapshot exposes:

GET  /v1/models
GET  /v1/models/deepseek-v4-flash
GET  /v1/models/deepseek-v4-pro
POST /v1/chat/completions
POST /v1/responses
POST /v1/completions
POST /v1/messages

For HX, the important idea is not to implement all seven endpoints ourselves. It is to ensure our test architecture can express the API surface actually required by a selected runtime/client profile.

7.2 Tool-call fidelity

DS4's source explains why canonical JSON re-rendering can differ from the exact model-emitted tool syntax and thereby break continuation/cache identity. DS4 maintains a bounded tool-ID-to-exact-sampled-representation map and uses deterministic canonicalization only as a fallback.

HX should turn that into a runtime-neutral invariant:

tool call generated
  -> tool id retained
  -> tool name retained
  -> arguments semantically retained
  -> tool result correlated to same call
  -> next model turn receives coherent history

7.3 Long agent prefix and cache behavior

The snapshot explicitly notes that Claude Code may send a large initial prompt, around 25k tokens, and recommends disk KV reuse to avoid repeated prefill. HX should therefore test:

  • cold first request;
  • warm same-session continuation;
  • session restart/resume if supported;
  • prefix/cache evidence if the runtime exposes it;
  • time-to-first-token and prefill throughput separately from decode throughput.

7.4 Test tracks, not one giant “model test”

DS4's CONTRIBUTING.md and QA_BEFORE_RELEASES.md separate fast server-side tests, model-backed vector/quality checks, long-context tests, tool-call quality, GPU/backend regression, and speed regression. HX should mirror the separation of concerns, not copy DS4's model-specific test implementation.

9. How this connects to the hooks and skills work

Hooks

Remain deterministic client/repository controls. Their unit/regression tests do not wait for a model.

Skills

Structure/trigger/reference validation can run without a model. Actual skill-following quality belongs to L3 live behavioral tests.

Agents

Definition/schema checks are model-free. Correct specialist selection, tool use, and hook-denial recovery require live inference.

Examples of future L3 scenarios:

  • Ask a local model to perform an operation that would tempt it to use Ansible; verify the model chooses the approved path or, if it does not, the permanent hook blocks it and the model recovers correctly.
  • Run a specialist that attempts to alter a protected authority file; verify the edit guard denies it and the agent returns a recommendation instead of fighting the guard.
  • Give conflicting TARGET-STATE and DISCOVERED evidence; verify the Architecture Decisions/Authority capability preserves the distinction.
  • Give a version-sensitive vLLM/Qwen task; verify Source-Driven Research asks for/uses version evidence rather than guessing.

10. Primary runtime lane: vLLM/Qwen

Do not change the primary runtime decision. The first live-runtime acceptance target remains the planned Qwen model served through vLLM on the intended HX compute host.

When that runtime becomes available, execute L2 → L3 → L4 progressively:

  1. endpoint/model identity;
  2. basic non-stream chat;
  3. streaming;
  4. single structured tool call;
  5. tool result continuation;
  6. long HX system/context prompt;
  7. selected hook/skill/agent behavioral scenarios;
  8. cold/warm performance and resource evidence.

Do not treat success on DS4 as proof that vLLM/Qwen works.

11. Experimental runtime lane: DS4/DeepSeek

Define the profile and documentation now; do not install or download a model as part of this implementation.

Later, when HX intentionally allocates hardware capable of holding a supported DS4 model, DS4 becomes useful for:

  • Anthropic-compatible Claude Code testing through /v1/messages;
  • OpenAI Chat/Responses cross-client testing;
  • tool-call fidelity testing;
  • long-prefix/cache experiments;
  • testing whether HX skills/hooks/agents are runtime-independent;
  • distributed inference experiments across trusted lab systems.
Distributed DS4 remains a later experiment. The reviewed source describes pipeline parallelism as primarily a capacity/long-prefill tool: generation remains autoregressive and pays cross-machine communication cost. Treat distributed DS4 as a research/demo workstream, not as a shortcut to the primary local-runtime milestone.

12. What not to import from DS4

  • Do not adopt ds4-agent as the HX orchestration framework.
  • Do not vendor the whole DS4 repository into HX unless a later explicit decision requires source modification.
  • Do not add DeepSeek model weights to the HX repository.
  • Do not redefine the current Qwen/vLLM target around DS4.
  • Do not copy DS4's remote-host QA topology, addresses, or machine assumptions into HX.
  • Do not treat DS4-specific DSML representation as the HX universal tool format.
  • Do not create tests that pass only because a mock emits the expected “intelligent” answer.
  • Do not claim offline fixtures validate model reasoning.

15. Model-free acceptance criteria for this implementation

  • A canonical HX AI Runtime Acceptance Contract exists.
  • Runtime tests are engine-neutral at the contract layer.
  • An offline fixture mode runs without model weights.
  • Offline results are explicitly labelled NO MODEL / protocol-only.
  • OpenAI-style chat fixture handling is tested where relevant to HX.
  • Anthropic-style messages fixture handling is tested where relevant to HX.
  • SSE event parsing is tested.
  • Tool IDs/names/arguments/results survive a deterministic multi-turn round trip.
  • Malformed/error responses are handled predictably.
  • Cancellation/timeout cleanup is tested.
  • Profiles exist for offline, primary vLLM/Qwen, and experimental DS4/DeepSeek.
  • Live-required tests skip cleanly when no endpoint/model is configured.
  • Evidence output distinguishes static/offline/live/model-backed results.
  • No DS4 weights were downloaded.
  • No DS4 source was wholesale vendored.
  • No vLLM/Qwen architectural decision was replaced.
  • Current hook/skill tests remain independent from the model installation schedule.
  • Relevant DS4 source provenance is documented for any substantially adapted code.

16. Live acceptance criteria once Qwen/vLLM arrives

  • Primary runtime identity is captured.
  • Basic chat passes.
  • Streaming passes.
  • Structured tool invocation passes.
  • Tool result continuation passes.
  • Long HX prompt is accepted at the configured context size.
  • Selected skill/agent scenarios run against a real model.
  • Hook denial/recovery is exercised with a real agent action.
  • Cold/warm latency and prefill/decode evidence are measured.
  • No claim based on DS4 substitutes for Qwen/vLLM-specific validation.

17. Later DS4 acceptance gate

Do not install DS4 merely because this plan exists. A separate execution decision should verify:

  • supported model and exact GGUF;
  • required RAM/VRAM and placement;
  • actual available HX hardware;
  • storage capacity for model files;
  • backend compatibility;
  • network trust assumptions for any distributed run;
  • desired experiment: Claude Code compatibility, cross-runtime conformance, caching, distributed inference, or performance.

19. Definition of done

The work is complete when HX has an operational, documented model-independent runtime validation layer that provides useful testing today and becomes the same acceptance entrypoint for the eventual vLLM/Qwen runtime and an optional future DS4/DeepSeek runtime.

Strategic payoff. HX should define what an AI runtime must do for HX, then test runtimes against that contract. This avoids accidentally defining the platform as “whatever vLLM currently does” while still keeping vLLM/Qwen as the primary implementation.
