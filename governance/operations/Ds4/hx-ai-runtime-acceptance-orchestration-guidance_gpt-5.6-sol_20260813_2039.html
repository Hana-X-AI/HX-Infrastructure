Core conclusion. The four documents are complementary, not replacements. Read all four before making changes. Implement the engine-neutral runtime-acceptance machinery first, then apply the newer hxs-3 placement semantics as a scoped workload-placement overlay.

2. Branch/worktree isolation — mandatory

Do not create feature/ai-runtime-acceptance from migration/docling-pilot. A new branch name does not provide isolation if it inherits Docling commits.

The desired Git graph is:

canonical-mainline
   |   |    |  feature/ai-runtime-acceptance
   |
   +-- migration/docling-pilot

Not:

canonical-mainline
   |
migration/docling-pilot
   |
feature/ai-runtime-acceptance

Preferred execution model: create a separate Git worktree from the exact canonical mainline commit and do the AI-runtime work there. If approved operations documents exist only on another branch, bring over only those required artifacts rather than inheriting unrelated implementation commits.

3. hxs-3 authority semantics

The most important placement rule is:

SERVER-REGISTRY.md owns durable host identity and role.
The DS4 workstream defines workload eligibility only.

Do not replace an existing authoritative durable role—such as agent-intelligence—with “flexible development-model compute” or “experimental AI runtime.” Instead keep these concepts distinct:

ConceptExample
Host identityhxs-3
Durable roleWhatever SERVER-REGISTRY.md currently authoritatively defines
Hardware capabilityGPU compute / RAM / storage / interconnect
Eligible workloadDS4/DeepSeek, Qwen Coder, another approved model/runtime
Active workloadWhichever profile is currently selected

Expected registry result. If SERVER-REGISTRY.md is already clean and does not permanently assign DS4 to hxs-3, the expected outcome is no registry change. DS4 eligibility belongs in workload/profile/service documentation unless the current schema explicitly supports that distinction.

4. Two-pass implementation model

Pass 1 — Runtime Acceptance Machinery

  • Define the engine-neutral HX AI Runtime Acceptance Contract.
  • Implement OFFLINE / NO MODEL fixture/protocol tests.
  • Create/extend profiles: offline-fixture, vllm-qwen PRIMARY, ds4-deepseek EXPERIMENTAL.
  • Define machine-readable evidence.
  • Define live-only model behavior/performance tests as SKIP until configured.
  • Do not bind DS4 permanently to hxs-3.

Pass 2 — hxs-3 Placement Overlay

  • Make hxs-3 an eligible DS4 placement when explicitly selected.
  • Preserve durable role from the registry.
  • Keep Qwen Coder/another model possible without server-role redesign.
  • Require a workload capacity gate before download/activation.
  • Keep runtime/model configuration isolated.
  • Do not assume simultaneous heavy-model residency.

Pass 2 is an overlay, not a repair pass. Because all four documents are read first, Pass 1 should already avoid host-role mistakes.

This preserves rollback boundaries. The runtime acceptance framework can survive even if placement decisions change later.

6. Capacity-gate interpretation

Do not interpret “hxs-3 has enough GPU capacity” as permission to assume all workloads can coexist. The gate must evaluate the selected workload against current authoritative evidence.

At minimum evaluate:

  • GPU model/count/VRAM;
  • system RAM;
  • storage;
  • exact model and quantization;
  • context target;
  • KV/cache allowance;
  • runtime overhead;
  • concurrency;
  • coexistence only if simultaneous residency is explicitly intended.

Without current authoritative evidence, the valid result is:

BLOCKED — INSUFFICIENT CURRENT HARDWARE EVIDENCE

No SSH or infrastructure mutation is required for this workstream.

7. Evidence-class separation

The offline suite must never overclaim. Results should distinguish at least:

protocol
model-behavior
performance

Offline fixture tests can prove protocol/client behavior such as request/response handling, SSE parsing, tool-call continuity, error handling, and cancellation. They cannot prove model intelligence, skill adherence, correct tool choice, context recall, throughput, or VRAM behavior.

8. Qwen Coder nuance

Do not assume “Qwen Coder on hxs-3” automatically means the existing vllm-qwen profile. A future hxs-3 development workload may use a distinct model/runtime profile. The runtime contract should make adding that profile possible without redefining hxs-3 or rewriting the contract.

9. Cross-pass consistency checks

  • Runtime contract remains engine-neutral.
  • vllm-qwen remains PRIMARY.
  • ds4-deepseek remains EXPERIMENTAL.
  • DS4 is workload-when-selected, not a server role.
  • hxs-3 durable role remains registry-owned.
  • Qwen Coder/another model remains possible.
  • No concurrent heavy-model residency is assumed without evidence.
  • No model weights downloaded.
  • No ds4-agent adopted.
  • No Ansible.
  • No secrets.
  • No second host/IP inventory.
  • No vLLM/Qwen architecture change.
  • Offline tests report OFFLINE / NO MODEL.
  • Live tests SKIP cleanly.
  • Docling/LangGraph changes are absent from the feature branch.
  • SERVER-REGISTRY.md is unchanged unless correcting an already-present incorrect DS4 role.

10. Workstream boundaries

This is an independent AI-runtime validation workstream. It should not be merged into the Docling pilot branch, should not start LangGraph, and should not become a host-deployment or model-installation exercise.

Allowed now:

  • repository code;
  • tests;
  • fixtures;
  • profiles;
  • governance/operations documents;
  • model-free validation;
  • completion reports.

Not allowed now:

  • model download;
  • SSH/host execution;
  • package install on hxs hosts;
  • infrastructure mutation;
  • runtime activation;
  • LangGraph implementation;
  • merge to main.

11. Definition of done

  • Feature branch is based directly on the canonical mainline commit.
  • Preferably implemented in a separate worktree.
  • Pass 1 and Pass 2 are separate reviewable commits.
  • Offline runtime acceptance suite runs model-free.
  • Live-required tests skip cleanly.
  • hxs-3 durable role is not redefined.
  • DS4 is represented only as an eligible experimental workload/profile.
  • Qwen Coder/another model remains possible.
  • Capacity gate exists and can return BLOCKED when evidence is insufficient.
  • No unrelated Docling/LangGraph changes appear in the branch.
  • Completion reports record base commit, branch/worktree, pass commits, final HEAD, test results, registry status, and deferred live-validation gates.
