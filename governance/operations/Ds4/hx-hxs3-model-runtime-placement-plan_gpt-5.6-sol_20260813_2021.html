hxs-3 Model Runtime Placement Plan

Revision to the DS4 integration plan: hxs-3 is not assigned a permanent DS4 or “experimental AI runtime” role. It remains a flexible development-model host whose GPU capacity may be used by DS4/DeepSeek, Qwen Coder, or another approved development model/runtime as requirements evolve.

Decision: approved Host: hxs-3 No permanent DS4 role Workload-based placement Prepared by GPT-5.6 Sol 2026-08-13 20:21 America/Panama
Corrected design principle. The server owns compute capacity; the model/runtime is a workload. hxs-3 should remain reusable for whichever development model is most useful at the time. DS4 is a candidate workload on hxs-3, not the identity of hxs-3.

2. Why this is the better architecture

Preserves flexibility

Development model needs will change. Binding hxs-3 permanently to DS4 would prematurely convert a scarce GPU resource into a single-purpose appliance.

Separates host identity from workload identity

The registry should describe what hxs-3 is; runtime configuration should describe what hxs-3 is currently running.

Supports comparative development

The same machine can be repurposed between Qwen Coder, DeepSeek/DS4, or another model without rewriting server governance.

Limits configuration drift

Each runtime should be isolated and reversible so changing the active model does not leave a mixed stack of stale services, environment variables, and model files.

3. Correct conceptual model

hxs-3
└── development-model compute capacity
    ├── workload profile: qwen-coder + approved runtime
    ├── workload profile: deepseek + DS4
    └── workload profile: future development model/runtime

Only the selected workload(s) are active.
The host identity does not change when the workload changes.

Do not model the system as:

hxs-3 = DS4 server

Model it as:

hxs-3 = reusable GPU-capable development host
current workload = selected model/runtime profile

6. Runtime isolation requirements

  • DS4 dependencies and configuration must not overwrite or mutate Qwen/vLLM configuration.
  • Runtime-specific environment variables must be scoped to the runtime/service/profile.
  • Model files must be separated by model identity and quantization.
  • Start/stop/status procedures must clearly identify the selected workload.
  • Ports must be configurable and documented rather than assumed globally.
  • Only the selected runtime should bind its intended endpoint unless concurrent operation has been explicitly capacity-tested.
  • Switching workloads should not require reinstalling the operating system or deleting another runtime.
  • Any shared CUDA/toolchain dependency must be documented and validated against both workloads before changing it.

7. Workload selection model

The intended operational model is profile-based:

select hxs-3 workload
        |
        +-- qwen-coder
        |     -> runtime configuration
        |     -> model selection
        |     -> capacity validation
        |
        +-- ds4-deepseek
        |     -> DS4 runtime
        |     -> supported model/quant
        |     -> capacity validation
        |
        +-- future-model
              -> approved runtime/profile
              -> capacity validation

Selection should be explicit. Do not infer that DS4 is active merely because DS4 is installed.

8. Capacity gate before activation

Every model/runtime profile placed on hxs-3 should pass the same capacity gate before model download or activation.

DimensionRequired evidence
GPUDevice model(s), count, VRAM per device, aggregate usable VRAM, topology/interconnect where relevant.
System RAMAvailable RAM after OS/service reservation.
StorageModel size, runtime/source/build size, cache, logs, temporary download/build space, retained alternative quantizations.
Model residencyChosen model/quant and estimated/observed runtime memory requirement.
Context/KVTarget context size, concurrency, KV/cache allowance.
Runtime overheadGraphs, scratch buffers, server overhead, backend-specific headroom.
CoexistenceIf another model/runtime remains active, measure combined capacity rather than assuming it fits.
No automatic model download. For DS4 specifically, do not download a large GGUF until the exact supported model, quantization, hxs-3 capacity, storage destination, and intended test objective have been approved and the gate passes.

9. Registry semantics

Do not make DS4 a durable server role in SERVER-REGISTRY.md. If the registry tracks workload/service state, record DS4 as a current/target workload only in the appropriate workload/service field or associated service documentation.

Preferred semantic separation:

SERVER IDENTITY
hxs-3
  -> hardware / network identity
  -> durable general-purpose development-model capacity

WORKLOAD STATE
  -> Qwen Coder / runtime X
  -> DS4 / DeepSeek
  -> another model/runtime

The workload may change.
The server identity remains stable.

If the current registry schema does not support this distinction, do not redesign it automatically. Use existing service/workload documentation and propose a schema change separately if needed.

10. DS4 placement inside this model

DS4 should be installed/configured as an optional isolated runtime profile for hxs-3.

Its purpose on hxs-3 is:

  • local DeepSeek experimentation when selected;
  • Anthropic-compatible /v1/messages testing;
  • Claude Code local-runtime compatibility experiments;
  • OpenAI API/tool-call conformance;
  • runtime acceptance-contract testing;
  • long-prefix/KV-cache experiments;
  • cross-runtime comparison with other HX model runtimes.

DS4 must remain removable/deactivatable without invalidating hxs-3's usefulness for another development model.

11. Qwen Coder placement inside this model

Qwen Coder or another dev model can occupy the same logical host capacity through a separate profile/runtime definition.

Do not force DS4-specific assumptions into Qwen Coder configuration, and do not force Qwen/vLLM assumptions into DS4.

shared:
  hardware inventory
  host storage conventions
  runtime acceptance contract
  operational logging/evidence conventions

separate:
  runtime binary/service
  model files
  model-specific environment
  launch arguments
  API capability profile
  cache/state
  performance evidence

13. Usage

The intended operating sequence is:

  1. Decide which development model/runtime should be active on hxs-3.
  2. Select the corresponding workload profile.
  3. Run the host/model capacity gate.
  4. Verify model files and runtime prerequisites.
  5. Start the selected runtime using its isolated service/script.
  6. Run the HX AI Runtime Acceptance Contract against that profile.
  7. Record evidence.
  8. Stop/deactivate the workload when changing models.
  9. Select and validate the next workload profile.

14. Non-goals

  • Do not assign hxs-3 a permanent DS4 role.
  • Do not assign hxs-3 a permanent “experimental AI runtime” role.
  • Do not prevent hxs-3 from hosting Qwen Coder or another approved development model.
  • Do not hardcode DS4 into the server registry as host identity.
  • Do not mix DS4 and Qwen/vLLM configuration trees.
  • Do not assume simultaneous model residency.
  • Do not download DS4 weights as part of this placement change.
  • Do not replace the HX AI Runtime Acceptance Contract with runtime-specific tests.

15. Definition of done

  • All DS4 documentation now describes hxs-3 as a placement target, not a permanent DS4 role.
  • hxs-3 remains reusable for Qwen Coder or another development model.
  • DS4 is represented as an isolated workload/runtime profile.
  • Runtime selection is explicit.
  • Host identity and workload identity are separate.
  • Exact host paths follow existing HX conventions or are documented as proposed if no convention exists.
  • Model weights stay outside Git.
  • Capacity validation precedes model download/activation.
  • Runtime-specific configuration remains isolated.
  • The HX AI Runtime Acceptance Contract remains engine-neutral.
This revision supersedes any earlier recommendation that assigned hxs-3 a durable DS4-specific or “experimental AI runtime” role. DS4 remains an experimental runtime/workload; hxs-3 remains flexible development-model compute capacity.
