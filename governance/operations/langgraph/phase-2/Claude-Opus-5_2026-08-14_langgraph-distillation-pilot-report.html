The findings that mattered most

The accepted model capability cannot be reached

The design named the Qwen3.5-9B acceptance as its inference capability and LangGraph as its intended client. But runtime-acceptance-decisions.md binds that endpoint to 127.0.0.1 on hxs-4. LangGraph runs on hxs-11; its gateway runs on hxs-8. Neither can reach a loopback socket on a third host.

I wrote that loopback constraint myself, during the Qwen commissioning earlier the same day, and then cited the same capability as consumable from a different host. Two workstreams, one contradiction, invisible from inside either. Now recorded as blocked and routed back to the acceptance authority rather than engineered around.

The flagship gate could not fail

The design's headline validation requirement was a test proving the checkpointer's connection settings are correct — the silent-data-loss case. testing-qa showed that the two constructions an implementer reaches for first both pass while the system is broken: a config echo asserts the line of code that set the value, and a same-connection read-back sees its own uncommitted rows.

The corpus already contained the correct construction — an integration case (lgc-456) that reads back through an independent database session. The design had cited the defect from lgc-298 and missed the method. Now specified: cross-connection read-back, plus fault injection with the failing run retained as the artefact.

Three more worth recording

  • Two parameters were three. The checkpointer's connection recipe needs a third setting, prepare_threshold, absent from the 2025 material — and it is the same mechanism as the open connection-pooler question. Two problems that were one problem.
  • Gotcha 10, committed against the registry. The design called n8n and Crawl4AI "no current fleet role". Both are current assignments (hxs-13, hxs-6). The document warned against exactly this failure and then made it — against current authority rather than 2025 material.
  • Durable state with no bound, no retention, no backup, on hxs-9's single non-redundant 238.5 GB device shared with the LiteLLM database and Redis — while the design's own interrupt model makes approval-blocked threads long-lived by construction.

Method failures the reviews caught in the pilot itself

  • No upstream package pinned, though the brief requires it per-package and the DESIGN gate asserts it. Now recorded in the document as an acceptance-gate failure rather than concealed.
  • Seven ledger rows cited from a summary table rather than read. Caught during authoring, before review — the exact Docling error. All seven were then read; the citations held, and two of them yielded better material than had been written.
  • The provenance section asserted records that did not exist. Three reviewers flagged it independently. Now written.

5. Current upstream — re-verified, and it changed the design

The Docling lesson applied. The 2025 material builds on a supervisor package; current guidance composes agents with a constructor that wraps subagents as tools — and that constructor lives in the LangChain agents package, so the packaging boundary moved, not only the API.

One nuance the langgraph reviewer corrected: the supervisor package is in maintenance mode and remains available, and the supervisor pattern is still recommended, implemented through tool calling. "Superseded" overstated it. The lesson that survives is narrower and better: bind to the shape, keep the package replaceable.

Not pinned. Behaviour was verified; releases were not. That is an open gate.

6. The organizing question — what does LangGraph own?

Answered explicitly, with a dedicated section rather than left implicit in prose. The ruling that mattered: LangGraph's Store is not used in HX. It is cross-thread durable memory with semantic search — Mem0's job — and adopting it would create a second memory authority by default rather than by decision.

The mem0 review accepted the ruling and failed the defence, correctly: "disabled by default" was the wrong frame and factually wrong on the Server runtime path, the ruling had no enforcement mechanism, and the gate was unfalsifiable. It now has three falsifiable enforcement points — startup refusal, absence of store tables in the schema, and exclusion from the tool surface — and the write path has an owner: Mem0 decides what becomes a memory; orchestration submits raw material only.

On the open Docling question — should orchestration own the parsing-to-retrieval handoff? — the answer returned is bounded: a legitimate candidate to sequence it, not to own it. Owning the contract would make ingestion depend on the orchestrator being healthy.

8. Recommendation

Do not accept the deliverable yet. It is materially better than its first revision, but three capabilities failed it and none has seen the corrections.

What the owner needs to decide, as distinct from what needs verifying:

  1. Reachability of the accepted inference endpoint. Nothing downstream is implementable until this is resolved in the acceptance policy.
  2. Deployment mode — embedded library or packaged server. It silently decides the Store ruling, the Redis classification and the checkpointer configuration.
  3. Orchestration topology. Four candidates are documented with consequences; the ruling is the owner's, not a verification item.
  4. Whether to create the litellm and MCP-plane contracts, or downgrade those two classifications. (Historical, 2026-08-14. Resolved: the litellm contract requirement was withdrawn — the model gateway moved to OmniRoute and no gateway contract is outstanding. Only the MCP-plane contract question remains. See act-017 in governance/logs/actions-and-issues.md.)

On the method itself — which is what this second pilot was testing. It held against a harder domain: a stateful orchestrator with six live integration boundaries, where the Docling subject had one. The controls that caught real errors were the same ones the pattern predicted would: separate-context review, per-row provenance counting, source-hash verification, and the refusal to inherit a value without resolving it. The pattern needs no change. One addition is worth making to it: a gate's construction must be specified, not only its requirement — because the flagship gate here named the right property and would still have shipped unable to fail.
