LangGraph — Four Architecture Decisions Before Re-Review

The LangGraph design is REVISED / NOT ACCEPTED. These four owner decisions gate the re-review. They are decisions, not verification items — each changes the design, so they must land before the four capability reviews re-run.
Prepared by Claude (Opus 4.8)Date 2026-08-14For owner rulingBranch migration/langgraph-pilot @ f5a028b

Sequencing

Decisions 1–4 are the owner's. Each silently changes the design under review (deployment mode alone decides Store enforcement, Redis, and the checkpointer). So the order is: rule 1–4 → update the design to reflect the rulings → re-run the four reviews → accept. Re-reviewing now would just regenerate the same FAILs. Recommendations below are mine; the rulings are yours.

1Qwen network-consumability BLOCKS EVERYTHING

Problem. The accepted Qwen3.5-9B capability is bound 127.0.0.1-only on hxs-4 (the commissioning verdict, correctly, for a no-auth Ollama endpoint). LangGraph runs on hxs-11 and its gateway on hxs-8 — neither can reach a loopback socket on a third host. Nothing downstream is implementable until this is resolved in the acceptance policy, not engineered around.

OptionConsequence
A. Promote to network-consumable — define an explicit network-access + auth state for the endpointOllama has no auth; exposing it on the LAN publishes an unauthenticated model+tool endpoint. Would need a fronting/auth layer. Contradicts the loopback safety the commissioning chose.
B. OmniRoute is the only permitted remote path — Qwen stays loopback-only; the traffic plane fronts itKeeps the no-auth endpoint off the LAN; matches the emerging traffic-plane architecture. Couples this to decision 2 and to OmniRoute existing.
C. LangGraph does not use Qwen day-one — a different accepted capabilityRemoves the dependency entirely for first deployment; defers the promotion question.
Recommendation: B. It preserves the loopback safety the runtime acceptance deliberately chose and routes remote consumption through the plane that will own model traffic anyway. Record it via principle P-B: create accepted-local-runtime vs accepted-network-consumable as distinct states in runtime-acceptance-decisions.md; Qwen holds the former, and network consumption is authorized only through OmniRoute.

Unblocks: the entire downstream design. This is the one that gates the others.

2LiteLLM → OmniRoute reconciliation REMOVES A FALSE BLOCKER

Problem. The design assumes LiteLLM (hxs-8) as the model gateway and the report flags a missing litellm SME contract as a blocker. But OmniRoute / the HX AI Traffic Plane supersedes LiteLLM in target state. Building the litellm contract would formalize a superseded component.

OptionConsequence
A. Reconcile to OmniRoute nowCorrect target, but the OmniRoute traffic-plane contract may not exist yet — risks inventing it prematurely.
B. Mark model-gateway BLOCKED / PENDING OMNIROUTE; build neither contract nowStops wasted effort on a dead LiteLLM contract; keeps the boundary stable (LangGraph consumes a verified capability envelope via the traffic plane and enforces it before dispatch) while the named plane is pending.
Recommendation: B. Do not build the LiteLLM contract. In the design, replace LiteLLM references with model gateway → BLOCKED / PENDING OMNIROUTE RECONCILIATION, and downgrade the litellm SME requirement. The ownership boundary is unchanged — only the named plane moved.

Unblocks: removes one of the two SME-gate blockers; prevents building a dead contract.

3Deployment mode: embedded library vs packaged server DESIGN-DEFINING

Historical / superseded runtime assumption

The final owner ruling records Decision 3: FINAL — PACKAGED SERVER in governance/operations/langgraph/phase-2/Claude-Opus-5_2026-08-14_langgraph-review-verdicts.md. The comparison below is retained as the decision's historical input and must not be used to reopen the deployment-mode ruling.

Problem. This is not packaging trivia — it silently decides Store semantics, Redis requirement, checkpointer construction, process ownership, networking, service lifecycle, failure isolation, and how OmniRoute interacts with orchestration/model calls.

DimensionEmbedded libraryPackaged server
Process / lifecycleIn-process with the orchestration serviceSeparate service/process, own lifecycle
Failure isolationShares fate with host processIsolated; can be restarted independently
NetworkingNo new endpointNew endpoint + access model
Store / checkpointerSimpler; in-processMust expose/persist across the boundary
Recommendation: Do NOT pick from the report alone. Run a focused comparison of both modes against the current architecture — including OmniRoute and jcode, which emerged after most of the 2025 material was written. This is a real evaluation, not a snap call; it can be its own small architecture pass.

Unblocks: Store enforcement details, Redis classification, checkpointer configuration.

4Is MCP day-one required? LIKELY REMOVES A BLOCKER

Problem. The report classified the MCP tool plane CURRENT REQUIRED, which makes an MCP-plane SME contract mandatory. But HX has deliberately deferred broad MCP hardening/exposure — so a day-one MCP requirement may manufacture a blocker inconsistent with current posture.

OptionConsequence
A. Keep CURRENT REQUIREDNeeds the MCP-plane contract now; adds a blocker; inconsistent with deferred-MCP posture.
B. Downgrade to LATER / DEFERRED if minimum-useful orchestration doesn't depend on MCP tools day-oneRemoves the second SME-gate blocker; matches HX's existing MCP posture. Re-add later when MCP hardening lands.
Recommendation: B, unless LangGraph's minimum useful first-deployment orchestration genuinely depends on MCP tools. Test that against the actual first use case; my bias is that it does not.

Unblocks: removes the MCP-plane-contract blocker from the SME gate.
