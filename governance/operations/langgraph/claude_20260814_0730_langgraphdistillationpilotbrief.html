7The organizing question: what does LangGraph own?

Concentrate the first pass on one question

Docling's risk was package mechanics. LangGraph's danger is different and worse: authority and state-ownership drift. A stateful orchestrator naturally tends to absorb everything it touches. So the distillation must interrogate boundaries aggressively and converge on an explicit answer to: what is LangGraph allowed to own in HX?

Expected convergence — verify, do not assume:

LangGraph OWNS:
- graph execution state
- thread / checkpoint state
- orchestration control flow
- interrupt / resume state
- orchestration-owned metadata

LangGraph does NOT automatically own:
- durable semantic / user / agent memory   -> Mem0
- retrieved knowledge                       -> LightRAG
- vectors / embeddings                      -> Qdrant + embedding plane
- model routing                             -> LiteLLM
- general queue infrastructure              -> Redis / platform role
- MCP server authority                      -> MCP plane
- infrastructure configuration              -> infrastructure controls

Boundary interrogations — resolve each, don't inherit

  • LangGraph Store ↔ Mem0: current LangGraph exposes a Store abstraction for durable cross-thread data — so it can now compete with Mem0 for the exact boundary we're protecting. Decide explicitly: (A) Store unused in HX; (B) Store restricted to orchestration-owned application metadata; or (C) a deliberately defined non-overlapping use. It must NOT silently become a second durable semantic-memory authority just because upstream supports it.
  • LangGraph ↔ Mem0: checkpoint/workflow state vs durable agent/user memory. Different owners.
  • LangGraph ↔ PostgreSQL: authoritative persistence + checkpoint storage — who owns what.
  • LangGraph ↔ Redis: ephemeral coordination/cache/queue vs durable graph state.
  • LangGraph ↔ LiteLLM: model routing belongs to the gateway. LangGraph requests capabilities/models, never binds directly to Qwen/Ollama/vLLM or "the box that happens to be there."
  • LangGraph ↔ MCP tool plane: consumes MCP-exposed tools through a current MCP client/adapter contract; does NOT own MCP server registration or gateway policy; must NOT depend on FastMCP-specific server details; must NOT become a second MCP control plane. Transport, discovery, allowed tool surface and failure semantics: VERIFICATION REQUIRED.
  • LangGraph ↔ LightRAG: retrieval/knowledge belongs to LightRAG; LangGraph sequences its use.
  • LangGraph ↔ Docling: orchestration may be a candidate owner of the Docling→LightRAG handoff (the open item from the Docling pass) — investigate, do not assume. Whatever this pass finds should feed back to that open Docling decision.
  • LangGraph ↔ agents: preserve the specialist-agent governance model. The orchestration pattern must NOT become a new source of authority over the specialists.

The service.md must then state ownership explicitly (a dedicated "what it owns / does not own" section), not leave it implicit in prose.

Model-routing boundary — authority: runtime-acceptance-decisions.md

Cite the governed policy, not the commissioning report. The hxs-4 model boundary is now a governance authority — governance/policy/runtime-acceptance-decisions.md, backed by executable invariants (37 PASS / 0 FAIL that fail-closed if the verdict is flipped or the record deleted). The commissioning report is evidence; the policy doc is authority. In service.md, cite the policy:

Qwen3.5-9B / hxs-4
  Authority : governance/policy/runtime-acceptance-decisions.md
  Status    : ACCEPTED for bounded local utility inference
  Intended client : LangGraph
  Constraints : client bounds prompt below the verified 65,536 envelope · thinking
    disabled unless deliberately required · endpoint loopback-only · OLLAMA_VULKAN=0 kept
  Exclusion : NOT ACCEPTED as a Claude Code backend

The design implication is the ownership boundary: LangGraph consumes an accepted inference capability and enforces its verified envelope before dispatch — it does not own the runtime-qualification decision or rewrite the model's operating envelope. Turn the underlying discovery (an endpoint that silently truncates over-limit prompts and answers confidently from the wreckage) into a clean routing boundary, not a table LangGraph maintains:

The model-routing plane (LiteLLM) OWNS:
  endpoint identity · model capability metadata · the VERIFIED context envelope ·
  routing/fallback policy · ideally fail-closed overflow enforcement

LangGraph OWNS:
  computing the request it is about to send · honoring the verified envelope the
  routing plane supplies · refusing / compacting / splitting work before it exceeds
  that envelope · treating a missing/unverified limit as UNSAFE, never as "probably 200K"

So: LangGraph must consume a verified model-capability envelope from the routing plane and never infer safety from provider-advertised context alone. If the gateway can't guarantee fail-closed overflow, LangGraph rejects or reduces an over-budget request before dispatch. Model-specific limits live in the routing/capability contract, not hardcoded in graph logic. Exact per-endpoint limits: VERIFICATION REQUIRED.
