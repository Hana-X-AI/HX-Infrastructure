2. What it actually does

The system prompt is exceptionally narrow. It requires the model to output exactly one final SKILL.md, beginning with two-field YAML frontmatter and followed by concise operational sections such as Workflow, Decision Rules, Guardrails, Output Requirements and Verification.

It explicitly rejects:

  • tutorial prose;
  • research/citations;
  • meta commentary;
  • multiple alternatives;
  • host-specific assumptions unless the skill is host-specific;
  • unnecessary long explanations.

This narrowness is the product's main strength and also its main limitation.

6. Sample-output quality warning

The public sample is useful evidence because it shows both the strength and risk of the fine-tune.

Positive:

  • compact;
  • operational;
  • frontmatter is syntactically aligned with modern skill conventions;
  • guardrails are explicit;
  • no filler.

But the example also contains workflow assumptions that should not be accepted without review:

  • git add . is an overly broad default for some repositories;
  • “pull before push” is not a universally correct Git workflow;
  • the trigger description “all git operations” is broad and could conflict with more specific skills;
  • the generated skill has no awareness of project governance, branch protection or repository-specific authority;
  • the model itself warns that generated shell commands require review.

This is strong evidence for using the model as a drafting specialist, not as autonomous skill authority.

7. Claude Code launch support should not mislead us

Ollama advertises ollama launch claude --model cmdmbox/skill-expert. That proves a compatibility path, not suitability as a general Claude Code backend.

The model's system prompt says every response must be the contents of one SKILL.md. Therefore it is deliberately unsuitable for normal coding-agent conversations, repository analysis or broad task execution.

No local invocation was performed, and the advertised command establishes no HX placement or readiness decision.

9. Evidence controls for any future authorized evaluation

No evaluation is authorized and this Recon selects no model settings. If the owner later authorizes an evaluation after the canonical gate closes, its evidence record must:

  • record the exact model identity and digest, Ollama version, prompt, seed, and the complete resolved generation configuration — every effective options field, including temperature, top_p, repeat_penalty, stop, and num_ctx, not a subset;
  • record top-level thinking (enabled or disabled) separately from whether the thinking trace is shown or hidden;
  • capture done_reason alongside the model and runtime metadata;
  • treat --hidethinking only as a visibility control: it hides the reasoning trace while the thinking model still uses it, and does not make generation deterministic;
  • measure wall time, token rate, VRAM, RAM and offload rather than infer them from artifact size;
  • preserve generated output and independent validation results as evidence, without treating either as an adoption decision.
