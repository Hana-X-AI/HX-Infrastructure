hxs-4 — Qwen3.5-9B commissioning

Zero-assumption commissioning · 2026-08-14 · branch feature/ai-runtime-acceptance · commit 8f6e1a9
Outcome. Qwen3.5-9B runs on hxs-4's isolated 8 GB card, fully on the GPU up to a 16,384-token context and usable to 65,536 with a CPU/GPU split. Ollama serves the Anthropic Messages API directly, so Claude Code needs no translation layer, and it was tested end to end over an SSH tunnel.
Claude Code is not qualified against this endpoint. It connects, drives a real tool loop and returns real file contents — the protocol side works. It is not reliable, for two measured reasons. Claude Code believes the context window is 200,000 tokens and has no way to learn the real limit, so it routinely sends 69–73K tokens; and when a prompt exceeds 65,536 this runtime does not clamp or error, it silently collapses the prompt to 32,770 tokens and answers confidently from the wreckage. Detail in section 6.

The full-GPU ceiling is 16,384 tokens. Past that, the runtime moves model layers off to system memory to make room for the cache — which is why memory use barely rises while the cache triples.

Read these as allocation figures, not steady state. Each row was taken with the context allocated but barely used. Under a genuinely large prompt the same 65,536 configuration was later observed at 8.5 GB and a 39%/61% CPU/GPU split — more offload, and correspondingly slower, than the 28%/72% the ladder recorded. The ladder establishes what fits; it understates what a loaded session costs.

Bigger is not better below its own limit

This is the most useful number in the report. The same 8,311-token job, run at two settings:

16,3842,449 tok/s70 tok/s100% GPUcorrect

Identical work, same correct answer, but the 16K setting reads the prompt twice as fast and writes the answer 2.7× faster. A large context is not free headroom you leave switched on — you pay for it on every request, including the small ones. The only thing 64K buys is the ability to exceed 16K tokens at all. That caveat matters for anything agent-shaped: Claude Code's system prompt alone is 28,440 tokens, so for that client 16K is not a tradeoff, it is a non-starter (section 6).

It does deliver when you need it: at 64K the model read a 22,846-token document and correctly retrieved a specific fact buried in the middle of it, in 25 seconds, with no instability. Generation dropped to 17 tok/s with that much context loaded.

3. Three findings that change how this model must be sized

Finding 1 — isolating the GPU the usual way does not work here

hxs-4 has two cards: a 16 GB RTX 5060 Ti that is reserved, and the 8 GB RTX 5060 this workload is supposed to use. The standard way to restrict a process to one card is CUDA_VISIBLE_DEVICES. On this host that was not enough. Ollama's Vulkan backend ignored it entirely and re-enumerated both cards, including the reserved one — silently. Any residency measurement taken in that state would have been meaningless, because the model could have spread across 24 GB while appearing to fit in 8.

Isolation only held after disabling the Vulkan path outright:

Environment="CUDA_VISIBLE_DEVICES=GPU-cc758e31-d23b-3c53-bee6-dae3299a6f11"
Environment="GGML_VK_VISIBLE_DEVICES=999"
Environment="OLLAMA_VULKAN=0"

Verified after every restart since: one device accepted, reserved card absent. Devices are pinned by UUID, never by index — indexes reorder across reboots.

Finding 2 — this model does not size like a normal transformer

The runtime allocates a KV cache and a separate recurrent-state buffer, and reported "KV cache shifting is not supported for this context". That is the signature of a hybrid attention design: only some layers keep a growing cache, the rest carry fixed-size state.

The practical consequence is that the cache grows sublinearly — 12× from 4K to 64K, not the 16× that proportional scaling predicts. A standard KV formula will oversize this model and reject configurations that in fact run fine. This is why the fit gate was written to refuse to estimate cache size, and that refusal was correct — though not for the reason expected. The real cache is smaller than a textbook estimate, not larger.

Finding 3 — the published size is a download size, not a memory size

The artifact is 6.6 GB. Actual resident weights are 4.61 GB, and ollama ps reports 5.5 GB. The gap is the vision encoder, which does not load for text-only work. The model does advertise vision, tools and thinking.

Since measured, and the caution was overdone. Vision was subsequently tested: a generated image containing a red rectangle came back correctly identified as "red". It cost 12 MiB — 6,794 MiB text-only against 6,806 MiB with an image, at the same 16,384 context, still 100% on the GPU. Image input does not threaten residency on this card.

The packaging explains the gap: the artifact ships as a single model layer with no separate projector file, and the vision tensors simply are not resident on the GPU during text-only work. That is genuine native multimodality rather than a bolted-on encoder.

4. Talking to it

The significant result: Ollama 0.32.9 serves the Anthropic Messages API natively at /v1/messages. Claude Code speaks that protocol, so no translation proxy is needed. Verified end to end:

  • System prompts — stop_reason: end_turn
  • Tool calls — stop_reason: tool_use, correct name and arguments
  • Tool results fed back — model consumed the result and answered from it
  • Streaming — 108 events, correct types (message_start, content_block_delta, message_stop, …)

The OpenAI-compatible endpoint and Ollama's own API also work, including tool calling on both.

A trap worth knowing before you point a client at it

The model thinks before answering, and those thinking tokens are spent out of the same budget as the reply. Ask for a two-word answer with max_tokens: 128 and you get an empty response — the budget is gone before it starts writing. Same request at max_tokens: 1024 works, using 159 tokens.

Turning thinking off is honoured, and the difference is dramatic:

RequestBlocks returnedOutput tokens
defaultthinking, text159
"thinking":{"type":"disabled"}text5

Same answer, roughly 30× less output. For tool-driven work, leave thinking off unless a task genuinely needs it.

5. The incident — and why I am reporting it rather than quietly moving on

The first context-ladder run wedged the machine and it needed a reboot. Worth being precise about what happened, because the cause was my test method, not the hardware.

Ollama starts a separate runner process for each context size. My loop asked for a new context without unloading the previous one, so two runners of about 5.5 GB each tried to occupy an 8 GB card. It did not fail cleanly. There was no out-of-memory error and no fallback — the NVIDIA kernel context locked up. Two runner processes sat unkillable for 20 minutes, and every nvidia-smi issued afterwards locked up too, because a process in that state cannot be killed even with SIGKILL.

After a reboot, with an explicit unload between rungs, every step passed including 65,536. So there is no cliff between 4K and 8K; there was a bug in the harness.

The rule this leaves behind: on a single-GPU host, always unload and confirm the card is clear before changing context size. Overcommitting this card does not degrade gracefully — it takes the driver down with it.

I had earlier read that failure as evidence of a hard capacity cliff at 8K. That was wrong, and the corrected ladder disproves it.

6. Claude Code, tested end to end

Reachability was solved with an SSH tunnel, so the service never left loopback and the connection is authenticated by your key:

ssh -N -L 11434:127.0.0.1:11434 -i ~/.ssh/hx_fleet_ed25519 hxsa@<hxs-4>

Claude Code 2.1.221 was then pointed at it. Three tests, and they tell a layered story.

TestResultInput tokensWhat happened
Plain text replyPASS28,440Returned the exact requested string. 36.7 s to first token.
Tool use, default profileFAIL69,386Zero output, then hallucinated unrelated file paths. Never read the file.
Tool use, clean profilePARTIAL73,351Ran a 3-turn agent loop, genuinely read the file — then miscounted 4 lines as 6.

Claude Code's own prompt does not fit

Its baseline system prompt measured 28,440 tokens before any work begins. That single number decides the context setting: 16,384 is not a "slower but workable" option for Claude Code, it is impossible — the model would never see the user's request. With this workstation's plugins and skills loaded the prompt reached 69,386 tokens, and even with a stripped profile a trivial file-read task reached 73,351.

The failure mode that makes this unsafe to rely on

Claude Code reports contextWindow: 200000. It has no way to discover that the real limit is 65,536, so it will keep sending prompts past it. What happens then is the problem.

Tested directly: a prompt of roughly 85,000 tokens, with a specific fact placed at the very start, was sent to the endpoint. There was no error. The runtime processed 32,770 tokens — not the 65,536 it was configured for, but half that — and the model answered "The provided text does not contain a vault code." It had been truncated away, and nothing in the response indicated that more than half the input had been discarded.

So the endpoint is well behaved right up to about 65,000 tokens and then fails in the worst available way: it does not clamp, it does not error, it discards more than half the prompt and answers with confidence. A wrong answer that looks like a right answer is worse than a refusal.

Verdict

The protocol is proven and the agent loop genuinely functions — in the clean run Claude Code called its Read tool, received real file contents, and reasoned over them across three turns. But between a system prompt that exceeds the window on its own and an overflow mode that silently destroys the request, this endpoint should not be used as a Claude Code backend. The miscount of a four-line file is a fair illustration of what to expect even when the prompt does fit.

Two things would have to change for that verdict to move: the window would need real headroom above Claude Code's ~30K baseline — which the 16 GB card could provide — and the truncation behaviour would need to become an error rather than a silent collapse.

7. Where the published 8 GB guidance is wrong

The standard advice for running this model on an 8 GB card was checked row by row against this host. Much of it holds. The parts that do not are wrong in a consistent direction — they are too cautious, and one instruction actively costs performance.

Why the pattern is consistent. This guidance is written for desktops where the GPU is also driving a display and a browser, and it is tuned to avoid support requests rather than to get the most from a dedicated card. On a headless server with an isolated GPU it is systematically pessimistic. The "enable FlashAttention" rule is the one to actually watch — it is repeated as universal, and here it cost more in compute buffer than it saved in cache.

One sizing trap worth carrying forward. Artifact sizes are not comparable across distribution channels. Gemma 4 E4B is 8.94 GB as an Ollama library tag and 4.63 GB as a HuggingFace Q4_K_M GGUF — the same model, nearly 2× apart. And a 4-bit vLLM artifact is not the same size as a 4-bit GGUF: Qwen3.5-9B is 5.29 GB as GGUF Q4_K_M but 10.65 GB as w4a16, because that format keeps activations at 16-bit and ships the vision tower. Always resolve the real file size in the channel you will actually deploy from.

8. Open decisions

Network exposure

Still on 127.0.0.1:11434, and I would leave it there. Ollama has no authentication of any kind; binding it to all interfaces publishes an unauthenticated endpoint that accepts requests and emits tool-call payloads to anything that can route to the host. The tunnel above covers workstation use without that exposure.

Which context to run

The default is 65,536. Given the truncation behaviour, that is the right setting for anything that might send long prompts — it buys the largest safe margin before the cliff. For short interactive work from other clients, 16,384 is roughly 2.7× faster on generation and stays entirely on the GPU. One line in the service override either way.

What else is meant to live on hxs-4

The registry assigns hxs-4 Qdrant plus a web UI, Qwen2.5-3B, BGE-M3 embeddings and a reranker. None of them are installed — no Qdrant, no Docker, no serving stacks, no other model files. That entry describes intent, not the current machine.

It matters for planning: Qwen3.5-9B uses 6,984 MiB of the 8 GB card, about 86%. Those workloads cannot also fit there. They do have somewhere to go — the reserved 16 GB card is completely idle at 0 MiB. Worth deciding deliberately rather than discovering later.

Also worth noting, since it may affect the plan: on the 16 GB card this model would run at the full 64K context entirely on the GPU, with none of the CPU offload penalty measured above. That card is reserved, so this is an observation for you, not a recommendation to move anything.
