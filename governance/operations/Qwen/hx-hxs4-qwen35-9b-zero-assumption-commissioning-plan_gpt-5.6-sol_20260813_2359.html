HX-Infrastructure · Zero-Assumption Commissioning

hxs-4 Qwen3.5-9B / Ollama Full-Stack Commissioning Plan

A hardware-first, evidence-driven runbook for taking hxs-4 from an unverified host state to a proven live Qwen3.5-9B runtime. Every dependency—from OS/kernel, PCIe and NVIDIA driver through CUDA visibility, host tools, storage, Ollama GPU ownership, model residency, API semantics and Claude Code—is explicitly gated.

Host: hxs-4 Runtime: Ollama Model: qwen3.5:9b-q4_K_M Published artifact: ~6.6 GB GPU target: actual 8 GB NVIDIA device Start context: 4K Claude Code qualification: separate 64K-class gate Prepared by GPT-5.6 Sol
Non-negotiable rule: no assumptions. A prerequisite that has not been observed is not PASS. A successful command at one layer does not prove the layer beneath or above it. Missing evidence is BLOCKED. A detected mismatch is FAIL. Do not “fix forward” by installing more software until the cause and authority are known.

3. Gate semantics

4. Gate A — authority and rollback baseline

  • Read current SERVER-REGISTRY.md, hxs-4 discovery/as-built records, infrastructure contract, network authority and active phase status.
  • Record durable hxs-4 role exactly as the registry states it. This workload does not redefine it.
  • Record current repo branch/worktree/HEAD and host-change authorization.
  • Snapshot current hxs-4 services, GPU processes, package state relevant to NVIDIA/Ollama, and current systemd overrides before mutation.
  • Write rollback steps before the first package/service change.

5. Gate B — OS, kernel, boot and Secure Boot/DKMS

hostnamectl
cat /etc/os-release
uname -a
uptime
systemctl --failed
mokutil --sb-state 2>/dev/null || true

Record Ubuntu/release/kernel, failed units, Secure Boot state if supported, and DKMS state. A loaded driver is authoritative evidence; Secure Boot is diagnostic context, not an automatic failure.

6. Gate C — PCIe and GPU hardware identity

lspci -nnk | grep -A4 -Ei 'vga|3d|display'
nvidia-smi -L
nvidia-smi --query-gpu=name,uuid,pci.bus_id,memory.total,driver_version,pstate,temperature.gpu --format=csv,noheader
nvidia-smi topo -m 2>/dev/null || true

Verify the actual target is an 8 GB NVIDIA GPU. Record UUID and PCI bus ID. If another GPU is present, record it but do not allocate it to any runtime without a separate decision.

7. Gate D — NVIDIA driver, kernel modules and device access

lsmod | grep -E '^nvidia'
modinfo nvidia | head -n 40
cat /proc/driver/nvidia/version 2>/dev/null || true
ls -l /dev/nvidia*
dmesg -T | grep -iE 'nvidia|nouveau|NVRM|Xid' | tail -n 150
nvidia-smi

Verify:

  • intended NVIDIA module loaded;
  • target device is not unexpectedly owned by nouveau;
  • no unresolved NVRM/Xid errors;
  • device nodes exist;
  • future Ollama service account has effective device access.

8. Gate E — CUDA: driver capability vs toolkit

Do not conflate these layers:

LayerHow verifiedRequirement
NVIDIA drivernvidia-smi, module/versionMust support the actual GPU and meet current Ollama minimum.
CUDA capability exposed by drivernvidia-smiMust be sufficient for the GPU/runtime.
CUDA runtime librariesldconfig, Ollama GPU discoveryMust be usable by Ollama.
CUDA toolkit / nvccnvcc --version if installedNot automatically required for normal Ollama NVIDIA inference.
nvidia-smi
command -v nvcc && nvcc --version || true
ldconfig -p | grep -E 'libcuda|libnvidia' | head -n 80

Never install a full CUDA toolkit merely because nvcc is absent. Install only a proven dependency.

Capacity must cover model blob, temporary pull space, cache/state, logs and reserve. No model artifact belongs in Git.

14. Gate K — pre-acquisition model eligibility

Use current official Ollama metadata for qwen3.5:9b-q4_K_M. Published blob size is ~6.6 GB, but do not declare full-GPU fit from file size. Runtime buffers and KV cache consume additional memory.

This gate answers only:

Is the exact artifact a reasonable candidate to acquire and test on this host?

It may return ELIGIBLE FOR ACQUISITION without claiming eventual 100% GPU residency. True residency is a post-pull live gate.

15. Gate L — install Ollama reproducibly

Resolve current stable Ollama version and official Linux method immediately before execution. For auditability, prefer downloading the official installer to a temporary file, recording its hash, reviewing source/location, then executing it rather than losing the installer identity in a pipe.

curl -fsSL https://ollama.com/install.sh -o /tmp/ollama-install.sh
sha256sum /tmp/ollama-install.sh
# inspect / record current source, then execute under approved sudo flow

After installation:

ollama --version
systemctl status ollama --no-pager
systemctl cat ollama
systemctl show ollama -p User -p Group -p Environment
journalctl -u ollama -n 150 --no-pager

16. Gate M — conservative service configuration

During commissioning, use loopback only and one model/request at a time. Where supported by the installed version, set:

CUDA_VISIBLE_DEVICES=GPU-<verified-8GB-UUID>
OLLAMA_MODELS=<verified-HX-model-path>
OLLAMA_CONTEXT_LENGTH=4096
OLLAMA_NUM_PARALLEL=1
OLLAMA_MAX_LOADED_MODELS=1
OLLAMA_DEBUG=1

Do not set OLLAMA_HOST=0.0.0.0 yet. Keep network exposure as a later gate. After commissioning, disable debug logging unless needed.

17. Gate N — prove GPU discovery before model pull

systemctl daemon-reload
systemctl restart ollama
systemctl show ollama -p Environment
journalctl -u ollama -n 250 --no-pager
nvidia-smi

Confirm Ollama detects an acceleration library and the intended GPU. If it falls back to CPU unexpectedly, this gate FAILS. Do not hide the failure by pulling the model anyway.

Use text-only first; vision is a separate capability test.

ollama ps

Record Processor split, allocated context, VRAM, RAM, load time, prompt evaluation speed and generation speed. 100% GPU is preferred; partial CPU offload must be reported rather than called equivalent.

20. Gate Q — context ladder and three qualification levels

LevelTargetMeaning
Q04KMinimum current Ollama default on <24 GiB VRAM; basic local-runtime commissioning.
Q18K → 16K → 32KIncreasing HX API/tool/repository usefulness; measure residency and throughput each step.

At each level record ollama ps, VRAM/RAM, GPU/CPU split, prompt-eval rate, generation rate and stability. Stop escalation on OOM, severe offload, instability or unusable resource pressure. Do not attempt 256K during commissioning.

  • streaming chat;
  • thinking/reasoning representation where supported;
  • tool definition;
  • tool call ID/name/arguments;
  • tool-result continuation;

22. Gate S — HX Runtime Acceptance

Add ollama-qwen35-9b as a runtime profile. Do not modify the engine-neutral contract. Run:

L2 — live protocol/runtime
L3 — bounded model behavior
L4 — context/resource/performance characterization

Record exact context and Processor split for every behavioral result; behavior measured at 4K must not be silently generalized to 64K.

23. Gate T — controlled network exposure

Only after local API and HX L2 PASS. Configure the current supported Ollama server binding through systemd/environment using the authoritative hxs-4 address. Verify effective environment and listening socket. Re-run minimal remote identity/chat/stream/tool tests from the approved client/control host.

24. Gate U — Anthropic API compatibility before Claude Code

Test /v1/messages directly before launching Claude Code:

  • simple message;
  • streaming;
  • system prompt;
  • multi-turn;
  • tool use/tool result;
  • thinking fields if applicable.

Record known compatibility differences; do not assume parity with Anthropic’s hosted API.

25. Gate V — Claude Code qualification

Context prerequisite. Current Ollama guidance recommends at least 64K context for agents/coding tools. Do not call hxs-4 “Claude Code qualified” merely because Claude Code launches at 4K.

If 64K can be allocated stably, run the bounded workflow:

  1. basic prompt;
  2. read-only repository navigation;
  3. safe tool call;
  4. tool-result continuation;
  5. skill activation;
  6. specialist/subagent;
  7. deliberate HX hook denial;
  8. recognition of denial;
  9. recovery via approved path;
  10. bounded code change.

If 64K cannot be supported, report OLLAMA/QWEN OPERATIONAL — CLAUDE CODE CONTEXT NOT QUALIFIED. That is a valid result, not a failed model installation.

Do not implement vLLM as part of this work. Record the architectural rule:

All visible GPUs are a shared resource unless isolated. Ollama may spread a model across available GPUs when it does not fit one GPU. Therefore a future vLLM workload on another GPU requires explicit device visibility boundaries before either service starts.

Do not assume hxs-4 has a 16 GB GPU. Confirm hardware from registry/live evidence before any vLLM design is activated.

27. Failure handling and rollback

Every mutation must have a recorded inverse before execution. Rollback covers:

  • Ollama service stop/disable;
  • systemd override removal;
  • Ollama binary/libraries per current official uninstall path;
  • service user/group only if created solely for Ollama and safe to remove;
  • model store deletion only after preserving required evidence;
  • network binding rollback to loopback;
  • HX profile disable/defer;
  • verification that GPU processes and port 11434 return to prior state.
