Position. jcode is not being adopted as a replacement for Claude Code. It is being advanced to an aggressive pilot as a complementary local-model execution harness. If the pilot succeeds, HX gains two agent execution lanes: Claude Code for hosted/premium reasoning and jcode for local/private/high-volume execution, both governed by the same HX repository contract.

Harness fit
Excellent

Persistent server/session architecture plus a versioned harness API creates a credible automation substrate.

  • Rust implementation with a large source/test surface, not a thin wrapper.
  • Reads HX-compatible AGENTS.md and Claude-format skills.
  • Can consume Claude-style MCP configuration where transports are supported.

  • Has sophisticated swarm/multi-agent capabilities that may later become useful as an execution substrate for HX specialists.

4. Pilot posture: cautious entry, aggressive execution

There is one synchronization checkpoint before pilot start. At that checkpoint, HX confirms:

  • pilot scope;
  • exact jcode version/artifact;
  • runtime/model path;
  • control-enforcement method;
  • rollback;
  • success/failure criteria.

After that checkpoint, execute the approved pilot aggressively. Do not stop for repeated architectural reconfirmation when the next step is already inside the approved pilot envelope. Stop only on:

  • hard safety/control failure;
  • unexpected repository mutation;
  • runtime/tool fidelity failure;
  • evidence that the selected policy-enforcement approach is not working;
  • owner-defined hard stop.

5. Tool profile decision: FULL

Owner choice: use profile = "full" during the pilot. The purpose is to test jcode as a real agent harness, not an artificially constrained demo.

This changes the testing burden. Because the full profile exposes a broad capability surface, the pilot must inventory and classify every enabled tool before first repo mutation.

6. Memory decision: test both modes

Memory is not rejected. The pilot explicitly compares:

MODE A — MEMORY OFF
baseline harness behavior
deterministic repository context only

MODE B — MEMORY ON
jcode semantic memory / recall / extraction enabled
same task family and model where feasible

Compare:

  • task completion quality;
  • instruction retention;
  • unexpected stale-context influence;
  • cross-session usefulness;
  • context/token efficiency;
  • privacy and evidence traceability;
  • whether jcode memory competes with or complements HX repository authority.

Memory may be retained if it proves useful and remains subordinate to current HX instructions/authority. Repository truth always wins over recalled memory.

7. Policy enforcement: A or C only

Critical adoption gate. jcode's current pre_tool hook is useful but fails open on timeout/spawn/error. HX permanent controls cannot depend solely on that behavior.

Approved solution families:

OptionDispositionDescription
A — upstream fail-closed supportPREFERREDUse/contribute a configurable jcode mode where policy-hook execution failure blocks protected tool actions.
B — HX maintained forkNOT PREFERREDDo not begin by carrying a long-term HX fork solely to alter hook semantics.
C — lower/shared HX enforcementPREFERREDEnforce permanent policy outside jcode's optional hook layer so Claude Code, jcode and future harnesses share the same deterministic control boundary.

The pilot may use jcode's native hook as additional defense-in-depth, but jcode is not considered an approved HX execution harness until A or C provides deterministic permanent-control semantics.

8. Candidate shared-control pattern

Option C deserves serious investigation because it could simplify the entire HX multi-harness architecture.

Claude Code ─┐
             │
jcode ───────┼── shared HX command/file authority gate ── OS/repository
             │
future ──────┘

A lower/shared boundary could enforce permanent rules such as:

  • Ansible prohibition;
  • protected authority-file mutation rules;
  • dangerous filesystem boundaries;
  • approved fleet-control path;
  • credential/secret write controls where appropriate.

The exact mechanism is a pilot research task, not a preselected implementation.

  • jcode reads root AGENTS.md.
  • jcode follows child DOX/AGENTS authority when entering governed subtrees.

18. Pilot failure conditions

Stop and classify rather than rationalize if:

  • jcode cannot reliably follow HX authority.
  • existing Claude-format skills behave incompatibly.
  • full-profile tools create uncontrollable privilege ambiguity.
  • the selected A/C control approach cannot make permanent HX controls deterministic.
  • memory materially overrides stale/current authority incorrectly.
  • OmniRoute translation breaks tool semantics.
  • local model quality is insufficient for the intended task class.
  • jcode introduces unacceptable repository/process instability.
