PERMANENT HX CONTROL PROBLEM — CRITICAL

jcode's native pre_tool lifecycle hook:
  exit 0 = allow
  exit 2 = block

But current jcode behavior fails open on:
- hook timeout
- spawn failure
- missing hook binary
- unexpected execution error/status

This is NOT sufficient as the sole enforcement mechanism for HX permanent controls.

APPROVED SOLUTION FAMILIES:

OPTION A — UPSTREAM FAIL-CLOSED
Investigate whether current/newer jcode already has configurable fail-closed semantics.
If not, determine the cleanest upstreamable design/contribution.

OPTION C — LOWER/SHARED HX ENFORCEMENT
Investigate a deterministic enforcement layer below/around the harness so Claude Code, jcode and future execution clients share the same permanent controls.

Examples of permanent HX rules that must remain deterministic:
- no Ansible
- protected authority-file mutation policy
- approved fleet-control path
- dangerous filesystem boundaries
- other current permanent controls from HX authority

DO NOT:
- immediately create/maintain an HX fork just to change jcode hook semantics
- declare jcode approved before A or C is proven
- rely solely on native fail-open pre_tool for permanent HX policy

Native jcode hook may still be used as defense-in-depth.
