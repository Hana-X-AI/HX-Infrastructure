Executive finding

LoopX is not a feature; it is a competing kernel. It describes its state as the source of truth, drives bounded host turns, admits effects through Agent → Capability → Provider, and owns the operating loop around goals, todo claims, gates, monitoring, quotas, writeback, recovery, scheduling, and handoff. Those are precisely the surfaces HX already distributes across sdd-core, governance files, LangGraph, executors, and the MCP plane.

The correct question is not “Can LoopX plug into HX?” It can. The correct question is “Which existing HX authority would be intentionally delegated to LoopX?” Without that decision, integration would produce dual control: two task ledgers, two orchestration layers, two recovery models, and ambiguous evidence ownership. With a strict boundary, LoopX could become a valuable operational work-state plane beneath constitutional/specification authority and above execution harnesses.

What LoopX really is

goal + policy→durable todo / claims / gates→turn decision→capability + provider effect→validated readback→evidence / quota / recovery

LoopX is a local-first, provider-neutral control plane above coding-agent harnesses such as Codex, Claude Code, Cursor, OpenCode, Pi, and custom runners. Its kernel persists goal state, run history, attention status, leases, compute quota, accepted writeback, and recovery information across individual model sessions. It also includes an agent-native Kanban model, peer-agent coordination, scheduler and heartbeat machinery, bounded external host turns, dashboards and projections, domain capabilities, installers, self-update paths, and experimental memory/context-learning features.

That breadth is both its strength and the core adoption risk. The kernel architecture is disciplined: effects are separated from state transition, quota is intended to be spent after validated writeback, public projection is distinguished from private state, and failure receipts are first-class. The surrounding product surface is much broader and younger: adapters, hooks, MCP servers, HTTP status APIs, launchers, connectors, content/research programs, memory experiments, and install automation all enlarge the trust boundary.

Source-level findings that matter

1. Claude Code hardening is not an HX security boundary

The project candidly states that hardening is not a sandbox. Its PreToolUse hook permits read tools plus TodoWrite, web tools, and tool search. When a turn is allowed, Bash is screened by a small destructive-string denylist and is otherwise admitted. That cannot enforce an authorized workspace, block indirect writes, or reliably prevent network effects. The hook’s fail-closed behavior when state cannot be read is positive, but it does not compensate for the Bash gap.

2. The Claude MCP adapter has correctness defects

  • list_todos() is implemented like should_run() and calls the quota should-run path instead of listing todos.
  • claim_task and complete_task do not mirror the no-goal handling present in the read paths.
  • The subprocess wrapper returns concatenated human output without a typed return-code contract.
  • complete_task decides whether to spend quota by substring matching representations such as "ok": true rather than parsing a stable structured response.
  • The lifecycle smoke directly invokes the CLI for completion instead of exercising the adapter’s actual complete_task behavior. The riskiest bridge is therefore not proven end to end.
Pilot consequence: do not use the Claude hook or MCP adapter in the first pilot. These are not cosmetic issues; they affect task identity, completion, and quota accounting. Require an upstream fix, local reviewed patch, and adapter-level tests before enabling them.

3. Probe registration is weaker than probe policy

The architecture allows a free-form next_probe. Policy requires probes to be read-only, but registration does not structurally prove that property. Do not enable probe execution until capability identity—not human text—determines admissibility.

4. The status service is local-trust, not authenticated control

The service binds to loopback by default; write APIs are disabled by default and limited to loopback, and CORS was tightened after the security release. Those are good defaults. Still, a local non-browser client without an Origin is accepted, and status reads can expose goal state and private Markdown. Treat it as a local operator convenience, not an authorization boundary. Keep it off in the pilot.

5. Installer scope is too broad for reconnaissance-to-pilot transition

The one-line installer resolves and downloads GitHub source and hashes the downloaded archive, but does not verify it against a separately pinned, signed expected digest. The local installer writes user-level executables, releases, Codex skills, and commands by default; optional Claude setup can write MCP configuration, commands, settings, hooks, and a virtual environment. HX should neither use curl | bash nor let the project modify global agent configuration. Use an isolated, exact source pin and manual, minimal entry point.

6. Some execution controls are genuinely strong

  • Caller-approved validation commands use tokenized arguments, no shell, a controlled working directory, a timeout, and recorded status.
  • Worker-command validation is now strict after the security repair.
  • The architecture distinguishes current source state from projections and public from private data.
  • Release automation publishes checksums and GitHub attestations, and dependency review is pinned.
  • The project documents failure and limitation boundaries unusually well.

What HX should borrow even if LoopX is never adopted

  1. Typed turn-result vocabulary. Make “continue, blocked, gated, complete, failed, attention required” machine-verifiable states instead of prose conventions.
  2. Effect interpreter boundary. Decide state transitions separately from provider execution; accept writeback only after readback proves the effect.
  3. Quota after accepted evidence. Failed or unaccepted completion must not consume the same accounting path as validated work.
  4. Leases rather than possession. Claims expire and can be recovered; an agent session is never permanent ownership.
  5. Public projection versus private authority. Dashboards are derived views, never the source of truth.
  6. Independent failure receipts. Preserve why progress stopped even when the executor crashes or the provider is unavailable.
  7. Evidence-first handoff. A successor receives goal state, accepted artifacts, open gates, remaining budget, and provenance—not merely a chat summary.

Proposed bounded pilot

Pilot thesis: LoopX must demonstrate materially better multi-session continuity, recovery, and evidence discipline than HX’s current file-driven method—without creating a second authority. This is a decision proposal, not authorization to install or mutate an HX repository.

Operating envelope

  • Use a disposable greenfield repository, not HX-Infrastructure and not a production service.
  • One bounded goal, one active executor, manual CLI integration, and a short multi-session task with known expected outcomes.
  • Inside this isolated pilot only, LoopX is the sole runtime todo/claim/gate/quota ledger. Do not mirror or dual-write execution todos into the HX actions/issues log.
  • sdd-core remains the source for the goal’s constitution and acceptance criteria. LoopX references those artifacts; it does not rewrite them.
  • Start without LangGraph to validate the kernel boundary. If the kernel passes, add one minimal LangGraph workflow and prove there is exactly one scheduler for each work unit.
  • Pin a supported release or reviewed commit by exact digest. Do not use current untagged main merely because it matches the supplied snapshot.

Explicitly disabled in the first pilot

installers, user/global configuration writes, Claude hooks, Claude MCP adapter, status server and write APIs, scheduler/heartbeat, peer/multi-agent launcher, reward memory, context learning, Lark/OpenViking, research/content/PR programs, probes/next_probe, self-update/auto-repair, dashboards, cloud/network connectors, and all domain capabilities unrelated to the single goal.

Hard-stop conditions

  • Any HX canonical file is mutated by the pilot without explicit operator action.
  • A second routine work/task truth appears or synchronization requires bidirectional dual-write.
  • Completion or quota accounting depends on parsing human-readable output.
  • Unbounded Bash, network access, broad filesystem scope, or global agent configuration becomes necessary.
  • Duplicate effects or quota spend occur after crash/retry.
  • Stale state is accepted, a gate can be bypassed, or private evidence leaks through a projection.
  • The operational burden exceeds the continuity benefit versus the baseline.
  • A pilot finding requires redefining sdd-core, LangGraph, Mem0, LightRAG, MCP, or governance ownership without a separate owner decision.

Final synchronization position

What was learned: LoopX addresses a real missing layer—durable operational work-state across agent sessions—and its kernel contains excellent architecture patterns.
Why it cannot simply be added: it is authoritative by design and collides with HX’s existing execution, tracking, and orchestration boundaries.
Best defensible role: a candidate delegated runtime work-state plane beneath sdd-core intent and above LangGraph/executors, with memory, knowledge, and tool policy staying in their current owners.
Immediate recommendation: reference the design now; do not install it into HX; approve a narrowly controlled greenfield pilot only after the authority decision and adapter/security gates are accepted.
No implementation performed: this reconnaissance executed no project code, installed no package, changed no repository configuration, and started no service.
