HX-Infrastructure · Architecture Decision

OmniRoute as the HX AI Traffic Plane

Formalizes the decision to adopt OmniRoute as the preferred AI gateway/router for HX, replacing the planned LiteLLM gateway role while preserving HX governance, runtime authority and validation boundaries.

Decision: ADOPT — NARROW SCOPE Replaces: LiteLLM gateway role Source snapshot: release/v3.8.50 · exact commit unproven from ZIP Source archive SHA-256: 2b04f4cba777b40ccc2af52ce23e2ffac27f2d8b5bcbd6cef6776b91c96c06e3 Owner exception: SSRF protection globally disabled Prepared by GPT-5.6 Sol 2026-08-14 00:31 America/Panama Reconciled: 2026-08-15 · HX Phase 3
Decision. HX will use OmniRoute as the AI traffic plane / model gateway. OmniRoute replaces LiteLLM in that role. It does not replace sdd-core, SERVER-REGISTRY, HX runtime profiles, HX acceptance, hooks, skills, the owner-approved Agent Zero → Claude Code → Max repository-management hierarchy, infrastructure orchestration or governance.

1. Why OmniRoute fits HX

Protocol fit
Strong

OpenAI- and Anthropic-compatible surfaces allow clients to use stable protocols while backends vary.

Local runtime fit
Strong

Ollama and vLLM are first-class provider types in the reviewed source, matching HX's local-first runtime strategy.

Governance fit
Conditional

Excellent if OmniRoute remains the traffic plane; poor if its own agent/memory/skills/control systems are allowed to compete with HX.

The practical HX problem is not "which single model server should own everything?" It is that HX will have multiple runtimes, model sizes, GPU classes, context limits and API dialects. OmniRoute gives clients one stable gateway while HX retains authority over where workloads live and how they are validated.

6. Owner-approved SSRF decision

HX exception: OmniRoute's SSRF protection will be disabled globally. This is an explicit owner decision, not a default recommendation inherited from upstream.

The reason is pragmatic: HX is a trusted lab/dev network whose intended provider endpoints are private-address runtimes. The operator accepts the reduced SSRF boundary in exchange for unrestricted private-network routing behavior.

This exception does not give OmniRoute infrastructure authority. Compensating HX boundaries remain:

  • When deployed, OmniRoute must be reachable only on the trusted HX network.
  • The gateway must not be exposed directly to the public Internet.
  • API authentication must be enabled for HX clients.
  • OmniRoute service credentials must be scoped to gateway needs.
  • MITM/root-CA, cloud sync, keychain import and unrelated privileged modules remain excluded.
  • Runtime endpoints are configured from approved HX runtime profiles/authority, not discovered as infrastructure truth.
  • HX network/fleet controls remain outside OmniRoute.
  • The SSRF exception must be visible in configuration and documentation so future maintainers do not mistake it for an upstream-safe default.

7. First pilot boundary

The first OmniRoute pilot is deliberately narrow:

DIRECT PATH
HX conformance harness → hxs-4 Ollama → Qwen3.5-9B

VERSUS

ROUTED PATH
HX conformance harness → OmniRoute → hxs-4 Ollama → Qwen3.5-9B

The pilot does not prove "OmniRoute is generally good." It answers whether OmniRoute is sufficiently transparent and useful for HX's traffic-plane role.

Claude Code boundary: the pilot may test Anthropic Messages protocol fidelity, but it does not use Claude Code as the workload client and cannot override workload-specific runtime acceptance. Qwen3.5-9B remains accepted only for bounded local utility inference, not as a Claude Code backend.

Functions enabled in pilot

  • Ollama provider;
  • explicit static model route;
  • OpenAI-compatible gateway;
  • Anthropic-compatible gateway where required;
  • basic health/model discovery;
  • traffic telemetry;
  • global SSRF protection disabled per owner decision.

Functions disabled in pilot

  • auto-routing;
  • multi-model intelligence/fusion;
  • prompt compression;
  • memory injection;
  • context relay;
  • skills;
  • A2A/agent orchestration;
  • MCP mutation/control;
  • MITM/root CA;
  • cloud sync;
  • tunnels unless separately approved.

9. HX acceptance integration

OmniRoute must be treated as another runtime path through the existing engine-neutral acceptance framework.

L0 repository/static
L1 offline protocol fixtures
L2 direct live runtime
L2 routed live runtime through OmniRoute
L3 model/agent behavior direct vs routed
L4 performance/resource overhead
L5 cross-runtime / cross-route conformance

Passing the direct runtime does not prove the routed path. Passing OmniRoute does not prove every backend. Each route is evidence-bound.

11. Deployment shape

Do not adopt the full OmniRoute product topology unless a later need justifies it. Prefer the smallest supported deployment that supplies the gateway core.

Initial implementation preference:

  • pin exact OmniRoute version/artifact digest;
  • use the minimal build/profile where supported;
  • exclude privileged modules not needed by HX;
  • start loopback/local-LAN only;
  • enable API authentication before shared use;
  • store configuration/secrets outside Git;
  • use a managed service/container consistent with current HX conventions;
  • do not introduce Redis/browser sidecars unless a proven required feature needs them.

Any installer, process-execution, exposure, secret-handling or packaging decision requires Aisha, Frank and Vera review. A deployable artifact requires a verified tag or commit and exact artifact/container digest; the reviewed ZIP is source evidence, not by itself a deployment pin.

12. Migration from LiteLLM

If LiteLLM has only been planned/documented and is not yet a live dependency, migration is primarily a repository architecture update:

  1. Find all LiteLLM references in current target-state documents/config/templates.
  2. Classify each reference: gateway role, provider-specific feature, generic OpenAI proxy assumption, or historical note.
  3. Replace active gateway references with OmniRoute.
  4. Do not rewrite historical evidence to pretend LiteLLM was never considered.
  5. Preserve any useful generic gateway requirements rather than copying OmniRoute-specific implementation everywhere.
  6. Add an OmniRoute traffic-plane profile/specification.
  7. Add direct-vs-routed HX acceptance paths.
  8. Add explicit SSRF-owner-exception documentation.
  9. Run repository invariants and confirm no competing gateway authority remains.

14. Success criteria

  • OmniRoute provides a stable OpenAI/Anthropic-facing endpoint across approved HX runtimes.
  • Direct-vs-routed HX L2 tests show tool/stream/error semantics remain acceptable.
  • Gateway latency/throughput overhead is acceptable for development/test/demo workloads.
  • Ollama and vLLM routes can be added without changing client configuration architecture.
  • SERVER-REGISTRY and HX runtime profiles remain authoritative.
  • No OmniRoute memory/skill/agent subsystem competes with HX.
  • No LiteLLM dependency remains in active target-state gateway architecture.
  • Global SSRF disablement is explicit, reproducible and documented as an owner-approved HX exception.
  • Protocol compatibility never overrides workload-specific runtime acceptance; Qwen3.5-9B is not represented as a Claude Code backend.
  • Repository changes follow the external Claude Code → Max council model and do not enable OmniRoute's embedded agent plane.

15. Final architecture position

ADOPT OmniRoute — narrowly.
OmniRoute is the HX AI traffic plane and replaces LiteLLM in that role.

DO NOT adopt OmniRoute as the HX platform.
HX remains the control plane, source of truth, governance system, agent framework and validation authority. 
OmniRoute = HOW AI traffic gets there.
HX = WHAT is allowed, WHERE it runs, WHO controls it, and WHETHER it is proven.
