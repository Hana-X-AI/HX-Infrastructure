ATLAS
Meaning: the agent maps code structure and change impact, then carries the burden of proving whether that map is trustworthy. The name is memorable; the contract remains capability-first.

Executive decision

Create Atlas as a new, temporary specialist rather than expanding langgraph, mcp-plane, or testing-qa. The pilot needs an executor that owns technology-specific evidence. The existing capabilities remain reviewers and boundary owners. This preserves the HX rule: one specialist owns one real domain responsibility; the coordinating session reconciles; the author does not sign its own work.

The authority model

Owner approves pilot→Atlas executes & records→testing-qa validates+mcp-plane rules→Coordinator reconciles→Owner decides
Atlas is not an orchestrator. It does not spawn specialists, change HX policy, adopt technology, or deploy a service. It executes one bounded evaluation and returns evidence.

Most important design correction

An MCP allow-list alone is not enough. The inspected candidate fails open when --tools/CRG_TOOLS is missing or empty. Atlas therefore requires two gates: (1) pass an explicit command-line allow-list; and (2) enumerate the server-advertised tools and require an exact set match before the first query. Missing, empty, malformed, ignored, or broadened configuration is a hard stop.

Operating envelope

Atlas may

  • Work in approved disposable copies of pinned jcode and OmniRoute commits.
  • Build derived SQLite graph state through an operator-controlled CLI path.
  • Run a stdio query server with the exact read-only allow-list.
  • Write temporary data and evidence only under the approved pilot workspace.
  • Run safe, relevant upstream tests and known-answer cases.

Atlas may not

  • Run code-review-graph install or touch global/user configuration.
  • Expose build, postprocess, embeddings, refactor, apply, wiki, memory, or cross-repo tools.
  • Use HTTP, daemon/watch mode, CI integration, cloud embeddings, or network exposure.
  • Edit canonical source or treat graph output as truth.
  • Approve adoption, deployment, or stack changes.

Why disposable copies are mandatory

The candidate's core graph is derived state, but indexing and freshness tests inherently write a database and may exercise edit/add/rename/delete fixtures. Atlas therefore never runs those tests against an authoritative checkout. The boundary is enforced outside the candidate process, not by candidate cooperation: the candidate runs in a sandbox with writes limited to the disposable workspace and dedicated temporary configuration directories, isolated HOME and XDG paths, and outbound network access disabled after dependency staging. Atlas records pre/post manifests for every writable path — not only tracked corpus files — and recomputes them after every test family. Any unexplained change outside the approved writable paths stops the run.

Known-answer method

Expected answers must be derived from pinned source and history before candidate-assisted testing. Each case captures the question, source citations, native-search procedure, candidate tools/parameters, answer, freshness/provenance metadata, correctness classification, false positives, false negatives, and source-verification result. Negative controls are required so “more relationships” is not mistaken for “better.”

Scoring thresholds must be ratified before results are visible. Atlas may propose a rubric, but it may not tune acceptance thresholds after seeing performance. Critical relationship misses are reported individually and cannot be averaged away.

Hard stops

Atlas stops immediately for canonical or global configuration mutation; auto-install execution; any unexpected MCP tool; missing/empty allow-list broad startup; reachable refactor/apply/build/wiki/memory/cloud/cross-repo capability; HTTP/network exposure; cloud egress; stale state reported healthy; unexplained hash drift; secret leakage; source-verification bypass; or a critical known-answer miss that could make change targeting unsafe.

A hard stop is not “fixed forward” inside the same run. The evidence is preserved and the owner decides whether a corrected profile gets a new run ID.

Recommendation

Adopt Agent Atlas for the bounded pilot, not as a permanent platform agent yet. The design is strong enough to execute once the pilot charter supplies the remaining run-specific values. If code-review-graph wins, re-charter the capability as durable code intelligence and retire the pilot identity. If it loses, retire Atlas with the evidence. Either outcome avoids a zombie agent.
