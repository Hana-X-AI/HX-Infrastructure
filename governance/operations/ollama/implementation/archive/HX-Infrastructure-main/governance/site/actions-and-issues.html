iss-015 issue open related: act-014, iss-014
Item

Prompt overflow is silently truncated, not refused. On the hxs-4 Ollama endpoint configured with a 65,536-token context, prompts that exceed the window are not clamped to it and do not raise an error. The runtime discards the excess and processes only 32,770 tokens — roughly half the configured window — and the model then answers confidently from the remainder. Measured 2026-08-14: ~37K tokens processed fully at 43,880; ~54K processed fully at 64,880; ~74K and ~85K both collapsed to 32,770. In the 85K case a specific fact placed at the very start of the prompt was destroyed by the truncation and the model reported that the text did not contain it. No error, no warning, no indication in the response that more than half the input had been discarded.

Impact / outcome

Severe and silent. The failure produces a wrong answer that is indistinguishable from a right one, which is worse than a refusal because nothing signals that the result is unsound. It is the direct cause of the Claude Code disqualification: Claude Code reports contextWindow: 200000, has no mechanism to discover the real limit, and so routinely sends 69,000–73,000 tokens into a 65,536 window. Affects any client capable of exceeding the window, not only Claude Code.

Resolution / closeout

Mitigation, not a fix. No runtime setting was found that converts this into an error. Until one exists, any client pointed at this endpoint must bound its own prompt below the configured window, and no client that cannot be bounded should be trusted with it. The practical margin is server-measured: configure clients with an input budget derived from server-reported token accounting (window minus reserved output capacity), not a fixed near-ceiling estimate. The validated safe input limit must be below the configured window with sufficient headroom reserved for output tokens. Raising the window would move the cliff but not remove it — the collapse behaviour is a property of the runtime, not of the chosen window size. Recorded in the workload definition at tests/ai-runtime/workloads/qwen35-9b-ollama.json under context_overflow_behavior so the constraint travels with the workload.
