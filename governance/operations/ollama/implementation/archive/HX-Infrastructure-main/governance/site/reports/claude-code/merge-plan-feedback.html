Verdict

Adopt Claude's shape and GPT-5.6's discipline. Claude's plan is correctly scoped for a project that has asked to keep process light: a lean services/<name>/build.md per service, a curated agent roster, defect lessons distilled rather than imported. GPT-5.6's plan is heavier than this project wants, but two of its rules are cheap and worth taking wholesale — provenance tags on every migrated artifact, and scanning before import. Neither plan is wrong. Taken together they are better than either alone.

Where they differ, and what I would do

Process weight

Claude leanGPT-5.6 heavy

GPT-5.6 proposes 8 migration stages, formal acceptance criteria, an agent file contract and an Agent Zero operating contract. Claude proposes 7 steps and one lean build document per service.

Claude is right for this project. The owner has twice asked to keep process light, and the legacy repository's own ceremony — 90-file task trees per node — is exactly what produced 411 files for two services. But take GPT-5.6's acceptance criteria anyway: they are one short list, not a workflow, and without them "the merge is done" has no definition.

Git history — both plans discard 22 commits

disagree

Both plans treat the legacy repository as an archive to mine, with the current repository as the sole Git lineage. That is the right authority model, but it silently throws away real history.

Hana-X-AI/HX-Infrastructure has 22 commits on main — the DEFECT-062 to DEFECT-065 resolution trail, the quality-gate development, and a full CodeRabbit review pass. That is the record of why the legacy decisions were made. Preserving it costs one command and changes nothing about authority:

git tag legacy/pre-relocation-2025-12-04 origin/main
git push origin legacy/pre-relocation-2025-12-04

One lineage on main, as both plans want. The legacy history stays recoverable instead of existing only in a zip. I previously recommended a full unrelated-histories merge; both plans are right that this is cleaner, and a tag gets the benefit without the mess.

Neither plan noticed the destination already exists

gap

Both treat "legacy" as an archive or zip. It is a live, private GitHub repository under the org account, last pushed 2025-12-04.

That changes the merge from a filesystem exercise into a push. It also resolves act-005, open since 2026-08-11, which records that this project has no off-machine copy. The destination has existed the whole time. See the correction below — that action names the wrong repository.

Target structure

services/fuller tree

Claude's services/<name>/build.md — one document per service covering install, config, integration, validation and gotchas — is the better fit. It collapses the legacy 90-file task tree into something a person will actually read, and it maps cleanly onto the architecture, since every service already has an assigned host.

One refinement: name the owning agent and the target host in each build document. Claude's plan says to; it is worth making non-optional, because that single line is what keeps a build document traceable without any surrounding process.

Factual corrections

Checked against the live repositories and the current working tree today. None of these invalidate either plan.

The registry discrepancy is resolved

now stale

GPT-5.6 §4 flags that architecture v0.3 carries a role mapping while SERVER-REGISTRY.md has blank roles and Phase 2 blocked, and correctly refuses to resolve it, requiring an owner decision.

That instruction did its job. The owner ratified v0.3 on 2026-08-13. All 15 fleet servers now carry an assigned role and workload, all seven Phase 1 gate conditions are met, act-012 is closed, and Phase 2 is READY. The Phase 1 command guard is released as a direct consequence. Both reports predate that and should be read as of the morning of 2026-08-13.

"Current files: 759" counts Git internals

correction

Claude's summary strip reports 522 legacy files against 759 current files, implying the current repository is the larger of the two.

The current repository holds 132 project files. The 759 figure is very close to the 766 entries in the backup zip, which includes .git object files — so the count came from an archive listing rather than the working tree. The legacy figure of 522 is correct. The legacy repository is roughly four times the size of the current one, which strengthens rather than weakens the case for selective migration.

act-005 names the wrong repository

correction

Neither plan could have known this. act-005 has been blocked since 2026-08-11 on the claim that the repository name is taken by "an unrelated public Ansible project".

That refers to hanax-ai/HX-Infrastructure — a different, public repository under the personal account. The org repository Hana-X-AI/HX-Infrastructure is private and owned. The blocker was wrong, the entry is being corrected, and the action closes as soon as main is pushed.

The credential warning checks out

confirmed

GPT-5.6 §7.1 states the legacy documentation contains confirmed plaintext credentials and requires scanning before any import.

Corroborated. standards/credentials-vault-management.md is 1,108 lines with 249 vault references and contains at least one credential-shaped assignment. Whether that specific line is a live value or an illustrative example, the rule stands: scan every migrated file, and never carry a value across. This is not new security work — it enforces an existing project rule that credential values are never recorded in documentation.

What I would do

Claude's plan, with four amendments. Roughly a day of work, most of it the fact-correction sweep rather than the merge itself.

  • Push first, decide later. One command puts 16 commits somewhere other than this workstation. It is independent of every other decision here and should not wait for them.
  • Tag the legacy history before main moves, so 22 commits stay recoverable at no cost.
  • Follow Claude's structure — curated agent roster, services/ build docs, distilled defect lessons, legacy ceremony left behind.
  • Borrow two things from GPT-5.6: a provenance header on every migrated artifact naming its legacy source, its migration date, whether it is historical or adapted, and the current document it must not override; and a short acceptance-criteria list so the merge has a definition of done.

One thing neither plan raises: the fact-correction sweep is the bulk of the effort, not the migration. Every carried-forward file needs 192.168.10. → 192.168.50., hx.dev.local → hx.local.arpa, /home/agent0 → repository-relative paths, and agent0 → hxsa, with addresses taken from the registry and never guessed — reading an address out of a terminal paste already produced four wrong values out of fifteen on this project (ll-031).
