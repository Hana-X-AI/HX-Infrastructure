02 How to Read the Stack

FOUNDATIONAL / DECIDED is an owner-ratified direction or durable project standard. PROPOSED CORE belongs in the target platform; an item marked IN BY DEFAULT remains in the architecture unless a materially superior replacement or evidence-based exclusion emerges. CONDITIONAL is a real stack need with an unresolved product, model, or configuration choice. ROADMAP has credible value but should not be treated as current platform authority. DEFERRED is intentionally later. OUT / SUPERSEDED should not appear as target-state architecture.

03 True-North Architecture Principles

One authority per concern

One traffic plane, one durable-memory authority, one registry/governance truth, and one execution-control model. Integration must not create shadow authorities.

Capability before placement

Define the service contract and accepted use first. Hardware placement, deployment order, and optimization follow later.

Evidence-bounded acceptance

A runtime is accepted for a specific client, task, context envelope, and access path—not “accepted” in the abstract.

Open interfaces, replaceable components

Prefer OpenAI-compatible model APIs, MCP for tools, PostgreSQL/Redis/Qdrant for standard data roles, and contracts that permit components to change without redesigning the platform.

Native, observable operations

Linux services, isolated environments, explicit configuration, native Bash/SSH automation, tests, logs, and reproducible evidence are the baseline.

Dev/test realism without production theater

Exercise the complete stack and meaningful controls, but avoid premature HA, orchestration complexity, and a broad hardening program before the platform works.

06 Platform Plane Specifications

Plane 01Governance & Execution Control

Git-centered, specification-driven operating system for the project

FOUNDATIONAL Git + GitHub sdd-core pattern Markdown authorities dark-mode HTML reviews Claude Code agents · skills · hooks

Role: Hold architectural truth, decisions, contracts, policies, evidence, tests, actions, issues, and lessons; route AI agents to the correct authority; enforce boundaries before commands are executed.

Proposed shape: Repository-native specifications and governance remain authoritative; human reviews are rendered as polished HTML. Claude Code is the primary AI execution environment, augmented by specialist agents, reusable skills, and fail-closed hooks. Git history and tests provide provenance.

Boundary: AI tooling may propose and execute authorized work; it may not redefine owner decisions, silently widen acceptance, or mutate servers during planning.

Plane 02Systems Foundation

Simple, inspectable Linux service foundation

FOUNDATIONAL Ubuntu Server systemd Python virtual environments Bash + SSH/SCP PowerShell control scripts chrony local DNS/FQDN

Role: Provide the common operating substrate, service lifecycle, time, naming, secure operator access, and repeatable fleet administration.

Operating model: One isolated environment per Python service; one explicit systemd unit per long-running service; absolute interpreter paths; native configuration and logs. The validated fleet-control baseline is Bash over SSH/SCP with explicit host mapping and verification modes.

Boundary: This is deliberately not an Ansible stack and does not require Docker, Kubernetes, or another orchestration authority.

Plane 03Edge & Traffic

Separate human ingress from model-traffic authority

PROPOSED CORE NGINX OmniRoute OpenAI-compatible APIs LiteLLM SUPERSEDED

NGINX role: User-facing reverse proxy, TLS termination, path routing, and controlled ingress. It is the web edge, not the model-routing brain.

OmniRoute role: The narrow, governed AI traffic plane—model endpoint registry, routing, policy, access mediation, and observability for model calls. It should become the only approved path for remote consumption of otherwise local runtimes.

Boundary: OmniRoute routes traffic; it does not own agent orchestration, durable memory, model acceptance, or general MCP execution. LiteLLM remains historical/reference evidence and must not survive as a competing target gateway.

Plane 04AI Inference

Two runtimes with intentionally different jobs

PROPOSED CORE vLLM Ollama Hugging Face ecosystem Qwen family gpt-oss family

vLLM role: Strategic high-throughput and higher-context serving for primary reasoning, coding, and agent models through an OpenAI-compatible surface. Preferred where explicit context enforcement, batching, tensor parallelism, and production-style serving behavior matter.

Ollama role: Bounded local utility inference, rapid model evaluation, and simple loopback services. Complementary to vLLM, not a universal backend. The measured Qwen3.5-9B workload is accepted only for bounded local use and explicitly refused as a Claude Code backend.

Model layer: Qwen remains the primary family for reasoning, coding, and utility roles; gpt-oss remains a candidate for agent/tool execution.

Plane 05Retrieval & Knowledge

Document knowledge, vector search, graph retrieval, and code intelligence remain distinct

PROPOSED CORE Qdrant LightRAG Docling + Granite Docling 258M ADOPT WITH LIMITS Crawl4AI TEI or Infinity BGE-M3 / Nomic BGE reranker Code-Graph-RAG

Qdrant role: Vector storage and similarity search for governed collections. Collection ownership and embedding dimensions must be frozen before first ingest.

LightRAG role: Human, document, governance, and domain knowledge retrieval with graph-enhanced context.

Docling + Granite Docling role: High-quality PDF and document parsing. Granite Docling 258M is HX's preferred embedded Docling VLM for scans, complex reading order, tables, equations, and code. The conventional Docling pipeline remains the operational fallback for clean born-digital material.

Granite Docling acceptance: ADOPT WITH LIMITS. Pin model revision, prefetch artifacts, validate DocTags, bound page time/retries, and measure fidelity/performance.

Plane 06Agents, Memory & MCP

Orchestration, durable memory, and tool exposure are separate capabilities

PROPOSED CORE LangGraph FastMCP custom Hana-X MCP services Mem0 · IN BY DEFAULT Streamable HTTP

LangGraph role: Stateful workflow and agent orchestration, durable checkpoints, structured human interrupts, resumability, and capability composition.

FastMCP role: Standard implementation framework for exposing governed Hana-X capabilities through MCP (document conversion, crawling, retrieval, infra intelligence).

Mem0 role: Proposed-core durable user/agent memory service with its own storage, retention, and deletion boundary. In by default. Must not duplicate LangGraph checkpoints or LightRAG knowledge.

Boundary: LangGraph owns orchestration state; Mem0 owns durable user/agent memory; LightRAG owns domain knowledge; FastMCP exposes tools; OmniRoute owns model traffic.

Plane 07Data & State

Durable relational state, fast ephemeral state, and narrowly scoped local state

PROPOSED CORE PostgreSQL Redis SQLite — narrow use only

PostgreSQL role: Platform state, identities, configuration, audit, service-owned schemas, and durable LangGraph checkpoints.

Redis role: Cache, queues, pub/sub, sessions, and short-lived coordination—not authoritative durable state.

SQLite role: Permitted only for genuinely local, low-concurrency, service-owned history where portability is valuable.

Plane 08Experience & Automation

Human interface, agent-aware UI, and workflow automation

PROPOSED CORE Open WebUI CopilotKit AG-UI n8n

Open WebUI role: Primary ready-made chat and model interaction surface for development, testing, and demos.

CopilotKit + AG-UI role: Custom agent-aware application experiences, streaming state/events, and embedded copilots.

n8n role: Deterministic workflow automation and external-system integration.

Plane 09Observability & Recovery

Metrics, dashboards, logs, exporters, and tested recovery

PROPOSED CORE Prometheus Grafana Loki node_exporter DCGM exporter backup/snapshot tooling

Role: Collect host, GPU, service, model, and application telemetry; retain searchable logs; verify backups and restores.

08 Explicitly Excluded & Superseded Technologies

Ansible

PERMANENTLY OUT

Native Bash/SSH is the validated fleet-control baseline. Do not retain Ansible in plans, agents, procedures, or compatibility language.

LiteLLM as target gateway

SUPERSEDED

OmniRoute is the proposed traffic-plane authority; running both as peers creates routing and policy ambiguity.

Kubernetes

NOT JUSTIFIED

The dev/test/demo environment does not presently need a cluster scheduler, HA control plane, or a second operational substrate.

Docker as platform dependency

NOT REQUIRED

Current HX direction favors bare-metal services with virtualenv and systemd isolation.

Direct network-exposed Ollama

REFUSED

Ollama’s local endpoint remains loopback-only. Remote use must traverse the governed traffic plane.

Premature production machinery

DEFERRED

Broad HA, multi-tenancy, service mesh, and exhaustive hardening are not current prerequisites.

10 Recommended True-North Statement

HX-Infrastructure is a self-hosted, specification-governed AI platform for development, testing, and demonstrations. It uses native Linux services and Bash/SSH operations; NGINX for TLS termination, path routing, and controlled human ingress; OmniRoute for governed model traffic; vLLM and Ollama for distinct inference classes; LangGraph for orchestration; Mem0 for durable user/agent memory; FastMCP for bounded capability exposure; PostgreSQL, Redis, and Qdrant for clearly separated state roles; LightRAG, Docling with Granite Docling 258M as its preferred embedded VLM, Crawl4AI, and purpose-built embedding/rerank serving for knowledge workflows; Open WebUI plus CopilotKit/AG-UI for user experience; n8n for deterministic automation; and Prometheus, Grafana, and Loki for operational visibility. Claude Code, jcode, and future read-only code intelligence support the engineering process under repository-enforced authority.
