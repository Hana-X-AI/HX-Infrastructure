Proposed Technology Agent Roster

A validation draft derived from the proposed technology stack and prior HX agent work. It lists proposed human agent identities, component ownership, lifecycle, and the evidence state of each name. It does not create, activate, or install any agent.

Recommended roster shape: capability-first, human-named, broad catalogue with lean activation.
Create durable specialists only for technologies that own a distinct platform responsibility. Combine tightly related components under one accountable agent. Keep pilot technologies temporary until adoption is earned. Do not create one autonomous agent per package, exporter, model, database client, or UI library.

Pinned rule — mandatory for every agent definition

BLOCKING PRE-TASK GATE. No agent may begin task execution, invoke task tools, edit files, change configuration, install software, deploy services, or rely on remembered assumptions until the required Knowledge Base Review is complete.

Knowledge Base Review (mandatory pre-task step)

Before executing any task, you must review the knowledge base located in your assigned operations directory. Each agent's operations directory contains the unzipped source repository for its system.

Base path: C:\Users\JarvisRichardson\Desktop\HX-Infrastructure\governance\operations\<AgentName>\<repo-release-folder>

Example (OmniRoute): C:\Users\JarvisRichardson\Desktop\HX-Infrastructure\governance\operations\OmniRoute\OmniRoute-release-v3.8.50

Some tasks will also require reading from other directories in the shared library. When a task depends on information outside your own operations directory, review the relevant directory before proceeding rather than assuming or inventing details.

No task execution begins until this review is complete.

Application rules

  • Existing agents: retrofit this directive one agent at a time and preserve each agent's identity and capability contract.
  • New agents: include the directive in the first-pass definition before activation or use.
  • Technology directory mapping: the human agent name maps to the applicable technology-named directory shown in the operations crosswalk; the placeholder does not require renaming an existing operations folder.
  • Multi-technology agents: review every assigned operations directory needed for the task. For example, Drew may need both diagram-design and gitdiagram; Skye may need both skills and skill-expert.
  • Cross-domain tasks: review the relevant shared-library or adjacent operations material before proceeding.
  • Hard stop: if a required directory, release folder, source repository or shared dependency is missing, ambiguous, inaccessible or stale beyond safe use, stop and report the blocker. Never fill the gap with assumption or invention.
  • Completion acknowledgement: the agent's task response must identify the operations source reviewed before claiming execution began.

Consolidations that prevent agent sprawl

  • One model-portfolio agent: Quincy covers Hugging Face, Qwen and gpt-oss; do not create one agent per model family.
  • One embedding agent: Evan covers TEI/Infinity, embedding models and rerankers because these decisions are coupled.
  • One observability agent: Oscar covers Prometheus, Grafana, Loki and exporters.
  • One UI-framework agent: Cody covers CopilotKit and AG-UI; Wendy remains separate because Open WebUI is an operated product.
  • One MCP-plane agent: Felix owns FastMCP and transport/exposure contracts; individual MCP services remain bounded capabilities, not autonomous specialists by default.
  • One Code Intelligence authority: Atlas is the current pilot identity. Code-Graph-RAG remains a comparator, not a peer agent.
  • OmniRoute stays federated: its repository size justifies Max plus nine stewards and ephemeral task cells; do not collapse it into a generic “OmniRoute expert.”
