Deep Review of the Claude Code Docling Pilot Brief

The brief is well structured and much closer to an execution contract than a planning essay. It correctly freezes the repository architecture, makes the ledger the source-selection mechanism, protects the sanitized-history boundary, forces provenance, and uses the pilot to test the transformation model rather than Docling deployment. 3. P0 — Change “current authoritative service document” to target-state design authority

The brief currently risks converting a plan into operational fact. It says the service document is current and authoritative while the same document will contain VERIFICATION REQUIRED items and no infrastructure work is allowed.

The correct authority model is:

Status: PLANNED / TARGET-STATE
Authority:
  - authoritative for current intended Docling MCP service design
  - not evidence that the service is installed, configured, reachable, or validated
  - SERVER-REGISTRY.md remains authoritative for placement/role
  - servers/<host>/configuration.md becomes as-built authority after implementation

Change the service tree line from:

Status and authority        # current, authoritative; supersedes 2025

to:

Status and authority        # current target-state design; supersedes 2025 design,
                            # but does not assert implementation/as-built state

This single wording change protects the project from a future AI reading a planning artifact and assuming Docling is already operational.

6. P1 — Resolve the “plan mode” vs file-write contradiction

The document calls this “plan mode,” but also instructs Claude Code to create service.md, update manifest.jsonl, and create provenance-index.jsonl. Those are repository writes.

I recommend renaming the mode:

MODE: REPOSITORY-MIGRATION / DOCUMENT-ONLY
Allowed:
  - read repository and sanitized legacy ref
  - create/edit service.md, manifest/provenance and pilot report
  - run local read-only/search/render/validation commands
  - use a dedicated migration branch/worktree

Forbidden:
  - SSH or remote host execution
  - package installation
  - server/service configuration
  - deployment
  - changing SERVER-REGISTRY roles
  - changing manifest dispositions/schema
  - changing infrastructure

If Claude Code has a literal product “plan mode” that blocks writes, leave it in plan mode only to produce the proposed diff, then explicitly switch to repository-document execution for the approved pilot. Do not rely on ambiguous wording.

8. P1 — Do not mark historical files “migrated” merely because their knowledge was cited

The ledger-closure section says historical source rows used in the document should advance from pending to migrated. That can confuse “knowledge was distilled” with “the file was migrated into main.”

Keep the source-file disposition semantics intact. The historical file remains historical in the sanitized ref. What changed is that knowledge from it was consumed.

Preferred model:

disposition: historical
location: sanitized-ref
distillation_status: used | reviewed-not-used | blocked
distilled_into: ["services/docling-mcp/service.md#failure-handling"]
reviewed_by: [...]
migration_status: unchanged unless v3 explicitly defines it as knowledge-migration state

If v3 does not contain a separate distillation field and the schema is frozen, use provenance-index.jsonl to record used/reviewed-not-used and leave the historical row’s file-migration status unchanged. Do not invent a misleading state transition just to “close” the row.

10. P1 — Correct the vLLM / Docling boundary

The current wording says “Docling serves via vLLM-fronted stack.” That conflates two different responsibilities.

Use:

Docling is the document-processing service.
Any LLM-dependent Docling workflow must use the current model-gateway contract
(e.g. LiteLLM routing to approved model backends) if such an integration is part

Do not describe core Docling conversion/OCR as being “served by vLLM.”

This matters because otherwise the first service document can accidentally encode a false runtime dependency.

Similarly, remove “Blackwell toolchain pins” from the Docling-specific verification list unless the current target host and current Docling design actually require GPU acceleration. A fleet-wide GPU concern should not silently become a Docling requirement.

11. P1 — Separate required current integrations from legacy integration candidates

The target structure currently mandates LiteLLM, Qdrant, Redis and LightRAG integration-contract subsections. That is fine only if current architecture requires each direct integration.

For each legacy integration, Claude Code should classify:

StateMeaning
CURRENT REQUIREDExplicitly required by current architecture/service placement; author the contract.
INDIRECTDocling reaches the capability through another current service/gateway; do not invent a direct client contract.
LEGACY CANDIDATEUseful historical integration but not yet approved for current design; retain in provenance/verification list.
RETIREDNo current role; lesson only.

This prevents the pilot from turning “it integrated in 2025” into “Docling must directly integrate in 2026.”

12. P1 — SME sign-off needs a real gate

The brief correctly says missing reconstructed specialist contracts should be reported, not silently skipped. Tighten that into an acceptance rule:

  • A historical 2025 SME review is evidence, never current sign-off.
  • A current SME sign-off may be recorded only if the corresponding current capability contract exists and the review actually ran.
  • If a required current SME contract is missing, mark the relevant section SME REVIEW REQUIRED.
  • The pilot may still produce a useful draft, but it does not receive “multi-SME pass” status until the required reviews exist.

I would make docling-mcp, infrastructure-ops and testing-qa mandatory final reviewers. Other integration SMEs become mandatory only for integrations that survive as CURRENT REQUIRED.

15. P2 — Make “concise” measurable enough to prevent another pseudo-spec

I would not impose a rigid word limit, but give Claude Code an explicit compression rule:

  • No historical chronology.
  • No copied task sequences.
  • No defect narratives longer than the current constraint + provenance.
  • No duplicated installation and validation prose.
  • Prefer tables for integration contracts and verification items.
  • If the document exceeds roughly 6,000–8,000 words, Claude Code must explain what cannot be safely condensed.

The exact number is less important than giving the pilot a concrete signal that compactness is part of the experiment.
