F1

§0 cannot both retire the guard and meet its own acceptance criteria

blocking

§0 retires hx-phase1-guard.ps1 and the phase1-gate skill. §7 requires "Remediation suite 153/0" as an acceptance criterion. Those two cannot both hold.

Measured nowCount

Deleting the guard fails the suite immediately. The tests are not incidental to it — a fifth of the assertions exist to prove the guard denies what it should and permits what it should, and that history is why the guard works at all (ll-002: an untested guard pattern is an unguarded path).

Resolve by choosing one: retire the guard and rewrite those 18 assertions in the same change, restating the expected count; or keep the guard as a storage-and-credential guard with the phase logic removed, which preserves the tests and the permissions.deny rules the infrastructure contract requires in any phase. The second is less work and loses nothing. What must not happen is deleting the hook and discovering the suite number afterwards.

F2

Dropping the Phase 2 column breaks three live hooks

blocking

§0 says to "drop the now-obsolete Phase 2 status column" from SERVER-REGISTRY.md. That column is not obsolete — it is read at runtime by three hooks, in both the active and packaged copies:

.claude/hooks/hx-common.ps1        Test-HxPhase2Open parses **Phase 2 Status:**
.claude/hooks/hx-phase1-guard.ps1  gates on it
.claude/hooks/hx-session-state.ps1 reports it into every session
claude-hooks/claude-hooks/hooks/   the packaged copies of all three

The registry currently reads Phase 1 COMPLETE, Phase 2 READY. Removing the column makes Test-HxPhase2Open fall through to its default, which is guard active — so dropping the column to signal "the gate is gone" would re-block the fleet. The failure is silent and points the wrong way.

Resolve: if the guard is retired per F1, remove the column and its three readers in one change. If the guard is kept, keep the column. Either way, column and readers move together.

F3

done

All 15 fleet rows carry an Assigned Role and Workload/Model transcribed from v0.3, the FQDN column was corrected from not configured to the resolving hxs-N.hx.local.arpa names, all seven gate conditions are ticked, and act-012 is closed. F4

"Retire the gate" and "the gate is complete" are different outcomes

decide

The manifest frames the phase gate as something to remove. The repository records it as something that was satisfied: seven of seven conditions met, Phase 1 COMPLETE, Phase 2 READY.

Stripping the gate language deletes the evidence that Phase 1 was completed properly — fifteen servers discovered, documented, reviewed and assigned before any configuration began. That record is the reason the fleet inventory can be trusted.

Suggestion: retire the gate as a control while keeping it as a record. Mark the section historical and dated rather than removing it. The control has already done its job and released; erasing it costs the provenance and buys nothing.

F5

The manifest carried the credentials it warns about

fixed

§6 correctly identifies the exposure and mandates scanning every migration commit. The manifest itself then printed the password four times and the API key once, in a document destined for a governance directory and a published artifact.

Redacted before commit — five occurrences here, plus two more in the 11:25 deep-pass document. The working tree now holds zero credential values. Neither file had been published, so nothing left the workstation.

The exposure is not closed by redaction. The value is already in committed history via 43530f5. Both credentials need rotating regardless of what any file says now, and that is unaffected by the merge.

F6

Acceptance criterion 1 fails against the current repository

tension

§7 requires "no secret object in active history". The current repository's active history already contains one, from this morning (43530f5). The criterion cannot pass as written without rewriting history.

Resolve by choosing one: rewrite history before the push, which is clean but discards commit hashes already cited across the governance log; or restate the criterion as "no secret object introduced from this point, and both exposed credentials rotated", which is honest and achievable. Rotation is what actually neutralises the risk — a value in an old object is harmless once it no longer opens anything.

F7

Half the password-guard claim confirmed; half unverifiable here

partial

§3b marks hx-password-guard-hook.py as exclude-and-rebuild because it "contains secret literals and fails to compile".

Secret literals: confirmed. Fetched from the live org repository — 4,236 bytes, and it contains the exposed password. A guard that hard-codes the credential it defends against is a good reason to rebuild rather than migrate, and it is a third location for that value beyond the two already known.

Fails to compile: not verified. Python is not installed on this workstation, so I could not run py_compile. Recording it as unverified rather than repeating it — the disposition is right either way, and the reason given for it should be one that was actually checked.

What the manifest gets right

  • File-level, not thematic. 26 commands, 6 hooks, 6 gates, 10 standards, 18 templates, 17 procedures and both node trees each carry a disposition. That is the artifact all three reviews asked for.
  • Seven disposition types with a legend — adopt / adapt / reconstruct / covered / historical / retire / exclude. "Covered" is the one most plans omit, and it is what stops a merge re-importing things the current repo already does better.
  • The 411 node files collapse to two build documents. Correct. Importing 90-file task trees would recreate the ceremony the owner has twice asked to avoid.
  • Registry-driven IP validator rather than a hardcoded subnet. Better than the hardcode this project proposed, which would have become the next stale validator.
  • Agents reconstructed, not copied. Verified independently: hx-agents/ in the live org repository holds five description documents and no per-agent profiles. The profiles do not exist to copy, in the archive or the remote.
  • Transform facts into new documents rather than editing historical ones in place — preserves provenance, and matches the lesson this project learned when stale cross-host claims had to be corrected across thirteen records (ll-030).

Recommended order

Unchanged from the manifest except that F1 and F2 are settled before §0 runs, and one step is already done.

  • 1. Rotate both credentials. Independent of everything else, unblocked, and the only action that actually closes the exposure.
  • 2. Decide F1 and F2 together — guard retired with tests rewritten, or guard kept with phase logic stripped. The Phase 2 column follows whichever is chosen.
  • 3. Push to the org remote. Still the largest unmitigated risk: nineteen commits on one workstation. Independent of the merge.
  • 4. Then §0 as amended, skipping the roles row, and re-baseline the suite number deliberately rather than discovering it.
  • 5. Then §1 onward as written.
