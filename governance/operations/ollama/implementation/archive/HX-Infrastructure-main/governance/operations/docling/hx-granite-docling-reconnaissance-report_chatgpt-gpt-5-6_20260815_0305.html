What it actually is

Granite Docling is an image-and-text-to-text model specialized for document pages. It combines a SigLIP2 vision encoder, a projector derived from the Idefics3 pattern, and a Granite 165M language model. It reads a rendered page and emits DocTags—Docling’s structured markup representing content and layout. Docling then converts those tags into its unified document object and exports Markdown, HTML, JSON, and other formats.

PDF / slide / scan→page image→Granite Docling→DocTags→DoclingDocument→Markdown / HTML / JSON / RAG

It consolidates functions traditionally split across OCR, layout analysis, reading-order reconstruction, table recognition, formula recognition, and post-processing. It supports full-page and bounding-box-guided inference. English is the primary language; Japanese, Chinese, and Arabic support is explicitly experimental.

The architecture correction

Granite Docling = Docling’s preferred embedded VLM, not HX’s general vision model.
  • Docling Serve owns the model weights, cache, page rendering, inference configuration, DocTags validation, and document export.
  • Docling MCP remains a thin governed tool surface; it owns no weights and does not become a model gateway.
  • OmniRoute is not in the core conversion path. Granite Docling is an implementation detail of the document capability, not a remotely consumable conversational endpoint.
  • LightRAG/Qdrant receive normalized, validated Docling output. They do not parse the original document.

Do not discard the conventional Docling pipeline

Granite Docling should be the preferred VLM, but the classic Docling pipeline remains valuable. The strongest design is a controlled dual-path capability:

PathBest useWhy retain it
Conventional Docling pipelineClean born-digital PDFs, Office documents, routine bulk conversion, and control comparisonsLikely faster and more deterministic where embedded text and layout metadata are already reliable.
Granite Docling VLM pipelineScans, complex reading order, tables, equations, code, damaged text layers, and fidelity escalationUnifies visual understanding and structured generation and materially improves difficult page elements.

The routing rule must be evidence-based. HX should not assume that every scanned document requires Granite or that every born-digital document does not. The acceptance corpus will determine whether Granite becomes the universal default with fallback, or an escalation path selected by document characteristics.

Material constraints and risks

  1. Performance is not yet proven on HX’s intended execution class. The 258M parameter count is small, but full-page autoregressive output can still be expensive. CPU feasibility is not the same as acceptable throughput.
  2. It can hallucinate structure or content. IBM’s model card acknowledges small-model generation risks. For ingestion, a fluent wrong table or equation is more dangerous than an explicit conversion failure.
  3. Language coverage is uneven. English is primary; Japanese, Chinese, and Arabic are experimental. Other languages are not established by the reviewed sources.
  4. vLLM has a special model revision requirement. Official instructions use the untied revision because tied-weight support failed in the cited vLLM line. HX should not choose vLLM for this model merely because vLLM is already in the inference stack; Docling’s default Transformers integration is the clean starting path.
  5. First-use downloads violate reproducibility. Docling can automatically download the model. HX should instead pin the exact model revision, prefetch it, verify hashes, and bind the model cache explicitly before service start.
  6. Remote URLs are an input-security surface. A conversion service that accepts arbitrary URLs can become an SSRF or uncontrolled-download mechanism. Preserve Docling Serve's default-deny URL policy for remote fetching: retain private-address blocking, disable automatic redirects, and prefer staged local files when remote access is unnecessary. If remote fetching is enabled, bind the service to a trusted interface or require an authenticated, network-policy-enforcing proxy.
  7. Output length and loops require guards. The examples allow up to 8,192 generated tokens per page. Enforce page timeout, output-token ceiling, valid DocTags parsing, and bounded retries; never silently ingest malformed output.

Proposed acceptance evaluation

No open-ended demo is needed. Use a known-answer corpus covering the material HX expects to ingest:

  • born-digital prose with headings, lists, footnotes, and multi-column reading order;
  • scanned pages at several qualities and rotations;
  • simple and nested tables, including merged cells;
  • inline and block equations;
  • source-code blocks with indentation and syntax;
  • slides with mixed text, images, and charts;
  • at least one English and one available non-English sample;
  • adversarial long pages and malformed/unsupported documents.

Executable and reproducible. Each gate carries an explicit threshold, baseline, repeat count, and pass/fail rule — not a qualitative impression. Every run produces an execution manifest pinning corpus checksums, rasterization settings, prompts, decoding parameters, device, dtype, dependency versions, and model revisions, and retains the raw DocTags, the normalized output, and any failure artifacts for that run. High-risk or failed documents are quarantined or routed to human review, never silently ingested.

Required stack corrections

  1. Mem0: change from CONDITIONAL to PROPOSED CORE / IN BY DEFAULT. Its role remains durable user/agent memory, excluding LangGraph checkpoints and LightRAG knowledge. Replacement or exclusion requires a demonstrably superior solution or a material architecture conflict.
  2. Docling: express the stack item as Docling + Granite Docling 258M (preferred embedded VLM). Retain the conventional pipeline as a benchmark control and operational fallback.
  3. Model routing: keep Granite Docling inside the Docling service boundary. Do not route routine conversions through OmniRoute and do not expose Granite Docling as a general-purpose vision endpoint.

Final recommendation

Conditionally keep it — pending the acceptance gates. Granite Docling adoption and any default-routing policy remain conditional on passing the defined acceptance gates: CPU feasibility, performance, language coverage, reliability, and the benchmark evaluation. It is the strongest default candidate for HX's embedded Docling model and should enter the proposed architecture as such, but adoption is not settled by this recon. The open questions include default-routing policy (universal Granite-first versus selective escalation) and the gate outcomes above; routing is not the only unresolved question. Decide routing from a conventional-versus-VLM corpus benchmark, while pinning the model revision and enforcing strict output validation. This does not authorize installation, model download, or deployment.
