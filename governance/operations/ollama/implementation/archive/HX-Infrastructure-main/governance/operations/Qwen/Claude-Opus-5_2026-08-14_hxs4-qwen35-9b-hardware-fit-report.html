1Executive summary

The rule from the DS4 rollback was applied literally: hardware fit first, runtime and model selection second, implementation third. So the first thing built was the fit gate, and the first thing run was the fit evaluation — before any Ollama machinery, any install path, or any download.

The result is a single number worth acting on: after weights and a stated runtime allowance, roughly 0.36 GB of VRAM headroom remains on the target device. That is enough that 4K is plausible and not enough to declare it. Everything downstream follows from that.

Host mutation is not authorized, and the prompt says to stop

Installing Ollama, pulling a model and writing systemd overrides is Phase 3 server implementation. GOALS-AND-OBJECTIVES.md places Phase 3 after Phase 2 repository consolidation, which is the current phase. The deterministic HX guard independently denies package installation and model downloads.

The prompt's own rules are "UNVERIFIED = BLOCKED, not PASS" and "stop at the first failed or missing prerequisite", and its preflight requires recording whether host mutation is currently authorized. It is not. So Phases A1–A9 through N were not executed on the host, and nothing was inferred in their place.

What the gate refuses to do

It does not estimate KV cache. Weights are known from the published artifact size and the runtime allowance is a stated, adjustable 1 GB rather than a hidden fudge factor — but a fabricated KV figure would convert a guess into a false PASS, which is precisely the failure mode the DS4 pass exposed.

So it proves what arithmetic can prove — weights against VRAM, and the headroom that remains — and marks every context level MEASURE. The 4K verdict is "plausible", not "yes".

4The headroom finding, and what it means for 64K

~0.36 GB is the whole story

The weights fit. What is left over is the problem. Every KV allocation, at every context length, has to come out of roughly 0.36 GB — and that number does not grow as the context does.

Ollama's own guidance recommends at least 64K context for coding and agent tools. Going from 4K to 64K multiplies the KV footprint by about sixteen against headroom that stays fixed. This does not need a measurement to see the direction of.

Adjusting the runtime allowance moves the number but not the shape: at a 0.5 GB allowance the headroom is ~0.86 GB, still fixed while the demand scales.

That is why the three acceptance states are kept apart rather than collapsed:

A model that runs beautifully at 4K is state A. It is not state C, and the advertised 256K maximum is evidence of neither.

5GPU isolation is mandatory before any residency claim

An asymmetric pair makes this a correctness issue, not tidiness

hxs-4 carries a 16311 MiB card and an 8151 MiB card. Current Ollama may spread a model across all visible GPUs if it does not fit one. Without isolation, a successful load proves nothing about the 8 GB device — it may simply have borrowed the 16 GB one, which is reserved.

So the target must be pinned by UUID, never by index. GPU 0 is not durable identity: indices reorder. The UUID is not in repository evidence — the as-built record captured index, name, PCI bus ID, driver and memory, but not UUID. That is a live nvidia-smi -L query, and it is recorded as a gate rather than guessed.

7Upstream re-verification — not performed

The artifact size is carried forward, not confirmed

The prompt requires re-checking official Ollama sources at execution time: qwen3.5 tags, qwen3.5:9b-q4_K_M metadata, install docs, GPU support, context docs, Anthropic compatibility. That check was not run, so the ~6.6 GB figure and the tag are recorded as stated in the approved prompt, requiring verification rather than as confirmed fact.

The workload file carries digest: null and verified_upstream_on: null deliberately. The DS4 pass showed what happens when a version number is trusted from a document — upstream had moved two major versions and changed its protocol framework.
