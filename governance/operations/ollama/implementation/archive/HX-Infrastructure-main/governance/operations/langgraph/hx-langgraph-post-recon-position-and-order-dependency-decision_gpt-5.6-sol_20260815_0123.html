2. The central correction: dependencies are phase-relative

The earlier LangGraph distillation report classified the model gateway and MCP tool plane as CURRENT REQUIRED integrations. That was correct relative to the proposed service design being reviewed, but it should not be misread as saying both must already exist before the LangGraph Python package can be installed.

TECHNOLOGY INSTALLATION
        ≠
CORE RUNTIME VERIFICATION
        ≠
PERSISTENCE VERIFICATION
        ≠
MODEL-INTEGRATION VERIFICATION
        ≠
MCP-INTEGRATION VERIFICATION
        ≠
FINAL SERVICE ACCEPTANCE

Each layer has different prerequisites. The implementation order should be derived from those dependency edges after reconnaissance of the complete stack.

3. FastMCP and the MCP-plane question

Yes: if FastMCP is deployed first, it can resolve the LangGraph MCP-plane dependency. But the dependency is closed by a verified HX MCP-plane contract, not merely by the presence of a fastmcp package or a process answering on a port.

Current FastMCP supports network-accessible Streamable HTTP, multi-client service deployment, authentication, server composition, namespacing and proxying. Current LangChain MCP adapters support loading remote HTTP MCP tools into a LangGraph StateGraph. These capabilities make FastMCP a credible implementation substrate for the HX MCP plane.

Therefore MCP is not inherently a blocker to core LangGraph installation. It becomes a required gate when the implementation phase claims that LangGraph's MCP-dependent workflow capability is ready.

7. How final implementation order should be chosen

Do not choose order from the old phased roadmap because that roadmap predates multiple current architecture decisions, including OmniRoute replacing LiteLLM and the newer jcode/Code-Graph-RAG findings.

After Recon is complete across the stack, construct a dependency DAG and optimize for:

  1. Foundation dependencies first — host baselines, storage, service isolation, networking/time/DNS.
  2. Shared state before dependents where it unlocks meaningful acceptance — e.g. PostgreSQL before LangGraph persistent-checkpoint acceptance.
  3. Traffic plane before model-dependent application acceptance — OmniRoute before claiming remote LangGraph inference capability.
  4. MCP plane before MCP-dependent integration acceptance — FastMCP first if it is cheap/logical in the final DAG; otherwise defer only that verification slice.
  5. Knowledge/memory systems according to actual workflow dependencies, not because an old diagram placed them earlier.
  6. Observability at the earliest point where it materially improves validation, while respecting the dedicated spare-node plan.
Important: a dependency appearing later in the final order does not invalidate earlier component work. It changes the truth state of a particular verification claim. Use PASS, BLOCKED — DEPENDENCY NOT YET PRESENT, or DEFERRED BY IMPLEMENTATION ORDER rather than inventing substitutes.

8. LangGraph install strategy once its turn arrives

The execution handoff should install the embedded open-source core, not the standalone Agent Server, and it should verify capability progressively according to whichever dependencies already exist at that point.

Stage A — host / authority / version preflight
Stage B — dedicated Python environment
Stage C — pinned embedded LangGraph core
Stage D — deterministic no-LLM graph tests
Stage E — checkpoint security controls
Stage F — PostgreSQL checkpointer if PostgreSQL is ready
Stage G — failure-injection / independent-connection persistence tests
Stage H — OmniRoute model integration if traffic plane is ready
Stage I — FastMCP integration if MCP plane is ready
Stage J — evidence + rollback + status classification

This sequence verifies the technology without prematurely freezing the final orchestration topology or service contract.

9. Installation-time non-negotiables

  • Resolve the LangGraph host from current SERVER-REGISTRY; do not infer from historical material.
  • Dedicated virtual environment/service dependency tree.
  • Re-check current official LangGraph release at execution time and pin exact released versions.
  • Pin to a reviewed, patched line — this position was verified against LangGraph 1.2.11; pin that or a later patched release, and require patched versions of every selected checkpoint backend (langgraph-checkpoint, langgraph-checkpoint-postgres, langgraph-checkpoint-sqlite).
  • Do not install floating main.
  • Do not deploy standalone Agent Server as part of this workstream.
  • Do not enable/use LangGraph Store; Mem0 remains the durable cross-thread memory authority.
  • Set LANGGRAPH_STRICT_MSGPACK=true for checkpoint deserialization.
  • For any manually constructed serializer or checkpointer, pass an explicit allowed_msgpack_modules allowlist to the JsonPlusSerializer constructor rather than relying on the default; do not widen it without a proven need.
  • Keep pickle fallback disabled unless explicitly approved for a proven need.
  • Evaluate checkpoint encryption before persisted sensitive state is accepted.
  • For Postgres, call setup() as a deliberate migration step and prove persistence through an independent connection/session.
  • Do not call a config echo a persistence test.
  • Do not claim OmniRoute or MCP integration if those planes do not yet exist.
  • No Ansible.

12. Final position

Proceed with stack reconnaissance, not more LangGraph capability review.

When whole-stack Recon is complete, determine implementation order from the actual dependency graph. When LangGraph's turn arrives, install and verify the embedded core using the companion execution prompt. Integrations that already exist become active acceptance gates; integrations that are later in the sequence remain explicitly deferred and are verified when their turn arrives.
