HX Migration Method — Accepted as Standard GOVERNANCE DECISION

Ratifies the repository legacy-mining method as proven and permanent, and adds two validation principles the two pilots earned. Companion to repository-migration-pattern.md.
Author Claude (Opus 4.8)Date 2026-08-14Status ACCEPTEDOwner ratification required to commit

Decision

The repository migration / legacy-distillation method — the frozen pattern in governance/policy/repository-migration-pattern.md (ledger schema + invariants, single-source-of-record archive, capability-contract + separate-context review, provenance, acceptance gates) — is ACCEPTED as proven and becomes the repository's standard legacy-mining workflow. It is no longer a pilot. Future services run the workflow directly; they do not get pilot framing, but they DO get the same gates.

1Evidence — validated twice, on rising difficulty

PilotDifficultyOutcome
Docling (1st)1 live integration boundary; risk was package mechanicsAccepted after a corrective pass. Method mechanics validated.
LangGraph (2nd)Stateful orchestrator, 6 live integration boundaries; risk is authority/state driftMethod held. Deliverable correctly failed — three capability reviews FAIL, one CONDITIONAL — and caught a same-day cross-workstream architectural contradiction (an endpoint accepted loopback-only on one host, then treated as remotely consumable by a design on another) before any infrastructure was touched.

The controls that caught real errors were the ones the pattern predicted: separate-context capability review, per-row provenance counting, source-hash verification, and the refusal to inherit a value without resolving it. The pattern needs no structural change — only the two additions below.

2Two permanent principles (added to the pattern)

P-A · Gate construction

A validation gate must specify how it verifies, not only the property it claims to verify. A gate that names the right property but is constructed so it cannot fail is worse than no gate — it ships confidence.

Earned by: the LangGraph flagship checkpointer gate named the correct property (persistence correctness) but the two constructions an implementer reaches for first — a config echo and a same-connection read-back — both pass while persistence is broken. The corpus already held the correct construction (cross-connection read-back + fault injection with the failing run retained); the design cited the defect and missed the method.

P-B · Acceptance scope

An acceptance must state exactly what it authorizes and how that was verified — never more. Corollary: where an authorization has materially different scopes, make them distinct acceptance states (e.g. accepted-local-runtime vs accepted-network-consumable) rather than one verdict read broadly.

Earned by: the Qwen loopback-only acceptance authorized local commissioning use and was later read as remote reachability. The verdict was correct; its scope was implicit, so a second workstream over-read it. Applies to runtime acceptance and migration acceptance alike.

3What "standard workflow" means going forward

  • Future services are distilled with the frozen pattern + the resolved ledger + the legacy/2025 archive as source of record — no new pilot ceremony.
  • Every run still carries the full gates: separate-context SME reviews (no author self-certification), per-row provenance bound to the ledger hash, no-shadow-tree, target-state (not as-built) authority, source-hash verification, and honest coverage counting.
  • The two principles above are enforced as part of the pattern: gates specify construction; acceptances state scope.
  • A service's method pass is independent of its design acceptance. The method succeeding by producing a failing, corrected design is a success, not a regression.
