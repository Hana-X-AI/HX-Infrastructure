Hook Operationalization Plan

Operational design for evolving the existing HX Claude Code hook package from five approved project hooks into a small, deterministic enforcement layer that complements—not replaces—the repository's governance, skills, agents, tests, and native Bash/SSH fleet-control model.

Design rule. Skills and governance explain how HX work should be performed. Hooks enforce only the small number of deterministic invariants that must survive context loss, subagent boundaries, phase transitions, and human error.

1. Source baseline

The local hook package already installs five project hook behaviors without replacing unrelated .claude/settings.json content: SessionStart, PreToolUse, PostToolUse, SubagentStop, and Notification. Its installer is intentionally idempotent, preserves unrelated settings/hooks, and backs up an existing settings file before modification.

Current Claude Code hook semantics were cross-checked against the official hook reference and hook guide: project hooks are shareable from .claude/settings.json; PreToolUse can allow/deny/ask/defer; SubagentStop can block completion; and ConfigChange can block a project settings change from taking effect in the active session. Remain a compact dashboard: current phase state and registry counts. Do not turn it into a giant context injector or upstream skill router.

Phase gate

hx-phase1-guard.ps1

Continue to block role-specific/persistent configuration while Phase 2 is blocked. Once the authoritative registry opens Phase 2, this hook should stop enforcing Phase-1-only restrictions.

Validation

Keep immediate post-edit validation for discovery and registry artifacts. Extend it with registry-driven consistency checks; do not replace the existing checks.

Human UX

Installer

4. New hook: permanent policy guard

Purpose: enforce architectural prohibitions that remain true in every phase.

Event: PreToolUse for shell execution tools currently used by HX (Bash|PowerShell in the local package).

Initial rule set

Pattern/categoryDecisionReason
ansible, ansible-playbook, ansible-galaxyDENYAnsible is permanently outside the HX execution model. The validated native Bash/SSH fleet-control pattern remains authoritative.
Other commandsExit 0, no JSON outputDo not turn this into a generic shell allowlist or a duplicate of the phase guard. Unregulated commands pass through without emitting a permission-decision payload.

The hook must be phase-independent and must not depend on SERVER-REGISTRY.md Phase 2 state. It should not duplicate destructive-storage rules already owned by permissions.deny.

6. Extend discovery validation with registry-driven identity checks

Implement inside hx-validate-discovery.ps1 initially. Refactor to a helper later only if maintainability requires it.

SERVER-REGISTRY.md→ parse current identity truth→ servers/*/discovery.md→ compare

Checks

  • Duplicate current IP in registry → fail.
  • Duplicate current hostname/FQDN where uniqueness is required → fail.
  • Discovery identity disagrees with the corresponding current registry identity → fail with exact host/field/value.
  • Legacy endpoint/address presented as current → fail only when the current contracts make that distinction deterministic.
  • Missing data → use the existing lifecycle/phase semantics rather than inventing completeness requirements.
Critical rule: do not hardcode the current 192.168.50.x host map into another validator. The registry/current network contract is the data source. The validator checks consistency; it does not become a second inventory.

7. New hook: configuration integrity

Purpose: detect and reject weakening of the project-level Claude control configuration.

Event: ConfigChange, initially scoped to project_settings.

The hook should validate that required HX hook registrations and critical project controls remain present and structurally valid. If an invalid project-setting change occurs, block that configuration from becoming active in the running session and record a concise audit event.

Defense in depth, not sole protection. Current Claude Code documentation says ConfigChange can block a project setting change from taking effect in the active session. It does not mean the hook itself rewrites the changed file back to its old bytes. Therefore hx-authority-edit-guard.ps1 remains the first-line control for edits to .claude/settings.json; hx-config-integrity.ps1 is the post-change backstop.

8. Settings integration

Update the existing hook configuration rather than replacing it. Preserve unrelated project hooks and all non-hook settings.

Existing:
  SessionStart  -> hx-session-state.ps1
  PreToolUse    -> hx-phase1-guard.ps1
  PostToolUse   -> hx-validate-discovery.ps1
  SubagentStop  -> hx-validate-subagent.ps1
  Notification  -> hx-notify.ps1

Add:
  PreToolUse Bash|PowerShell -> hx-permanent-policy-guard.ps1
  PreToolUse Write|Edit      -> hx-authority-edit-guard.ps1
  ConfigChange project_settings -> hx-config-integrity.ps1

Do not rely on execution ordering between independent PreToolUse handlers. Each guard must be self-contained and safe if another guard also denies the same tool call.

9. Installer changes

Update apply-hooks.ps1 and its package fragment/readme so re-running the installer produces the new canonical hook set without damaging unrelated local/project settings.

  • Copy the three new scripts into .claude/hooks.

  • Preserve existing unrelated hooks.
  • Preserve permissions.deny and every other non-hook setting.
  • Continue backing up an existing settings file before modification.
  • Update verification documentation to include ConfigChange and the added PreToolUse handlers.

11. Explicit non-goals

  • No wholesale rewrite of the existing hook package.
  • No Ansible integration.
  • No generic shell allowlist.
  • No giant philosophy/context hook.
  • No WebFetch cache/provenance hook yet.
  • No permanent tool-failure ledger yet.
  • No secret scanner implemented as a noisy edit hook unless a deterministic low-false-positive current requirement exists; prefer repository tests/pre-commit validation.
  • No file-placement police hook merely because legacy code had one; structural assertions belong in tests where possible.
  • No additional hook event just for registry/IP checking.
  • No security-hardening or MCP-control expansion beyond this bounded Claude Code control-plane task.

12. Implementation sequence

  1. Preflight: inspect current repository authority chain, .claude/settings.json, existing hook scripts, current tests, discovery/sync workflows, and current PowerShell conventions.
  2. Baseline tests: prove the current five-hook package passes before modifying it.
  3. Permanent guard: add and test the Ansible prohibition independently.
  4. Authority guard: implement protected-path classification only after reconciling actual registry/discovery workflows.
  5. Discovery extension: add registry-driven identity consistency without a hardcoded parallel inventory.
  6. Config integrity: add project-settings validation as a secondary backstop.
  7. Installer/settings: update the fragment, installer, and README idempotently.
  8. Regression: run all current hook/repository tests plus the new tests; use /hooks for final runtime verification.
  9. Report: produce a dark-mode HTML completion report with exact files changed, test evidence, and any deviations.

13. Definition of done

  • The existing five hook behaviors still function.
  • Three new permanent control behaviors are operational.
  • Ansible is denied in every phase.
  • The Phase 1/Phase 2 guard retains its original bounded responsibility.
  • High-authority files cannot be casually mutated by specialists/subagents.
  • .claude/settings.json has both pre-edit protection and post-change integrity validation.
  • Discovery/registry identity validation derives truth from current authoritative data rather than another hardcoded map.
  • The existing destructive-storage permissions.deny rules are preserved unchanged unless a separate explicit owner decision modifies them.
  • The installer remains idempotent and preserves unrelated settings/hooks.
  • No new hook acts as a workflow engine or duplicate governance system.
  • All current and new tests pass.
  • A fresh Claude Code session shows the expected hook configuration and no startup errors.

14. Control-plane model

Governance / contracts→ Skills / agents→ Hooks→ Tests / evidence

Governance states the rule. Skills/agents explain the approved workflow. Hooks enforce immediate deterministic boundaries. Tests/evidence prove the repository and infrastructure state remain internally consistent.
