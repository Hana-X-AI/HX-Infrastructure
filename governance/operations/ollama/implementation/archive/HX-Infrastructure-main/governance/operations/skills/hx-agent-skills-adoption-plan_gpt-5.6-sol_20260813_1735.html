Agent Skills Integration & Migration Brief

This brief converts the review of addyosmani/agent-skills into an HX-native implementation direction. The objective is to mine useful mechanisms, workflows, and specialist-agent patterns into the existing HX repository without importing a competing lifecycle or control plane.

Decision: proceed with selective adoption Status: target-state implementation brief As-built: not asserted Prepared by: GPT-5.6 Sol 2026-08-13 17:35 America/Panama
Executive decision. Treat the upstream repository as a source library, not as a package to install wholesale. Preserve sdd-core and the HX repository's existing governance as the single execution backbone. Transform selected upstream concepts into HX-native skills, references, agents, and validation gates.

1. Authority and non-negotiable constraints

Control plane

Keep one authoritative workflow

  • .specify/memory/constitution.md remains the global governance authority.
  • knowledge/instructions.md remains the local repository/context router.
  • Do not introduce a second SDD lifecycle, task schema, meta-router, or parallel governance hierarchy.
  • Internal agent/source material may remain Markdown; human review artifacts should be polished HTML.
Infrastructure orchestration

Preserve the proven native fleet model

  • Ansible is permanently out of scope. Remove or revise stale references rather than reintroducing it.
  • The validated Bash/SSH fan-out pattern from hxs-cp remains the baseline for simple fleet control.
  • Skills may improve planning, validation, documentation, and script quality; they must not silently replace the orchestration model.
Truth model

Do not manufacture current state

  • Distinguish TARGET-STATE, AS-BUILT, DISCOVERED, PROPOSED, and LEGACY/HISTORICAL.
  • Migration artifacts must never elevate polished target-state prose into proof that a service is installed or configured.
  • Runtime evidence and authoritative host/service configuration remain the source of truth after implementation.
Scope control

Keep deferred work deferred

  • Do not let skills work reopen deep MCP exposure/security-hardening work before the core platform is operational.
  • Observability-specific implementation remains a later workstream tied to the reserved spare server.
  • Performance matters, but this development/test/demo environment is not being optimized at the expense of simplicity and full-stack coverage.

4. HX-native capability set to synthesize

HX Context Engineering

Teach agents how to resolve authority, load only relevant context, and avoid stale or cross-environment leakage.

HX Source-Driven Research

Require version-aware authoritative research for unstable infrastructure/tooling facts and explicit evidence for recommendations.

HX Adversarial Validation

Formalize independent fresh-context review of material claims, architecture choices, migration decisions, and risky implementation steps.

HX Planning & Gates

Dependency-first phases with entry criteria, exit criteria, verification evidence, rollback considerations, and bounded scope.

HX Architecture Decisions & Authority

Capture why decisions were made and tag documents/configuration with explicit authority/state semantics.

HX Legacy Migration

Mine legacy knowledge without importing stale environment state; transform useful service knowledge into the current repository model.

5. Agent/persona pattern to retain

The upstream distinction is valuable: skills = how, personas/agents = who, and the coordinating session/workflow = when/orchestration. HX should retain narrow specialist agents and keep synthesis in the main coordinating layer.

HX coordinating agent / operator→ independent specialist reviewers→ evidence-backed reports→ single reconciliation / merge
Do not create meta-orchestrator personas. Specialists should not recursively spawn or route to other specialists. Parallelism is appropriate only for independent investigations whose outputs can be reconciled centrally.

7. Execution sequence

Phase 0 — Preflight and authority discovery

  1. Read the current HX constitution, repository instructions, skill/agent directories, validation tooling, and the latest merge/migration material.
  2. Identify the actual current canonical locations for skills, specialist agents, references, validation rules, and human-facing documentation.
  3. Search for stale references to Ansible, obsolete orchestration patterns, legacy task schemas, or competing SDD routers relevant to this integration.
  4. Do not modify anything until the authority map and conflicts are explicit.

Gate: repository authority map completed; no target paths guessed.

Phase 1 — Build the migration manifest

  1. Inventory the six priority skills plus upstream docs/agents.md and relevant adoption guidance.
  2. Classify each useful section using ADOPT / ADAPT / MINE-REFERENCE / DEFER / REJECT.
  3. Explicitly record why spec-driven-development and using-agent-skills are not imported as governing frameworks.
  4. Identify reusable shared references that priority skills depend on, so no broken external references are introduced.

Gate: every proposed migrated element has a target, rationale, conflict check, and validation method.

Phase 2 — Implement HX-native skill/reference content

  1. Create or update HX-native capabilities using the repository's established skill format.
  2. Rewrite paths, terminology, assumptions, and examples around HX infrastructure—not generic application development.
  3. Keep core skill entrypoints lean; place substantial domain knowledge in references loaded only when needed.
  4. Encode explicit authority/state labels and the “verified vs inferred” distinction where relevant.

Gate: no imported skill creates a second control plane; no unresolved upstream path references remain.

Phase 3 — Reconcile specialist agents

  1. Compare current HX specialist agents against useful upstream persona patterns.
  2. Retain broad specialist capability but keep activation lean and purpose-specific.
  3. Ensure specialists produce bounded evidence/review outputs and do not recursively orchestrate other agents.
  4. Use parallel fan-out only where investigations are independent.

Gate: one coordinating layer; no routing-only persona; agent responsibilities are non-overlapping enough to justify their existence.

Phase 4 — Repository cleanup and controls

  1. Remove or revise stale Ansible references encountered in touched scope.
  2. Remove obsolete paths/instructions that would conflict with the new HX-native skills.
  3. Rebuild validators or controls only from current authoritative data; do not carry forward stale environment assumptions.
  4. Add provenance/attribution for substantially reused MIT-licensed content.

Gate: no contradictory instructions, no broken references, no legacy mechanism presented as current.

Phase 5 — Validation and handoff

  1. Run repository-native validation/linting for skills, agents, links, and references.
  2. Perform a clean-context review: can a fresh agent determine the correct authority order and choose the right HX capability without loading the whole skills catalog?
  3. Run adversarial checks for false current-state assertions, implicit Ansible reintroduction, competing lifecycle schemas, and unbounded hardening/observability scope.
  4. Produce a concise human-facing HTML completion report with changed files, decisions, rejected material, residual risks, and follow-up candidates.

Gate: all critical conflicts resolved; surviving deferred items are explicitly parked rather than silently omitted.

8. Acceptance criteria

  • sdd-core remains the sole execution/governance backbone.
  • No wholesale import of the 24-skill upstream lifecycle.
  • No using-agent-skills meta-router added as an HX authority.
  • No upstream tasks/plan.md/tasks/todo.md convention introduced unless it already matches current HX canonical structure.
  • Six priority capabilities are represented in HX-native form or deliberately consolidated where duplication would be harmful.
  • Specialist agents are capability-first, independently useful, leanly activated, and non-recursive.
  • Ansible remains absent from future-facing procedures and orchestration recommendations.
  • Target-state and as-built/current-state claims remain clearly separated.
  • Substantial upstream reuse includes appropriate MIT provenance/attribution.
  • All new references resolve locally; no skill depends on missing upstream repo-relative shared files.
  • Validation demonstrates that a fresh agent can navigate HX authority correctly without context flooding.
  • A dark-mode HTML completion report records final changes and any deferred follow-up work.

9. Explicit non-goals

  • Do not redesign HX around the upstream repository.
  • Do not add Ansible.
  • Do not convert this effort into a security-hardening or MCP-exposure project.
  • Do not bring the observability workstream forward merely because an upstream observability skill exists.
  • Do not copy legacy or upstream environment assumptions into current authoritative state.
  • Do not create a general-purpose meta-agent whose primary purpose is routing other agents.

10. Expected deliverables from Claude Code

  1. Migration manifest mapping exact upstream sections to HX dispositions and targets.
  2. HX-native skill/reference changes implementing the selected capabilities within existing repository conventions.
  3. Specialist-agent reconciliation where upstream persona patterns materially improve existing HX agents.
  4. Repository cleanup for touched stale/conflicting references, especially Ansible and competing lifecycle/router assumptions.
  5. Validation evidence showing clean authority, valid references, bounded activation, and no false as-built assertions.
  6. Human-facing completion report in dark-mode HTML.
