HX Infrastructure · Phase 3 Architecture Brief

OmniRoute Multi-Tier AI Agent Architecture

Repository reconnaissance, methodology validation, and a scalable operating model for Claude Code, Max, persistent domain stewards, and ephemeral task cells.

Prepared 16 August 2026 · Source snapshot: OmniRoute release/v3.8.50 ZIP · Static inspection only; no untrusted repository code executed.

Final recommendation: keep the three tiers—but federate Tier 2.
Claude Code remains the Meta-Agent. Max remains the single repository coordinator and integration authority. Max is joined at Tier 2 by nine persistent domain stewards whose knowledge and contracts survive across tasks. Tier 3 consists of short-lived, single-purpose task cells. Max alone dispatches work; sub-agents do not recursively spawn more agents.

Executive assessment

What is right

The proposed separation of intent, repository coordination, and atomic execution is fundamentally sound. It matches OmniRoute’s strong worktree discipline and reduces uncontrolled context mixing.

What would fail

A lone Max between Claude and every worker becomes a routing, memory, review, and integration bottleneck. OmniRoute’s cross-cutting request path makes folder-only delegation unsafe.

What changes

“Primary Agent” becomes a council led by Max. Persistent means a versioned role contract and maintained knowledge base—not an endlessly accumulating chat context.

Operating principle

One dispatcher, one writer per worktree, explicit domain reviewers, independent verification, and every meaningful fix converted into reusable repository knowledge. Every role has a human name; the technical title remains explicit.

Why this split fits OmniRoute

  • The request path crosses protocol, policy, providers, security, state, and quality; the primary agents mirror those architectural seams.
  • Agent and extension surfaces are large enough to deserve Nolan’s dedicated stewardship rather than being buried inside generic backend ownership.
  • CLI, Electron, installers, embedded services, and packaging make Frank’s delivery domain materially different from application engineering.
  • Vera is independent because the repository has extensive ratchets and two non-overlapping test runners; “tests passed” must identify which evidence was actually run.

Knowledge is a product of the workflow. OmniRoute’s existing fix history often captures root cause and regression guards well. Sue institutionalizes that strength so future agents retrieve a tested lesson instead of rediscovering the same failure.

End-to-end task protocol

  1. Claude establishes intent: desired outcome, user constraints, priority, and approval boundary.
  2. Max classifies: task type, risk, affected domains, lead steward, reviewers, and whether a freeze or owner ruling applies.
  3. Sam maps impact: follows imports and runtime flow, not just folders.
  4. Human/operator confirms base: required by repository rules before worktree creation.
  5. Max issues the task packet: exact scope, hard stops, acceptance commands, and return schema.
  6. Ruth proves the problem: failing-then-passing test, or explicitly documented live validation where the repository permits it. If a test or fixture is needed, she returns a patch against the confirmed base with its hash and failing command; she never edits the task branch.
  7. Max transfers the proof to Will: Max checks the base and patch hash, then authorizes Will to apply the approved reproducer patch in the task worktree. Will reruns the failure before implementation and remains the sole writer on the task branch.
  8. Domain stewards review: required overlaps are enforced.
  9. Brooke challenges and Paul validates: independent from implementation.
  10. Sue records the lesson: evidence becomes searchable operational knowledge.
  11. Max integrates: confirms gates, ownership, branch state, and release constraints.
  12. Claude reports: outcome, evidence, residual risk, and next decision to the user.

Concurrency and authority model

  • Max is the sole dispatcher. Workers can request another specialist, but only Max creates or assigns it.
  • Parallelize reads and independent tests freely; parallelize writes only when scopes and worktrees are disjoint.
  • One writer owns a task branch. Reviewers report findings; they do not silently edit the writer’s branch.
  • Cross-domain changes receive one lead. Review ownership does not create co-equal writers.
  • Security and release stops are blocking. Aisha and Vera can return work to Max; they do not redefine user intent.
  • Persistent agents do not merge their own advice. Max owns integration; Claude owns user-facing escalation.

Material reconnaissance findings that affect agent governance

  • Release identity is not fully closed: the snapshot declares 3.8.50 and its changelog entry is still TBD, while the public releases page currently identifies 3.8.49 as latest. The ZIP contains no Git metadata, so its exact commit cannot be proven from the archive alone.
  • Documentation has version drift: several architecture documents still identify 3.8.40 while other materials are newer. Agents must cite the implementation source they relied on.
  • Quality evidence is segmented: Node’s test runner and Vitest are both used. A generic “tests passed” claim is incomplete without commands and coverage of the affected subsystem.
  • Security must be a standing review domain: prior public security work included command-injection and authorization/guardrail concerns. Privileged paths cannot be treated as ordinary utility code.
  • Repository rules are unusually explicit: worktree ownership, failing-first regression evidence, no stash/pop, release freeze rules, and the protected _tasks boundary should be injected verbatim into every worker packet.
  • Provider counts are volatile: current branch-facing documentation has already drifted from the supplied snapshot. Agents should derive current provider capability from canonical registry data, not prose counts.

Activation sequence

  1. Approve names, charters, and Max’s sole-dispatch authority.
  2. Reconcile missing .agents/.claude material and decide the canonical control-plane location.
  3. Build the ownership and mandatory-review matrix from imports plus runtime flows.
  4. Implement the task-packet schema and refuse incomplete dispatches.
  5. Pilot three contrasting changes: one provider/protocol task, one database/state task, and one security/packaging task.
  6. Measure review escapes, rework, time-to-context, duplicate investigation, gate coverage, and knowledge reuse.
  7. Promote the model only after the pilot proves that Max is coordinating rather than rediscovering every domain.

Final recommendation

Adopt a three-tier, federated-control model: Claude Code for intent and user authority; Max as the single dispatcher and integrator within a council of nine persistent, human-named domain stewards; and human-named, ephemeral, non-recursive task cells for reconnaissance, reproduction, implementation, adversarial review, proof, and knowledge capture.

This structure respects the original strategy while removing its main scaling defect. It matches OmniRoute’s actual seams, protects its worktree and evidence rules, and turns the project’s strong documentation and fix history into an operational memory system. The architecture should be piloted before it is automated broadly; the first implementation target is the task packet and ownership map, not a large fleet of autonomous writers.
