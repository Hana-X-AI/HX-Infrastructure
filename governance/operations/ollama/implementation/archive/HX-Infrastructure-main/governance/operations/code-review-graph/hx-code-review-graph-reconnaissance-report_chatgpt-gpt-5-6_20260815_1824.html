The most important finding

The technology fits; the default authority surface does not. The project describes itself as local code intelligence, but its default MCP server exposes apply_refactor_tool, which writes exact replacements into source files, plus graph-building, embedding, wiki-generation, and multi-repository tools. When no --tools or CRG_TOOLS allow-list is supplied—or when the value is empty—the code deliberately keeps all tools. This is fail-open relative to HX’s read-only Code Intelligence Plane requirement.

The project does provide an explicit allow-list that removes unlisted MCP tools. That creates a credible no-fork path, but HX must wrap it in a startup control that requires a nonempty exact allow-list and verifies the advertised tool set before any client connects. An optional filter is not, by itself, a permanent control.

What the project really is

tracked source→Tree-sitter + resolvers→SQLite structural graph→flows / communities / impact→MCP or CLI context→AI reviewer

Architecturally, code-review-graph is a local static-analysis and retrieval engine, not an autonomous reviewer. It parses repository files into functions, classes, imports, calls, inheritance, tests, endpoints, events, configuration use, and framework-specific relationships. It stores the result in a local SQLite database, incrementally refreshes changed files, computes blast radius and execution flows, and exposes compact context to AI coding clients through MCP and CLI.

Optional sentence-transformer or cloud-compatible embeddings add semantic search. NetworkX provides graph analysis; optional igraph/Leiden improves community detection. A local watch process or multi-repository daemon can keep graphs fresh. A GitHub Action can publish risk-scored PR comments. It also contains write-capable refactoring and wiki features that are outside HX’s narrow intelligence role.

Evidence of maturity

  • Current and active: created 2026-02-26, current main pushed 2026-08-02, roughly 30,203 stars, 2,766 forks, and 100 open issues at review time.
  • Strong test investment: 74 top-level Python test modules and 2,313 statically counted test functions in the supplied snapshot. CI runs Ruff, mypy, Bandit, a Python-version matrix, and pytest with a 65% coverage floor.
  • Responsible security posture: private vulnerability reporting, dependency upper bounds, hashed lockfile, documented Bandit exceptions, loopback DNS-rebinding defense, parameterized SQL, repository-root validation, and explicit cloud-egress warnings.
  • Benchmark candor: the README explicitly calls its “recall 1.0” graph-derived upper bound circular, admits the independent co-change mode currently returns no predictions, reports MRR 0.35 and flow recall 33%, and distinguishes whole-corpus savings from a realistic grep baseline.
  • Maintainer concentration: the lead contributor has 589 recorded contributions; the next has 23. Community participation exists, but practical bus factor remains concentrated.
  • Beta and fast moving: the package classifier is Beta. Main is 198 commits and 140 changed files beyond the latest release tag while still declaring version 2.3.7.

Material risks and contradictions

  1. Release identity drift. main and PyPI/release both call themselves 2.3.7, but main is 198 commits ahead of the v2.3.7 tag. “Install 2.3.7” does not identify the reviewed implementation. Any HX pilot must pin the exact commit/archive hash.
  2. Read-only is not the default. No allow-list means every tool remains; an empty allow-list also remains a no-op by explicit test. That is good usability and wrong HX control behavior.
  3. Auto-install is too expansive. It writes MCP config, hooks, skills, AGENTS.md/CLAUDE.md instructions, and in some clients user-level files. HX must integrate manually and narrowly.
  4. The injected instruction overstates graph authority. “ALWAYS use graph before Grep/Glob/Read” conflicts with the project’s own admitted search and flow limitations. HX should use the graph to target source inspection—not substitute for source verification.
  5. Static analysis is inherently incomplete. Dynamic dispatch, reflection, registries, generated code, framework wiring, and language-specific resolution gaps create false negatives and false dead-code findings.
  6. Benchmark value is real but bounded. Token savings against whole-corpus reads are upper-bound marketing context. The realistic comparison must be CRG-assisted review versus disciplined grep/LSP/manual source review on the same known-answer tasks.
  7. HTTP exposure is not an HX path. The origin guard is enabled only for loopback. Binding to a LAN address disables it, and no inspected authentication layer replaces it. Use stdio in the pilot.
  8. Derived memory/wiki conflict. The repository includes a Q&A memory module and wiki generation. HX already assigns durable memory to Mem0 and human/document knowledge to LightRAG/governed docs. Do not enable these features.

Proposed bounded pilot

Pilot purpose: determine whether code-review-graph can provide materially better structural review context than disciplined native search while remaining deterministically read-only. This is a pilot proposal, not authorization to install.

Source and operating envelope

  • Pin exactly to commit 1a010deed6c283d4aa1e7e949e78fe3a7bcdfbb3 / supplied archive SHA-256 10f3f093…453d; do not use unpinned uvx code-review-graph.
  • Use code-heavy, already understood corpora: jcode and OmniRoute. Do not use HX-Infrastructure as the primary score corpus.
  • Use stdio only; no HTTP, daemon, GitHub Action, global registry, cloud embeddings, memory loop, wiki, source refactoring, or auto-install.
  • Build/update the derived index through an operator-controlled command, not an agent-exposed MCP tool.
  • Expose only an exact read-only query allow-list and verify the server’s advertised tools before client use.

list_graph_stats_tool, get_minimal_context_tool, query_graph_tool, get_impact_radius_tool, get_review_context_tool, detect_changes_tool, list_flows_tool, get_flow_tool, get_affected_flows_tool, list_communities_tool, get_community_tool, get_architecture_overview_tool, get_hub_nodes_tool, get_bridge_nodes_tool, get_knowledge_gaps_tool, get_surprising_connections_tool, and traverse_graph_tool.

Semantic search should enter only after the deterministic structural baseline. refactor_tool should remain excluded initially even though preview modes are read-only, because its dead-code and move recommendations encourage decisions beyond the plane’s evidence quality.

Hard stop conditions

  • Any source-writing, configuration-writing, hook-installing, or user-home mutation becomes reachable through the HX MCP profile.
  • Missing or empty allow-list starts the broad default server instead of refusing to start.
  • The graph silently reports ready after an incomplete update or provides stale results without a freshness marker.
  • Known critical call/import/test relationships are missed at a rate that makes source targeting unsafe.
  • CRG instructions cause agents to skip source verification or treat dead-code/refactor suggestions as facts.
  • Operational maintenance exceeds the value relative to native grep/LSP/manual review.

Adoption decision if the pilot passes

Recommended narrow role: code-review-graph = read-only structural code intelligence and change-impact context for Claude Code and jcode.
  • Adopt: parser/resolver graph, SQLite derived index, incremental updates, selected read-only query tools, provenance, and compact review context.
  • Do not adopt: auto-installer, injected graph-first authority language, source refactoring/apply, wiki/memory loop, cloud embeddings, HTTP exposure, global daemon/registry, and CI merge gates until separately justified.
  • Stack consequence: promote CRG into the proposed Code Intelligence Plane and demote Code-Graph-RAG to reference/comparator unless it later demonstrates a distinct non-overlapping advantage.

Final synchronization position

What was learned: the underlying technology is mature enough and aligned enough to justify a pilot; it is not safe to adopt with its default install or tool surface.
What HX would use: local structural indexing and read-only code queries for code-heavy repositories.
What remains excluded: writes, refactoring execution, generated memory/wiki authority, auto-installed controls, cloud egress, and network service exposure.
Next owner decision: approve or decline the bounded read-only pilot. No implementation, installation, or repository mutation has been performed by this reconnaissance.
