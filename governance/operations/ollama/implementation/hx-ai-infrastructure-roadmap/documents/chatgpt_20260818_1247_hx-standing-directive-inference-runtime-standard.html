HX-SD-001 — Inference Runtime Standard

Status: ACCEPTED — STANDING DIRECTIVE
Authority: Chief AI Officer, Hana-X
Decision date: 18 August 2026
Scope: HX-Ai-Infrastructure; HXS-1 through HXS-4 and later HX-managed local model servers
Proposed canonical repository path: governance/directives/hx-sd-001-inference-runtime-standard.md

Executive directive

Ollama is the default and approved inference runtime for HX-managed local model servers.

vLLM is not a parallel fleet standard and shall not be installed, configured, or introduced into an HX model-server build by default. It is retained as an evaluated alternative that may be piloted only when a specific workload fails an explicit Ollama acceptance requirement and the proposed vLLM path is approved through the HX governance process.

This directive eliminates runtime ambiguity. HX will operate one standard inference-runtime control path until retained evidence demonstrates that an exception creates sufficient value to justify a second operational path.

1. Decision

1.1 Standard runtime

Ollama shall be the standard runtime for:

  • HXS-1 through HXS-4;
  • repeatable Ubuntu model-server builds;
  • local and loopback inference endpoints;
  • GGUF and Ollama-registry model artifacts;
  • agent-driven installation, configuration and verification;
  • bounded development, testing and demonstration workloads;
  • model-server deployments for which Ollama satisfies the recorded acceptance contract.

Each server may run a unique model, but it shall inherit the same governed Ollama deployment pattern unless an approved exception states otherwise.

1.2 vLLM status

vLLM is classified as:

REFERENCE-ONLY / CONDITIONAL PILOT — NOT A DEFAULT DEPLOYMENT COMPONENT

Its presence in research, architecture comparisons, backlog records or the local agent library does not authorize installation or adoption.

1.3 Fine-tuning boundary

Neither Ollama nor vLLM is the HX fine-tuning control plane.

Fine-tuning shall use a separately approved training toolchain. The resulting model or adapter must pass provenance, compatibility, evaluation and acceptance gates before being packaged for the approved serving runtime.

2. Decision rationale

Ollama is the correct HX default because the current fleet pattern prioritizes repeatability, controlled local operation and agent-manageable deployment over maximum multi-tenant throughput.

The standard provides:

  • a smaller installation and dependency surface;
  • straightforward Ubuntu and systemd operation;
  • mature GGUF and quantized-model support;
  • automatic multi-GPU model distribution;
  • explicit model-store configuration;
  • Flash Attention and KV-cache controls;
  • native and compatibility APIs;
  • bounded concurrency and request queuing;
  • adapter and externally produced model import;
  • a coherent responsibility boundary for Owen, Craig, Quincy and Tessa.

Introducing vLLM fleet-wide would add a second runtime, packaging path, dependency chain, model-compatibility matrix, quantization-kernel path, distributed-GPU strategy and validation suite before HX has demonstrated a requirement for those costs.

3. Conditions that may justify a vLLM pilot

A vLLM pilot may be proposed only when retained evidence demonstrates at least one of the following:

  1. Ollama fails a defined concurrency or aggregate-throughput objective.
  2. Repeated large shared prompts make automatic prefix caching materially valuable.
  3. HX requires several LoRA adapters to be served concurrently from one base model and selected per request.
  4. A required model artifact or quantization is materially better supported by vLLM.
  5. Ollama cannot satisfy a defined long-context capacity, correctness or latency requirement.
  6. Future GPU hardware materially improves the suitability of vLLM distributed execution.
  7. A production-serving requirement emerges that exceeds the accepted Ollama service envelope.

A preference, benchmark claim, model-card recommendation, community report or theoretical throughput advantage is not sufficient.

4. Required evidence for a vLLM exception

The exception proposal must include a controlled comparison using the same workload and acceptance criteria.

Evidence category Minimum record
Workload named client, request shape, context distribution, concurrency and service objective
Artifact publisher, repository or registry, exact tag, full digest, quantization and byte size
Runtime exact Ollama and vLLM versions, source/container identity and configuration
Hardware GPU UUIDs, VRAM, PCIe link state, topology, peer-access and collective-performance evidence
Performance time to first token, prefill, decode, throughput, queue behavior and cache state
Capacity maximum accepted context, KV-cache allocation, concurrent sequences and VRAM margin
Correctness identical HX evaluation set, retained outputs and scored acceptance results
Reliability startup, restart, failure, overflow and sustained-run behavior
Operations installation, upgrade, rollback, observability and recovery burden
Validation independent Tessa verdict of PASS, FAIL or BLOCKED

The comparison must distinguish artifact fit from operational fit. Aggregate model bytes alone do not prove that a runtime can load, split, cache and serve the model correctly on the target GPUs.

5. Ollama control requirements

Ollama's status as the default does not waive correctness controls.

Every HX Ollama deployment shall:

  • pin the runtime version;
  • pin the selected model manifest or artifact by full digest;
  • configure an explicit model-store path;
  • configure an explicit context window;
  • record sampler and thinking settings when supported;
  • verify GPU placement and memory use;
  • expose only the approved network interface;
  • retain installation and acceptance evidence;
  • implement an HX context-budget control before agentic production use.

5.1 Silent-truncation control

Ollama v0.32.14 silently removes older chat messages when a rendered prompt exceeds the configured context and truncation remains at its default. This behavior is acceptable for the bounded HXS-1 MVP-1 smoke request but is not acceptable as an unmanaged behavior for persistent agent sessions.

Before an Ollama endpoint is approved for long-running agent memory, the HX traffic or client plane must:

  1. budget input, retained-history and output tokens;
  2. reserve output capacity before sending the request;
  3. reject, compact or summarize before context overflow;
  4. record each compaction or summarization event;
  5. use native fail-closed controls where supported and required;
  6. prove through testing that governing instructions are not silently lost.

This requirement is a runtime guard, not a reason to introduce vLLM fleet-wide.

7. Governance and exception flow

sequenceDiagram participant O as Owner / CAIO participant M as Meta-Agent participant I as Owen · Craig · Quincy participant T as Tessa O->>M: Define accepted workload and failure condition M->>I: Run Ollama baseline and retain evidence I-->>M: Acceptance or measured failure M->>I: Authorize bounded vLLM pilot only if triggered I-->>T: Submit identical comparison evidence T-->>O: Independent PASS / FAIL / BLOCKED O->>M: Approve exception or retain Ollama

An approved vLLM exception must be scoped to a named workload, model, server class and acceptance contract. It does not change the fleet default and cannot be generalized to other HX servers without a separate decision.

8. Consequences

Positive

  • one repeatable runtime pattern across the initial fleet;
  • lower operational and agent cognitive load;
  • clearer installation, audit and recovery ownership;
  • fewer untested combinations of models, kernels and distributed execution;
  • evidence-driven exceptions rather than speculative architecture expansion.

Accepted limitations

  • Ollama may provide less aggregate throughput than vLLM under high concurrency;
  • shared-prefix caching and multi-LoRA serving may be less capable;
  • long-context agent use requires an HX context-budget guard;
  • some future model artifacts may require conversion or an exception runtime.

These limitations are accepted until they cause a defined workload to fail.

9. Supersession and review

This directive supersedes any prior implication that Ollama and vLLM are co-equal default candidates for HX model-server deployment. It does not invalidate vLLM research; that material remains reference evidence for a future governed pilot.

This directive remains in force until one of the following occurs:

  • the CAIO explicitly supersedes it;
  • an HX workload fails the Ollama acceptance envelope and an exception is approved;
  • fleet hardware or service objectives materially change;
  • retained production evidence demonstrates that a different fleet standard produces greater total value.

Scheduled review alone does not authorize a runtime change.

10. Standing directive statement

Hana-X will standardize its local model-server fleet on Ollama. vLLM will not be deployed by default and may be introduced only as a workload-specific, evidence-gated exception approved by the CAIO after independent validation. Fine-tuning remains a separate control plane.

Decision state: Accepted and effective immediately for HX-Ai-Infrastructure planning and implementation.
