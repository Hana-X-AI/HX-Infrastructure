1. Why the full audit is warranted

hxs-4 is operational, but “operational” is not equivalent to “correctly normalized for durable HX use.” The commissioning succeeded only after discovering non-obvious GPU/backend behavior, a test harness incident that wedged the NVIDIA context, performance differences across context sizes, and a silent context-overflow failure that prevented Claude Code qualification.

The repository reconnaissance also found that hxs-4's live runtime does not yet have a fully reconciled as-built authority and that the runtime gate family contains stale assumptions from an earlier workload era. The first Craig mission should therefore be audit + truth reconstruction, not a health check.

3. The most important new finding — truncation is structural

Do not treat “upgrade Ollama” as the fix for Claude Code overflow.

The source explains the unsafe behavior observed on hxs-4. Native Ollama chat requests contain a Truncate field. The chat handler treats an unset field as truncation enabled. In the attached v0.32.11 Anthropic Messages adapter, the converted api.ChatRequest sets model, messages, options, stream, tools and thinking—but does not set Truncate. The request therefore reaches chat handling with the field unset and inherits truncation-enabled behavior.

        ↓

Truncate = nil
        ↓

truncate := req.Truncate == nil || *req.Truncate

over-limit history may be truncated

Current v0.32.13 still defaults an unset chat Truncate field to truncation enabled. Its release notes do not claim a correction to this path. Therefore Craig must keep the Claude Code refusal open until an over-limit /v1/messages request fails closed or an approved fronting layer enforces the real limit deterministically.

7. Context is the hardest configuration decision

Prior measurements establish a real tradeoff:

ContextObserved placement/performanceInterpretation
16K100% GPU, materially fasterExcellent local utility profile, but cannot accommodate agent-sized prompts.
32KPartial CPU offloadMore headroom, slower.
64KHeavier CPU offload; prior loaded run observed substantial slowdownLargest proven configured window, but still too small for some Claude Code sessions and unsafe past limit because of truncation.

Source adds another nuance: a fixed OLLAMA_CONTEXT_LENGTH disables the newer automatic context-selection path. Craig must therefore distinguish:

  • a fixed safety ceiling;
  • automatic sizing;
  • per-request num_ctx;
  • client-side context enforcement.
Current bias for hxs-4: do not lower the global context simply for speed until request-size enforcement exists. If short utility work benefits from 16K, prefer an explicit workload/client profile or per-request context over silently reducing the only safety margin.

8. Upgrade posture

The attached source is v0.32.11; the prior host evidence is 0.32.9; current official upstream at review is 0.32.13. Craig should absolutely evaluate an upgrade, but must not upgrade as a side effect of auditing configuration.

A version upgrade is its own mutation class requiring:

  • release/source diff;
  • binary/service/drop-in snapshot;
  • model-store preservation;
  • rollback to exact 0.32.9 baseline;
  • GPU isolation retest;
  • residency/context/performance retest;
  • native/OpenAI/Anthropic protocol retest;
  • deliberate over-limit truncation test.

10. Correction authority for the audit

Craig may correct Ollama-specific configuration drift during the audit workstream when the change is reversible, supported by live evidence + version-matched source, and has an explicit rollback.

Examples potentially in scope:

  • systemd Ollama drop-in environment cleanup;
  • debug/cloud/Vulkan/device visibility settings;
  • Ollama concurrency/load/context settings when audit evidence supports the change;
  • service restart;
  • explicit model unload/reload;
  • repeatable Ollama verification.

Still out of scope without separate authority:

  • GPU driver/toolkit changes;
  • host reboot;
  • use of the reserved 16 GB GPU;
  • network exposure beyond loopback;
  • OmniRoute modification;
  • model replacement;
  • filesystem/storage redesign;
  • server-role or registry decisions;
  • unreviewed Ollama version upgrade.
