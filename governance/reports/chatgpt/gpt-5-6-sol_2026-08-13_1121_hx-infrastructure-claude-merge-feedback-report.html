Recommended direction: hybrid, with a stricter history boundary

Use the current 2026 repository as the active chassis and authority model. Use the legacy project as a high-value engineering source and specialist-agent knowledge base. 5. Critical findings the merge plan must correct

5.1 Raw unrelated-history merge is the largest technical risk in Claude Code's plan.
The legacy material contains plaintext historical credentials and an encrypted vault whose surrounding documentation exposes the old credential model. A raw merge makes those historical objects part of the destination repository forever unless history is rewritten. "Private repository" is not an adequate mitigation.
5.2 Claude AI silently changes current governance.
Its report says the project is "post-pivot — no phase gate," yet the supplied current repo still defines Phase 1 as discovery-only, keeps role assignment manual, and blocks Phase 2 until the fleet gate is satisfied. That is a project decision, not a merge cleanup item.
5.3 "Retarget the old IP hook" is not enough.
Claude Code proposes changing the legacy validator from 192.168.10.x to 192.168.50.x. Better: rewrite the control so it reads the current registry dynamically. Hardcoding the new map merely creates the next stale validator.
5.4 The old agent catalogue itself has drift.
The 32-agent inventory and the orchestration guide do not name exactly the same specialists. Examples include different historical owners for LightRAG and Docling MCP roles. This is evidence that capability should be canonical and human persona/name should be metadata, not the routing key.
5.5 The legacy agent operating pattern should survive.
The best legacy design idea is narrow expert ownership: an Ollama specialist stays on model-serving details, a Docling specialist stays on Docling, a PostgreSQL specialist stays on persistence, and cross-domain integration is synthesized by an orchestrator. That separation is exactly what reduces implementation drift.

8. Git/history strategy — revised recommendation

The project requirement is one repository, not one undifferentiated history. A single GitHub repository can safely preserve both eras without making historical infrastructure state part of the active tree.

Preferred model

  1. Confirm the intended organization repository through authenticated Git access.
  2. Create a safety branch for the current 2026 main.
  3. Fetch/clone the old remote read-only; do not trust the ZIP as the complete Git source.
  4. Run full-history secret scanning.
  5. Rewrite/sanitize old history if credentials/vault material ever entered Git objects.
  6. Preserve sanitized old history as a dedicated archival branch/tag namespace such as legacy/2025-sanitized.
  7. Port selected agents/process/service knowledge into current main as new, reviewable commits with provenance references.

Do not do

  • Do not immediately git merge --allow-unrelated-histories against an unscanned legacy remote.
  • Do not rely on "private repo" as the reason secret-bearing objects are acceptable.
  • Do not import the complete old tree under archive/ and call that consolidation.
  • Do not rewrite all old hostnames/IPs in historical documents and then present them as current documents; that destroys provenance and can create false history.
  • Do not close act-005 until the destination is authenticated and the off-machine copy is actually verified.
Alternative if the owner requires both histories to be reachable from main: first sanitize the legacy history and rewrite it into a dedicated subdirectory namespace (for example archive/2025-pre-relocation/) before the unrelated-history merge. This is still less clean than the preferred archival-branch model, but it is materially safer than merging the raw old root directly over the current root.

15. Merge acceptance criteria

  • Exactly one active HX-Infrastructure remote repository is used for current work.
  • Current main authority contracts remain internally consistent after the merge.
  • No historical credential, vault secret, token, password or private key is imported into active history.
  • Legacy history, if retained, is scanned and sanitized first.
  • SERVER-REGISTRY.md remains the sole current host/role lifecycle authority.
  • No old 192.168.10.x, hx.dev.local or /home/agent0 value appears as a current environmental fact.
  • Specialist agents are present for all currently relevant platform capabilities, with current contracts and no embedded environment assumptions.
  • No specialist agent can independently assign hosts, roles or workloads outside the governing lifecycle.
  • Legacy commands/hooks/gates have an explicit migration disposition rather than being copied or discarded by directory.
  • Docling and LangGraph lessons are available to current agents without requiring them to traverse hundreds of stale task documents.
  • Current tests and governance HTML build still pass after integration.
  • The resulting repository is understandable as one project, not two historical trees living side by side.
