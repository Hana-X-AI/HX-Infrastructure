3. Critical corrections to the latest Claude conclusions

3.1 “Rotation makes the old branch harmless” is too strong.
Rotation/revocation is the first mandatory response to an exposed credential, but it does not erase sensitive values from Git objects, cached views, pull-request references, forks, or clones. GitHub’s current guidance explicitly separates secret rotation from history removal. Therefore a raw secret-bearing tag or branch should not be considered a clean archival solution merely because the credential is dead.
3.2 “There is no history to merge because the ZIP has no .git” is incomplete.
That statement is true only of the supplied ZIP. The later live-repository review reports that the private organization repository has 22 historical commits. Therefore the correct distinction is: the ZIP cannot preserve lineage; the live remote can. There is genuine history worth preserving, but that does not justify a raw unrelated-history merge into current main.
3.3 A raw legacy tag has the same secret-reachability problem as a raw legacy branch.
A tag is operationally cleaner than mixing unrelated histories into main, but a tag still keeps the referenced commits reachable. If those commits contain sensitive data, tagging the raw tip intentionally preserves those objects. Preserve a sanitized tag/branch, not the tainted original, in the final canonical repository.
3.4 “Ollama → vLLM” is a target-architecture preference, not grounds to discard Ollama expertise.
The current roadmap is vLLM-oriented on the GPU fleet, but model format, quantization, hardware fit and GGUF evaluation remain relevant. The Ollama/GGUF specialist should survive as an alternate-serving SME. The merge should not turn a current preference into permanent knowledge deletion.
3.5 “Ansible ruled out” is not a safe repository-merge conclusion.
The validated current fleet baseline is native Bash fan-out from hxs-cp; that proves what works today. It does not make Ansible knowledge worthless. Keep Ansible as conditional expertise and leave adoption to a later control-plane decision.
3.6 “Identity tier dropped” should be reframed as “not part of the current active topology.”
Old AD/CA/SSO deployment state should not migrate. DNS, certificate, identity and SSO expertise may still matter later. Preserve the capability and lessons while retiring the 2025 environment assumptions.

4.3 Why sanitization is preferable to “rotate and keep raw history”

OptionBenefitCost / riskRecommendation
Rotate only, keep raw branch/tagFast, preserves exact SHAs.Sensitive data remains intentionally reachable; old values can be copied, indexed or rediscovered; future reviewers must remember why they are “safe.”reject final state
Delete old history entirelyCleanest security posture.Loses 2025 decision provenance, defect-resolution history and engineering archaeology.too destructive

The pre-sanitization remote/history should be treated as quarantine evidence, not as a second active project repository. If a raw preservation copy is required for forensic reasons, keep it outside the canonical Git namespace with tightly controlled access; it should not be the normal place developers or AI agents clone from.

4.4 GitHub-specific security implication

History rewriting alone does not guarantee that previously exposed content disappears from all GitHub views or from other clones/forks. Current GitHub documentation states that cached views, pull-request references and other copies may retain sensitive data, and that rotation/revocation is the first step. This means the project should define two separate outcomes:

  • Canonical repository clean: no final reachable branch/tag/ref intentionally preserves the known sensitive data.
  • Historical exposure remediated as far as practical: credentials rotated/revoked, rewritten history pushed, collaborator copies cleaned, and GitHub Support contacted if server-side cached/PR references require removal and qualify for support remediation.

8. sdd-core and “lean” are not mutually exclusive

One Claude review argues that because .specify/ is not currently present, sdd-core should not be adopted. That conclusion is too mechanical.

The standing Hana-X modernization direction is to use sdd-core concepts as the execution backbone: file-driven specifications, global governance, and local context routing. The merge should therefore distinguish execution philosophy from directory proliferation.

  • Do not create an empty 14-folder knowledge hierarchy just because a framework can support it.
  • Do preserve the sdd-core principles where they improve agent execution: explicit source-of-truth files, local instructions, spec-before-change, and inherited architectural constraints.
  • If/when the current repo formalizes .specify/memory/constitution.md or knowledge/instructions.md, those files must absorb the current repository’s authority model rather than reintroduce the legacy constitution hierarchy.
  • Lean means “few authoritative artifacts with high information density,” not “no execution framework.”

9.1 Why service.md instead of only build.md

A service file should remain useful before, during and after implementation. It should carry:

  • status (planned, implemented, validated, retired);
  • target host(s) from the registry;
  • owning SME;
  • architecture/dependencies;
  • configuration conventions;
  • installation/build sequence where applicable;
  • validation criteria;
  • gotchas/legacy lessons;
  • provenance.

Host-specific final state still belongs in servers/<host>/configuration.md. This prevents the service layer from becoming a second server inventory.

10. Proposed migration sequence

  1. Freeze evidence. Record current local HEAD, worktree state, remote state, current registry state and latest approved architecture state.
  2. Rotate/revoke known exposed credentials. Treat all legacy secret values as burned. Do not repeat them in migration artifacts.
  3. Acquire the live 2025 Git repository read-only. Confirm the reported 22-commit history, branches, tags, PR references and exact secret-bearing paths/commits.
  4. Sanitize the legacy lineage. Remove/replace known sensitive values/files across history; validate the rewritten history; preserve the result as legacy/2025-sanitized.
  5. Protect current work off-machine. Push the current 2026 lineage to a non-default import branch in the canonical remote while consolidation is being validated.
  6. Establish the future main. Make current 2026 lineage the active mainline after the remote/branch transition is verified.
  7. Build the file-by-file migration manifest. Every legacy asset gets disposition, destination, transform rules, owning SME, secret status and provenance.
  8. Rebuild the specialist roster. Recover original profiles from the live history if present; otherwise reconstruct from inventory/orchestration/contribution evidence. Strip environment state.
  9. Triage commands/hooks/gates. Migrate control objectives one by one into current skills/hooks/tests.
  10. Mine service knowledge. Start with Docling/Docling MCP and LangGraph, then shared-state services and other directly mapped services.
  11. Create current service files. Use lean service.md artifacts with status, host mapping, SME owner, validation and legacy provenance.
  12. Run authority-conflict and secret scans. Reject migrated content that presents old IPs/domains/paths/status as current.
  13. Run current regression/governance checks. Existing tests and HTML site/build validation remain blocking.
  14. Merge curated integration branch. Land only explainable, reviewed migration commits into current main.
  15. Delete temporary refs. Keep only active main, sanitized legacy lineage and deliberate release/provenance tags.
