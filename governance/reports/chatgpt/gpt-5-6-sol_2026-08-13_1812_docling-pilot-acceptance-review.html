Docling Pilot: Deep Acceptance Review

Review of the returned Docling pilot package at three layers: the service-design transformation, the provenance/validation evidence, and the migration mechanism that produced it. The pilot produced a valuable current design draft and, more importantly, exposed defects in the frozen manifest and sanitized-history assumptions before they could be repeated across LangGraph.

1. Executive verdict

The pilot succeeded by finding where the process still breaks.

The Docling distillation method works. Claude Code compressed a very large historical body into a 4,548-word target-state design without copying the old tree, preserved important failure lessons, distinguished target-state from as-built state, and produced clean file-level accounting.

The end-to-end migration process does not yet pass. Two mandatory preflight conditions failed and were waived: the pinned ledger identity was wrong, and the sanitized historical source did not exist. More seriously, the pilot discovered that the frozen v3 ledger still contains structural information that can recreate the shadow-repository behavior it was meant to eliminate.

Do not throw away the Docling work. Do not start LangGraph yet. Patch the ledger implementation, establish the sanitized historical lineage, update Docling against current upstream architecture, perform the minimum specialist reviews, then use the corrected process for LangGraph.

3. What Claude Code did very well

  • It refused to manufacture as-built state. The authority header is exactly the right pattern for current service planning.
  • It kept historical sign-off historical. No current SME name was invented, and reviewed_by stayed empty.
  • It found architectural drift inside the legacy project. The direct-Qdrant implementation reappeared after an earlier design correction; that is precisely the kind of expensive lesson worth preserving.
  • It separated Docling from model serving. The CPU-only hxs-12 placement is used as a constraint rather than an excuse to drag vLLM into the service.
  • It collapsed task/test/defect volume correctly. 74 task files became architecture/sequence evidence, 57 test files became test disciplines, and defects became a small current gotcha set.
  • It declared deviations instead of hiding them. The failed preflight, scanner substitution and accidental harness persistence were surfaced explicitly.

4. P0 — The sanitized-source preflight failed

The most important process gate did not pass. The pilot says legacy/2025-sanitized has never existed and that the 195 readable files were fetched from the live historical org main under an owner-approved waiver.

That makes this a valid transformation experiment, but not a validation of the final migration workflow. The sanitized-history model remains unproven.

Before LangGraph:

  1. Acquire the historical Git lineage into an isolated quarantine repository/worktree.
  2. Complete the secret review and rewrite/sanitize that lineage.
  3. Publish/establish the intended sanitized historical ref.
  4. Populate sanitized object/file identities in the ledger.
  5. Run the next service distillation from that sanitized source only.

The waiver should not become precedent. Docling was the one pilot in which accepting a controlled exception produced useful evidence; LangGraph should prove the real final path.

6. P0 — Current upstream Docling MCP invalidates one inherited architecture assumption

The current service document says the processing library runs embedded/in-process and calls that three-layer shape “unchanged” from 2025. That is no longer a safe current target assumption.

Current official Docling MCP has moved to a remote/local/hybrid conversion architecture. The current line is v3 and uses MCP Python SDK v2. The recommended/default conversion mode is remote: a lightweight Docling MCP process calls a Docling Serve API. Local mode remains available through a local extra, and hybrid mode can fall back from remote to local.

This creates a real current architecture choice for HX:

CandidateShape on hxs-12AdvantagesCosts
A. Local embeddeddocling-mcp[local] does parsing in-processFewest processes; conceptually simple.Heavy MCP runtime; parsing and MCP lifecycle remain coupled; does not mirror upstream recommended topology.
B. Docling Serve + thin MCP façadeDocling Serve provides parsing API; Docling MCP remote mode talks over loopback/local networkClean Phase-4 parsing / Phase-5 MCP separation; models/cache/native dependencies belong to one parsing service; current upstream default architecture; explicit API health surface.Two service units and one local API boundary.
C. HybridRemote to Docling Serve with embedded local fallbackResilience/fallback.Duplicates local conversion dependency footprint and increases state/operational complexity.

I recommend evaluating B first, not blindly selecting it. It aligns unusually well with the existing HX roadmap, which already separates base Docling parsing from later Docling MCP capability. For this dev/test/demo environment, the extra service boundary may be worth the cleaner lifecycle; if not, A is still a valid deliberate choice.

Until this decision is made, the service document should say conversion topology: VERIFICATION REQUIRED and scope cache/native/model requirements conditionally to the local parser or Docling Serve layer.

8. P1 — LightRAG is pipeline-required, not yet proven as a direct Docling integration

The design currently classifies LightRAG as CURRENT REQUIRED because parsed content must eventually reach graph/retrieval processing. That is directionally correct, but the current roadmap establishes an ingestion pipeline, not necessarily a direct Docling → LightRAG service call.

Use a more precise classification until the handoff architecture is decided:

LightRAG:
  classification: CURRENT PIPELINE REQUIRED
  direct_service_contract: NOT YET ESTABLISHED
  handoff_owner: VERIFICATION REQUIRED
  candidate patterns:
    - orchestrator calls Docling, then LightRAG
    - LightRAG pulls/accepts parsed output
    - queue/event handoff
    - explicit direct Docling push (only if deliberately selected)

This preserves the architectural requirement without reintroducing the 2025 “Docling owns the whole ingestion pipeline” mistake.

10. P1 — Correct the pilot’s coverage language

The pilot report headline says it “distilled 195 files.” The provenance file shows a more precise result:

  • 120 files had content used in the current design.
  • 75 were reviewed at inventory/shape level and contributed no distinct content.
  • 3 were blocked and never opened.

Use “195 content-eligible files reviewed; 120 contributed distilled content”. That is stronger evidence, not weaker—it proves the process can explicitly say “reviewed and not useful” instead of pretending every historical file deserves survival.

12. P1 — The secret-control substitution was acceptable for the pilot, not sufficient for migration closure

Claude Code did the right thing by not inventing an “approved scanner.” It used an upstream control—author from extracted meaning, never copy secret-bearing text—and then ran multiple shape/high-entropy checks. That is a reasonable compensating control for this document-only experiment.

But it does not prove the historical Git lineage is clean and it does not close credential rotation. Keep these separate:

  • Returned pilot artifacts: clean by the checks run.
  • Raw historical source: still sensitive/quarantined.
  • Sanitized historical ref: not yet created/validated.
  • Credential rotation action: still open.

The harness-created session copy of legacy charter text should be deleted from the session/result directory if accessible and then noted as cleaned. It is outside Git, but leaving stray raw copies is unnecessary.

15. Recommended Docling architecture decision packet

Do not open twenty owner questions at once. The next Docling design review can collapse to three decisions:

  1. Conversion topology: embedded local vs Docling Serve + remote MCP façade vs hybrid. I would evaluate Serve + thin MCP first because it follows current upstream and mirrors the HX Phase-4/Phase-5 split.
  2. Ingestion handoff: who owns Docling → downstream ingestion orchestration? Preserve LightRAG as a pipeline dependency without assuming a direct push contract.
  3. MCP exposure path: Docling MCP directly on hxs-12, composed/proxied by hxs-7, or both. Detailed security remains deferred; this decision is only topology/routing.

Everything else—ports, cache sizes, worker counts, OCR defaults, package pins—can be resolved later through implementation-time verification and measurement.

  • Historical defects distilled into current constraints.

19. Final recommendation

Keep the Docling draft. Hold LangGraph. Fix the substrate once.

This pilot did exactly what a good pilot should do: it demonstrated that the expensive historical engineering knowledge can be compressed into useful current design without importing the old repository, and it exposed process assumptions that looked correct on paper but were false in the live repositories.

The next move is a narrow corrective pass, not another planning cycle. Patch the ledger to v3.1, establish the sanitized source, currentize Docling’s conversion topology, bind provenance to exact source identities, reconstruct the minimum SMEs, and rerun acceptance. Then the same method is safe to scale to LangGraph.
