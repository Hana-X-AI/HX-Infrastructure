Executive Decision

Objective: converge the historical HX-Infrastructure project and the current HX-Infrastructure Git repository into one repository, one Git lineage, one authoritative infrastructure state, and one coordinated AI operating model.

Decision: the current Git repository remains the surviving repository and sole Git history. The legacy project is not merged as a second tree or second governance system. It is treated as a high-value engineering source from which specialist-agent capability, reusable technical knowledge, proven workflow patterns, tests, procedures, and lessons are selectively migrated.

The original assessment’s blanket recommendation to exclude the legacy Agent Zero / 32-agent system is revised. The historical evidence shows that the specialist-agent model was materially useful: technology SMEs reviewed design decisions in their own domain, caught cross-technology mistakes, and reduced implementation drift. Examples include Ollama, Docling, LangGraph, FastAPI, PostgreSQL, Redis, LightRAG, n8n, FastMCP, Crawl4AI, infrastructure, architecture, and QA specialists working as a review and synthesis team.

Therefore:

Preserve the specialist-agent operating pattern. Rebuild it under the current repository’s authority model. Do not preserve the old environment assumptions embedded inside those agents.

The same principle applies to the legacy .claude commands, hooks, and quality gates. They should no longer be categorized as a single “do not merge” block. They should be evaluated asset-by-asset and either retained, adapted, replaced by an existing current mechanism, or retired.

No physical merge or configuration change is authorized by this report. This remains a planning and repository-design assessment.

2. Single-Repository Principle

The merge must produce one active repository, not an archive repo nested inside a current repo.

The following rules define “one repo”:

  1. One .git directory: the current repository’s .git survives unchanged as the repository lineage.
  2. One infrastructure truth: current server discovery, current addressing, current hostname conventions, current registry, and current approved architecture govern.
  3. One governance chain: AGENTS.md, CLAUDE.md, GOALS-AND-OBJECTIVES.md, INFRASTRUCTURE-CONTRACT.md, SERVER-REGISTRY.md, and current governance records remain authoritative unless intentionally changed through the current process.
  4. One AI execution model: specialist agents may be numerous, but they must all inherit the same current contracts and routing rules.
  5. One service knowledge model: reusable service knowledge is stored by technology/service and linked to current server assignments; old host-specific state does not become present state.
  6. No nested legacy project tree: do not copy the full legacy repository into archive/old-HX-Infrastructure/ or similar. That would produce two projects inside one Git repository and preserve conflicting truth.

5. Revised Assessment of Agent Zero and the Specialist-Agent System

5.1 Why the specialist model should be retained

The historical project shows a repeatable multi-agent pattern:

  1. a service or node charter/specification was prepared;
  2. domain specialists reviewed only their area of expertise;
  3. each specialist produced findings, constraints, test expectations, and implementation concerns;
  4. Agent Zero synthesized the contributions, reconciled conflicts, and surfaced remaining owner decisions;
  5. the unified design then advanced to tasks and implementation.

For hx-lang-server, the charter review records 12 specialist reviews covering:

  • LangGraph;
  • FastAPI;
  • PostgreSQL;
  • Redis;
  • LightRAG;
  • Ollama;
  • n8n;
  • FastMCP;
  • Crawl4AI MCP;
  • platform architecture;
  • infrastructure/operations;
  • testing/quality.

The synthesis document records explicit conflict resolution across memory sizing, Redis pool sizing, key namespaces, and state schema versioning. This is exactly the kind of domain isolation that reduces implementation drift.

The Docling project similarly contains specialist contributions for Docling, FastMCP/MCP tools, LightRAG extraction, LiteLLM integration, infrastructure, architecture, security, and QA.

5.2 What should be preserved

Preserve these capabilities:

  • Agent Zero / orchestrator — task decomposition, specialist selection, parallel/sequential execution planning, synthesis, conflict detection, owner escalation, final coherence checks.
  • Platform architecture specialist — architecture tradeoffs, integration boundaries, ADR-quality reasoning, cross-service consistency.
  • Infrastructure/operations specialist — host/runtime/service-manager/storage/network execution constraints.
  • QA/testing specialist — testability, acceptance criteria, integration tests, negative tests, quality gates.
  • Technology SMEs — narrow expertise in technologies actually present in the approved HX stack.
  • Cross-specialist review — use multiple SMEs only where boundaries intersect.
  • Synthesis before implementation — disagreements are reconciled before an implementation agent is allowed to improvise.

5.3 What must not be preserved unchanged

The legacy agent definitions contain environment-specific assumptions that must be stripped:

  • 192.168.10.x addressing;
  • hx.dev.local hostnames;
  • /home/agent0/HX-Infrastructure absolute paths;
  • Samba AD assumptions as universal infrastructure policy;
  • old service-account and credential instructions;
  • references to historical server names as currently authoritative;
  • old model names or context-size assumptions unless revalidated;
  • old tool availability assumptions;
  • old lifecycle vocabulary that conflicts with the current repo.

Several historical documents also disagree about agent names and assignments. For example, one inventory presents “Jim Patterson” generically, while actual LangGraph artifacts identify Jim Harper as the Ollama SME; another orchestration guide refers to different Ollama/PostgreSQL/Redis specialist names. This means the capabilities and proven contributions are more authoritative than the old personality/name registry.

5.4 Recommended agent migration strategy

Do not attempt a blind one-for-one copy of 32 historical personas.

Instead:

  • preserve the full 32-agent inventory as a migration candidate catalogue;
  • reconstruct agent profiles from actual contribution evidence and current stack relevance;
  • activate a smaller high-value first wave;
  • retain inactive specialist definitions only when they still map to likely HX technologies;
  • add new specialists where the modern stack has changed, especially vLLM;
  • require all migrated agents to inherit current repository governance.

10.1 Why this structure works

Infrastructure state remains host-centric

servers/ answers: what is this physical server, what was discovered, and what is configured on it?

Service design remains service-centric

services/ answers: how is this workload designed/configured, independent of which current host runs it?

This avoids recreating legacy node names as the architecture. A Docling service can move from one host to another without moving its entire design history.

Specialist knowledge remains technology-centric

knowledge/technologies/ answers: what have we learned about this technology that any future implementation agent should know?

This is where sanitized legacy expertise should accumulate.

Agents are capability-centric

.claude/agents/ answers: which bounded expert should reason about this domain?

Specialist agents reference knowledge/technologies/<technology>/ and current contracts rather than carrying large, stale infrastructure assumptions inside their prompt.

Human-facing governance remains presentation-centric

governance/ continues to carry polished review artifacts, with HTML as the default for new human-facing reports. Markdown remains appropriate for agent/source contracts and machine-editable knowledge.

11. Proposed Agent File Contract

Each reconstructed specialist should be deliberately small and stable. A specialist profile should contain:

  1. Role and scope — what the agent is expert in.
  2. Out-of-scope boundaries — what it must defer to another specialist or owner.
  3. Required current context — authoritative repo files that must be read first.
  4. Technology knowledge routes — relevant knowledge/technologies/... paths.
  5. Evidence requirements — local discovery / official docs / tests needed before conclusions.
  6. Change authority — planning only, review only, or implementation within an approved role.
  7. Handoff contract — concise findings, assumptions, risks, unresolved decisions, and validation commands.

Agent profiles should not embed:

  • IP tables;
  • passwords;
  • permanent host assignments;
  • stale package versions;
  • model deployments;
  • hardcoded user home paths.

Those belong in current state/configuration sources.

12. Proposed Agent Zero Operating Contract

Agent Zero should return as a repo-governed orchestrator, not as an alternate project authority.

Recommended responsibilities:

  • read the root and local AGENTS.md chain;
  • identify the affected technology domains;
  • choose the minimum specialist set needed;
  • run specialists in parallel where their work is independent;
  • prevent specialists from changing adjacent domains without handoff;
  • synthesize disagreements and make conflicts explicit;
  • distinguish owner decisions from technical recommendations;
  • validate that final proposals match current infrastructure state;
  • ensure test/verification requirements are defined before implementation;
  • stop at current phase gates.

Agent Zero must not:

  • invent server roles;
  • overwrite registry authority;
  • revive legacy topology;
  • create a second lifecycle/governance system;
  • treat historical service status as current status;

STAYS AS AUTHORITY

  • broken hooks unchanged;

16. Guidance for Any AI Continuing This Work

  1. Do not merge by directory similarity. Merge by semantic role and authority.
  2. Do not confuse many agents with many authorities. There can be 32+ specialists and still only one repository governance chain.
  3. Use specialist isolation to prevent drift. Ollama questions go to the Ollama specialist; Docling questions go to Docling; infrastructure questions go to infrastructure; cross-domain changes go through synthesis.
  4. Current state always beats historical state. Legacy documents are evidence and knowledge, not live inventory.
  5. Recover expertise from contributions, not only old agent inventory labels. The historical naming registry is inconsistent in places.
  6. Prefer adaptation over duplication. If a current skill/hook already solves a problem, enhance it rather than recreating the old mechanism beside it.
  7. Preserve failure knowledge aggressively. Sanitized defects and lessons are among the highest-value assets in the legacy corpus.
  8. Stop at planning gates. Do not begin service deployment merely because historical tasks describe how.

17. Final Recommendation

Proceed with a curated convergence into the current Git repository.

The merged HX-Infrastructure repository should combine:

  • the current project’s authoritative fleet state and governance;
  • the legacy project’s proven specialist-agent model;
  • the legacy project’s strongest service engineering knowledge and lessons;
  • the current sdd-core-style execution backbone and repository contracts.

The correct architectural principle is:

One repository, one truth, many specialists.

Agent Zero and the specialist agents should be preserved because they provided real implementation value, but they should be reconstructed as bounded capabilities that consume current repository state. Legacy commands and hooks should be mined rather than discarded: keep what prevents drift, catches defects, improves handoffs, or makes execution repeatable; retire what merely enforces a dead topology or duplicates current governance.

The proposed repository structure in this report provides the target boundary for that convergence.
