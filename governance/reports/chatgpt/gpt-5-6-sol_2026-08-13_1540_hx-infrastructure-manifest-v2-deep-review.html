Deep Review of Migration Manifest v2

The dual-layer JSONL + generated HTML design is correct and should be retained. This review goes below coverage and formatting into the classifier semantics: what actually enters current main, how sensitive historical material is handled, whether legacy controls are being over-retained, whether current authority is encoded strongly enough, and whether an executor can complete the migration without inventing decisions.

1. Executive verdict

Keep the ledger. Change what “historical” means.

V2 solves the file-accountability problem and introduces a very good execution substrate. It should become the canonical migration ledger. The JSONL is valid, has exactly one row per legacy file, the IDs and paths are unique, and the HTML rollups are derived from the data rather than hand-maintained.

But the classifier has changed the merge model in a way I do not recommend: 430 historical files plus 3 retired files are assigned target paths under governance/migrations/legacy-2025/ in the current working tree. That means 433 of 522 legacy files would physically reappear inside current main. It is technically one Git repository, but operationally it is the old project nested inside the new one—the exact “shadow repository” outcome the previous reviews converged against.

Recommended v2.1 rule: historical means “preserved by the sanitized legacy Git ref and indexed from current main,” not “copied into current main.” Current main keeps the ledger, provenance index, distilled lessons, reconstructed agents, current service documents and selected adapted controls. The sanitized historical branch keeps the old file-level record.

3. P0 — Do not commit a raw 522-file import branch into the canonical repository

The v2 execution order begins by landing all 522 legacy files verbatim on import/legacy-2025, then removing/scrubbing sensitive material afterward. This is unsafe if that branch is committed in the canonical repository, because a later deletion or edit does not remove the earlier Git objects. The first import commit would itself become the secret-bearing history we have been trying to avoid.

The correct order is:

  1. Acquire the historical repository or archive in a quarantine working area outside the canonical repository.
  2. Rotate/revoke known exposed values.
  3. Run broad secret discovery across files and, for the historical Git repository, across all history.
  4. Rewrite/sanitize the historical lineage in quarantine.
  5. Validate that the sanitized lineage is clean.
  6. Only then introduce legacy/2025-sanitized to the canonical remote.
  7. Never create a raw import/legacy-2025 ref in the final canonical repository.

If a temporary raw branch is useful during analysis, it should live only in an isolated local/quarantine repository and be destroyed after the sanitized derivative is verified.

4. P0 — Do not copy the 430-file historical tree into current main

V2 defines historical files as “preserved read-only under governance/migrations/legacy-2025/.” The ledger confirms that every one of the 430 historical rows targets that active-tree prefix, and the 3 retired rows do as well.

What should be in current main

  • manifest.jsonl
  • generated migration HTML
  • provenance/index mapping old path → sanitized legacy ref/commit
  • small sanitized legacy lesson documents
  • current services/*/service.md
  • reconstructed specialist agents
  • selected adapted skills/hooks/tests

What should not be in current main

  • the 198-file Docling historical tree

  • old root trackers and status snapshots
  • old topology/inventory trees
  • terminal-capture junk
  • retired vault/provisioning material

The sanitized legacy branch is the archive. The current tree needs an index into it, not another copy of it. This gives us one repository without making main look like two projects placed beside each other.

5. P0 — Secret classification is incomplete

V2 correctly tracks 30 references to legacy-secret-001, but the earlier evidence identified more than one exposed credential class. V2’s narrative indicates the deterministic detector was narrowed to the reused known token because broader regex results were noisy. That is fine as one detector, but it cannot become the full secret inventory.

Required v2.1 change: separate exact-known-secret detection from generic secret discovery.

secret_refs: ["legacy-secret-001", "legacy-secret-002"]
secret_scan:
  exact_known_values: true
  high_entropy_tokens: true
  assignment_patterns: true
  env_secret_names: true
  private_key_markers: true
  bearer_tokens: true
  provider_key_patterns: true
  manual_review: required-on-hit

Do not place the literal values in the ledger. The scanning runtime receives those values securely and emits only IDs/findings.

6. P0/P1 — Secret-bearing historical rows cannot be “read-only archived” without a sanitation model

Of the 30 rows marked secret_risk=confirmed, the ledger currently classifies 22 as historical and 3 as retire. Those 25 rows target current-tree archive paths. This creates two mutually exclusive meanings of “read-only”:

  • If copied verbatim, they reintroduce sensitive values.
  • If scrubbed, they are no longer verbatim/read-only source artifacts and their checksum no longer proves identity with the original.

The fix is to keep three identities distinct:

The ledger should store both source and sanitized hashes where a file is rewritten.

8. P1 — Standards, templates and procedures are substantially over-retained

Standards

V2 marks all ten standards adapt. A lean repository should not preserve a standards library just because it exists.

  • Naming conventions: adapt/merge into the current documentation standard.
  • Testing requirements + document quality checklist: adapt the strongest missing rules.
  • Architecture/deployment/documentation/infrastructure-layer/utility standards: usually covered; cherry-pick gaps only.
  • Legacy vault/credential-management standard: retire. Do not translate the retired mechanism into a current standard.
  • Legacy standards README: retire.

Templates

All 18 are marked adapt. That contradicts the stated lean goal.

  • Collapse the useful service architecture/spec/plan/deployment patterns into one current service template.
  • Keep a lean test plan/test case pair if current tests benefit.
  • Retire charter, RAIDD, old research-vault, duplicated defect/execution/index and process-specific templates unless a real current workflow demands them.

Procedures

All 11 main procedures are marked adapt. They need individual semantics.

  • Context loading: adapt.
  • Testing research: adapt.
  • Network health check: adapt, but registry-driven.
  • Spec/task/task-execution/closeout: preserve lightly where they enforce good AI execution discipline.
  • Charter workflow: retire.
  • Core project team: use as agent-reconstruction evidence, not an active procedure.
  • Legacy node deployment workflow: mine reusable sequencing, do not recreate the old node/process model.

9. P1 — Environment-dependency metadata is not content-complete

The ledger marks 502 of 522 rows as environment_dependency=none; only 12 are marked for the old model-serving runtime, 6 for the old network and 2 for the retired orchestration mechanism. That cannot safely represent a legacy repository previously measured to contain widespread old addresses, hostnames, root paths and user assumptions.

Do not use a single categorical field. Add independent content-derived flags:

"legacy_facts": {
  "old_ip": true|false,
  "old_domain": true|false,
  "old_root_path": true|false,
  "old_username": true|false,
  "old_hostname": true|false,
  "old_service_assignment": true|false,
  "old_runtime_or_version": true|false,
  "retired_process_reference": true|false
}

These should be generated by scanning content, not inferred from directory names. An adapted file is not eligible for current status until every flagged old fact has been reconciled deliberately.

10. P1 — Provenance needs stronger identifiers

The current row schema has the path but not enough information to prove exactly which historical object was reviewed. Add:

"source_repo": "Hana-X-AI/HX-Infrastructure",
"source_ref": "legacy/2025-sanitized",
"source_commit": "<sha>",
"source_sha256": "<raw-or-quarantine-hash>",
"sanitized_sha256": "<if rewritten>",
"target_path": "services/docling-mcp/service.md",
"target_section": "legacy failure lessons",
"migration_commit": "<filled after execution>"

If the live Git history cannot map a ZIP file exactly, record the archive snapshot/hash instead of pretending a commit association exists.

11. P1 — Exact target paths are required for the 88 active rows

The 88 adapt/reconstruct rows currently use a placeholder such as (reconciled active tree). That is not enough for an execution ledger: the executor still has to decide where the result belongs.

Before a row can move from needs-review to approved, it should contain either:

  • an exact target_path; or
  • a target_artifact plus target_section for many-to-one distillation.

Example: 50 historical LangGraph persistence files may all point to services/langgraph/service.md / Persistence & Checkpointing. That makes the many-to-one transformation explicit and auditable.

Zero covered is suspicious. The current repository already has governance, session-state tooling, documentation standards, tests, templates and status mechanisms. A classifier that finds no legacy file genuinely covered by current capability is likely biased toward retention.

V2.1 should not aim for a target count; it should restore semantic file-by-file review. 17. Ledger lifecycle model

One status field is not enough. Separate the decision from the execution state:

"decision_status": "unreviewed | approved | rejected | needs-review",
"migration_status": "pending | in-progress | migrated | validated | failed",
"reviewed_by": ["owner", "platform-architect", "service-sme"],
"reviewed_at": "2026-08-13T...",
"migration_commit": null

Group rules may pre-classify a file, but they should start as decision_status=needs-review when the policy is known to be broad. The ledger becomes authoritative only after the semantic review approves each row.

20. Final recommendation

Do not throw away v2. Refine it.

The hardest mechanical problem is solved. We finally have an exact inventory and a machine-readable control surface. The remaining work is to stop the deterministic classifier from becoming a deterministic way to over-import legacy material.

The final model should be: 522-row ledger in current main; sanitized historical lineage in a separate historical ref; a small provenance index; current service knowledge distilled into service.md; capability-first agents reconstructed; current controls rebuilt from authoritative data; and no legacy shadow tree inside the active checkout.

Once those v2.1 policy corrections are made, I would consider the manifest ready to drive actual migration batches.
