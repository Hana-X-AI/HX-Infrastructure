Verdict: strong architecture, one revision away from execution-grade

3. Blocking revisions before execution

P0 — Remove secret literals from the manifest itself.
The manifest states that no compromised credential value may enter the merged tree, but its own header/secret appendix repeats the full historical service-account password. If this HTML is committed, the migration control document itself becomes a fresh credential-bearing artifact. Replace all literal values with stable IDs such as legacy-secret-001 and legacy-secret-002. Keep the actual detection patterns only in an ephemeral scanning input or external secret-scanning system, never in tracked planning documentation.
P0 — Make the manifest truly one-row-per-source-file.
The document is titled “File-by-File Migration Manifest,” but it contains only 69 tabular decision rows across all sections, several of which are current-repo edits rather than legacy files. The 26-command inventory is compressed into eight grouped rows; the 18 templates into three rows; the 17 procedures into four; and 411 Docling/lang-server files into ten source families. Grouping is excellent for the human summary, but it is insufficient as the execution ledger because a file can disappear without ever receiving an explicit disposition.
P1 — Eliminate mechanical fact translation.
Phrases such as 10.→50. and “Ollama → vLLM” read like search/replace instructions. That is unsafe. A legacy address must be resolved through the current registry/service crosswalk; it is not numerically translated. A legacy model-serving task must be decomposed into invariant requirements (endpoint abstraction, timeout behavior, model selection, health, concurrency, failure handling) and then re-designed for the current serving stack. The migration operation should be extract → reconcile → author, not replace → call current.
P1 — Tighten the Git remote cutover sequence.
“Authenticate the org remote and push current main” is ambiguous because the org remote reportedly already has a historical main. The safe first push is the current lineage to a uniquely named import branch. Only after fetching and verifying the remote refs, sanitizing the historical lineage, and recording both tips should the current lineage be promoted to the default main. The manifest should make a destructive or force push impossible to infer.
P1 — Re-baseline verification after gate retirement.
The manifest correctly says to apply the owner edits and then establish a new baseline, but its final acceptance criteria still require exactly 153/0. Retiring the phase guard/skill can legitimately change assertion count. Replace the hardcoded count with “all approved current tests pass, with any assertion-count delta reviewed and recorded,” then capture the new expected count after the owner-edit commit.

4. “File-by-file” gap — how to fix it without creating another 500-page document

Do not abandon the grouped HTML. It is the right human interface. Add a machine-executable ledger underneath it.

Human artifact

Keep the current HTML structure as the review/report layer: grouped decisions, rationale, priorities, acceptance criteria and summaries.

Recommended: generate this HTML from the ledger so summary counts can never drift from the underlying file list.

Canonical execution ledger

Create governance/migrations/legacy-2025/manifest.jsonl with exactly one JSON object for every legacy file.

JSONL is easy for agents to stream, diff, validate and update one file at a time. HTML remains the human-facing format.

Minimum row schema

{
  "id": "legacy-0001",
  "legacy_path": "...",
  "legacy_commit": "...",
  "asset_type": "hook|command|procedure|service|...",
  "disposition": "adopt|adapt|reconstruct|covered|historical|retire|exclude",
  "inherits_policy": "optional-group-rule-id",
  "target_path": "...",
  "owner_capability": "...",
  "authority_class": "current-supporting|historical-only|none",
  "secret_risk": "none|inspect|confirmed",
  "environment_dependency": "none|host-map|network|runtime-version|credential|...",
  "transform_method": "extract-reconcile-author|...",
  "validation": "...",
  "status": "unreviewed|approved|migrated|validated|rejected"
}

For 198 Docling and 213 lang-server files, most rows can inherit a group rule. That still leaves every file individually accountable without requiring 411 bespoke paragraphs.

Coverage validation should be automated. The union of manifest legacy_path entries must equal the full 522-file inventory exactly: no missing paths, no duplicates, no phantom paths. The renderer should refuse to build the “final” HTML if coverage is not 522/522.

6. Review of §0 — owner decisions

Direction is correct. I recommend three refinements.

  • Gate retirement: retire the phase-named guard and skill, but preserve useful integrity logic under neutral names. Registry completeness is useful even when it is not a phase gate. A clean target is a registry-integrity test/check, not a repurposed phase1-gate artifact.
  • Registry role commitment: if the old “Phase 2 status” column contains useful operational state, rename it to a lifecycle-neutral field such as Implementation State or Deployment State rather than deleting status tracking altogether. If equivalent lifecycle state already exists elsewhere, deletion is fine. The manifest should verify before removing the column.
  • Permanent orchestration exclusion: make the native hxs-cp Bash/SSH fan-out pattern the explicit current baseline in the authoritative control-plane document. Do not merely delete an old candidate line; replace ambiguity with the proven operating model.

7. Review of §1 — specialist agents

The capability-first reconstruction is one of the best parts of the manifest. It needs an agent contract so reconstructed specialists remain narrow instead of becoming generic assistants over time.

Required fields for every reconstructed agent

  • capability_id — stable routing identity.
  • historical_aliases — persona names only for provenance.
  • scope and explicit out_of_scope.
  • authoritative_inputs — current contracts/registry/service docs the agent must read.
  • historical_sources — legacy evidence it may mine, marked non-authoritative.
  • allowed_outputs — recommendations, service changes, tests, etc.
  • validation_partner — usually QA or another SME; specialists do not self-certify.
  • activation — active / retained-inactive.
Keep Ollama/GGUF knowledge clearly separate from current serving authority. “Historical only” may be too weak if GGUF/local-serving evaluation remains technically useful. I would classify it as retained-inactive capability knowledge rather than merely a historical document. It cannot prescribe current deployment, but it can be invoked for alternate-serving or quantization research.

Prefer service.md over build.md

I recommend one durable services/<service>/service.md rather than a file named only build.md. “Build” is a lifecycle moment; the document should remain useful after installation. It can contain:

  • status and target host(s);
  • owning SME;
  • purpose and architecture;
  • dependencies/interfaces;
  • installation/configuration sequence;
  • validation and rollback;
  • known gotchas;
  • legacy provenance;
  • current-version verification notes.

The actual host-specific resulting state still belongs in servers/<host>/configuration.md. That keeps service knowledge from becoming a second inventory.

9. Review of §3–§5 — commands, hooks, gates, standards, procedures

Commands: do not retire spec/task discipline just because the legacy workflow was heavy

The blanket row retiring cc-{charter,spec,task,task-execution,project-closeout}-workflow is too coarse. The charter/phase machinery can go, but specification, task decomposition, execution evidence and closeout checks are valuable AI-development controls when implemented lightly.

Status-report utility is not the same thing as a status database

governance/logs/actions-and-issues.md should remain the only routine tracking store, but a read-only status-report skill that synthesizes registry, actions/issues, service status and test results could still be useful. Consider reconstruct-readonly instead of simply covered.

Network health check should be registry-driven too

The same rule that improves the IP validator applies to network-health-check.sh: do not “retarget” a fixed host list to the new subnet. Generate/parse the fleet from current authoritative data so adding/reassigning a host does not require editing the diagnostic script.

11. Safer Git execution sequence

  1. Capture both tips. Record current local HEAD and all org-remote branches/tags before changing anything.
  2. Fetch first. Verify the remote identity, visibility and existing default branch. Do not assume the remote main is empty.
  3. Push current lineage to an import branch: e.g. import/current-2026-08-13. This protects current work off-machine without replacing the historical mainline.
  4. Quarantine and sanitize the historical lineage. Produce legacy/2025-sanitized; verify no known sensitive value is reachable from that ref.
  5. Promote current lineage to future main through an explicit branch/default-branch transition after both histories are safely represented.
  6. Create the sanitized legacy tag on the sanitized historical tip.
  7. Create integrate/legacy-knowledge from current main and perform all curated migration there.
  8. Merge only the curated integration commits into current main. Never merge the sanitized legacy branch into main solely to join ancestry.
  9. Delete temporary import/integration refs after validation.
