The exact-coverage result is the one worth dwelling on. Every previous artifact in this exchange asserted counts that turned out to be drifted, miscounted or drawn from the wrong source. This one was generated from the tree and agrees with the tree.

Findings

V1

distill and a 1:1 target_path contradict each other

structural

All 417 rows with transform_method: distill also carry a one-to-one target_path — 417 distinct destinations, one per source file, each preserving the original filename under governance/migrations/legacy-2025/….

Those two fields assert opposite things. Distil means the file is read and its substance folded into something else, leaving no per-file output — which is the whole argument for not importing the 90-file task trees. A 1:1 target path is a copy. A row cannot be both, and an executor following the ledger literally would copy all 417 files into the tree, reproducing the structure the manifest set out to avoid.

Suggested fix: separate archival from distillation. Archived-for-provenance rows keep their 1:1 path with transform: archive. Rows genuinely distilled point at the consolidated destination they feed — the service build document — and repeat it across the group. The field then answers "where does this end up" truthfully in both cases.

V2

29 of 30 known secret-bearing files still land in the tree

decide

Exactly one file is excluded: the live vault/credentials.yml. The other 29 confirmed-secret files all carry a target_path — 22 archived under governance/migrations/legacy-2025/, 2 adapted, 2 reconstructed, 3 retired but still pathed. Only one row uses transform: scrub-secret; 22 use distill.

This is defensible — every one of the 30 carries validation: rotate+scan-clean, so the gate exists and the intent is that rotation happens first, after which the literal is inert. But it should be a conscious choice rather than a side effect, because the earlier stated goal was that the compromised token reaches no go-forward history at all, and the ledger's own data says 29 files containing it are scheduled to be written.

Decide: either scrub on the way in — change those 22 from distill to scrub-secret, so the archive is clean regardless of rotation timing — or accept dead credentials in the archive and say so explicitly, so nobody later reads a scan hit as a live exposure. The first is safer and costs one field change per row.

V3

The v1 credential defect is fixed

confirmed

Neither the password nor the API key appears anywhere in the ledger or the generated HTML. The 30 affected files are referenced only by the opaque handle legacy-secret-001, which is the right pattern: it names the location and the blast radius without reproducing the value.

Worth recording as the general rule, since this project hit it three times in one day: state where a secret is and what it opens; never restate the value. That is what makes a finding actionable rather than an exposure (ll-033).

What the dual-layer design gets right

  • Generated, not asserted. The HTML is rendered from the ledger, so the page cannot drift from the data. Every prior artifact here carried hand-written counts, and every one of them drifted.
  • Disposition separated from transform. "What happens to this file" and "how" are genuinely different axes, and collapsing them is what made the v1 rows ambiguous.
  • Grouping demoted to a tag. inherits_policy keeps the policy rationale visible without letting a group swallow its members — which is how coverage stays provably 522.
  • Import-branch-first execution. import/legacy-2025 → quarantine and rotate → archive → reconcile and promote. Nothing force-merged, and the quarantine step sits before anything reaches a working branch.
  • Broad retention, lean activation. 430 archived read-only against 88 actively worked. That is the shape the owner asked for, and here it falls out of the data rather than being asserted.

Recommendation

Proceed on this ledger. Fix V1 before execution, since an executor following it literally would produce the wrong tree; V2 is a decision rather than a defect. Neither is a reason to rebuild — the coverage guarantee is the hard part and it already holds.

Unchanged and still outstanding: rotate both credentials (iss-012), and finish the history purge on this repository — the rewritten history is clean, but the old commits remain reachable until the backup tag and refs/original are dropped and the reflog expired.
