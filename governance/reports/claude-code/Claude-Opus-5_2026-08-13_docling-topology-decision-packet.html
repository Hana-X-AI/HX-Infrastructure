Docling Conversion Topology — DECIDED

Ruled 2026-08-13: remote mode, Docling Serve co-located on hxs-12. The options and their trade-offs are kept below as the record of what was weighed.

RULING — 2026-08-13

Remote mode, with Docling Serve co-located on hxs-12. Two units on one host: docling-serve parses and owns the native libraries, model weights and parser cache; docling-mcp presents the MCP surface with conversion_mode=remote and service_url pointed at loopback. fallback_to_local stays false, since no local converter is installed.

Correction to this packet’s own analysis. It said co-locating Serve on hxs-12 made option B "strictly worse than A". That was overstated. Co-location still delivers lifecycle separation — a parser upgrade restarts Serve, not the MCP surface — it is the upstream default path, it keeps hxs-12’s registry role accurate because the host still parses, and relocating Serve later becomes a service_url change rather than a redesign.

And one advantage the packet missed entirely: docling-serve ships a cpu extra resolved against a CPU-only torch index. docling-mcp[local] has no equivalent. So the CUDA-wheel hazard flagged against option A is not merely mitigated by this ruling — it is designed out, because the parsing dependency set is installed from a package that supports a CPU-only build as a first-class option.

Verified 2026-08-13: docling-serve v1.30.0 (released 2026-08-07), requires-python >=3.10, uvicorn defaults host 0.0.0.0 / port 5001 — the bind must be overridden to loopback.

First, a correction to how this was framed

The prior review described "three conversion modes". The package source says otherwise. ConversionMode has exactly two values — remote (the default) and local. What gets called hybrid is not a mode at all; it is a separate boolean, fallback_to_local, defaulting to false. So you are choosing between two modes and one flag, not three modes.

What changed since the recommendation to "evaluate B first"

B and C have no host, and co-locating Serve defeats the point

No row in SERVER-REGISTRY.md assigns a Docling Serve workload to any server, and the ratified fleet map contains no Serve instance. That leaves two routes, and both cost something the original recommendation did not price:

Co-locate Serve on hxs-12. The same native libraries and model weights land on the same 232.64 GB filesystem, plus a second systemd unit and an HTTP hop. B becomes strictly worse than A.

Place Serve elsewhere. Requires a new owner role assignment. Every GPU-less candidate in the fleet is a 4–6 core machine, so the CPU parsing cost is relocated, not removed. It would also make hxs-12's registry role — "Ingestion — parsing" — inaccurate, since hxs-12 would no longer parse.

What argues for each

A · Local

  • For: no new host, no new service, no network hop. Matches the registry role exactly. Fewest moving parts for a dev/test/demo environment.
  • Against: couples parsing and MCP lifecycles — a parser upgrade restarts the MCP surface. Pulls the torch/CUDA wheel chain onto a GPU-less host unless torch is deliberately resolved from the CPU-only index. Model weights and cache compete with the OS on a single non-redundant disk.

B · Remote

  • For: the package's own default. Separates the parsing lifecycle from the MCP lifecycle, which mirrors the roadmap's phase-4 parsing / phase-5 MCP split. Model weights, native libraries and cache live in one parsing service. No container and no GPU implied — Serve installs as a Python package with a CPU path.
  • Against: requires standing up a service that does not exist, on a host not yet assigned. Introduces a network dependency into every conversion. Two of the settings that would bound that dependency — service_timeout and service_max_retries — are declared in the package but not consumed by the remote client, so a remote conversion cannot currently be bounded through configuration.

C · Remote with fallback

  • For: survives a Serve outage.
  • Against: carries A's full dependency footprint, including the GPU wheel chain, purely as a fallback. Two code paths to test and two sets of behaviour to reason about. Resilience a dev/test environment likely does not need.

Recommendation

Evaluate B, but decide Serve placement first — it is the real question. B's architectural argument is sound and it is upstream's default, but B is not a configuration choice: it is a request for a new service on a host you have not assigned. If Serve ends up co-located on hxs-12, B delivers none of its benefit and A is the better answer.

So the decision decomposes:

  1. Is a separate Docling Serve host available or worth assigning? If no → choose A and accept the lifecycle coupling.
  2. If yes → choose B, assign the host in the registry, and restate hxs-12's role as MCP façade rather than parsing.
  3. Choose C only if a Serve outage must not stop parsing — which, for a dev/test/demo environment, is hard to justify against carrying the full local footprint anyway.

No option is selected in the design document. It carries conversion topology: VERIFICATION REQUIRED and scopes native libraries, model artefacts, cache and health conditionally, so it stays correct whichever way you rule.
