3Authority model (target-state, not as-built)

The document is authoritative for intended design only. A future reader — human or AI — must never infer "Docling is installed/configured/reachable" from the existence of a polished service document. Use this exact header:

# Docling MCP

Status: TARGET-STATE DESIGN
Target placement: <resolve from SERVER-REGISTRY.md>
As-built status: NOT ASSERTED BY THIS DOCUMENT

Authority boundary:
- Authoritative for the current *intended* Docling MCP service design.
- Does NOT assert the service is installed, configured, reachable, or validated.
- SERVER-REGISTRY.md is authoritative for host/role placement.
- servers/<host>/configuration.md is the as-built authority AFTER implementation.
- Legacy 2025 sources are non-authoritative evidence and lessons only.

Current-fact authority precedence

1. SERVER-REGISTRY.md / current infrastructure contracts
2. current server records + current governance decisions
3. approved current architecture rationale (v0.3)
4. the current service design being authored here
5. legacy sanitized material — evidence/lessons only, never authority

Resolve, never translate. Resolve every host, address, port and name from current authoritative files. Never numerically translate or infer a current endpoint from its 2025 value (e.g. do not derive an IP by mapping 192.168.10.x→192.168.50.x). If the current value is not yet fixed, mark it VERIFICATION REQUIRED.

8Ledger closure — record knowledge use, not a false migration

A historical file does not migrate; knowledge from it does. Do not flip migration_status to migrated for a historical source just because it was cited — a future executor would read that as "this file is now in main." The v3 schema is frozen, so record distillation state in provenance-index.jsonl, leaving the historical row's file-migration status unchanged.

provenance-index.jsonl entry (per cited row):
{
  "id": "lgc-###",
  "disposition": "historical",          # unchanged
  "location": "sanitized-ref",          # unchanged
  "distillation_status": "used | reviewed-not-used | blocked",
  "distilled_into": ["services/docling-mcp/service.md#failure-handling"],
  "reviewed_by": ["docling-mcp", ...],  # current SMEs only, per §9
  "sanitized_sha256": "<if known>",
  "migration_commit": null              # planning only
}
  • Leave migration_status: pending on historical rows. Do not invent a state transition to "close" a row.
  • Confirm no Docling row flipped to a main target during the pilot.
  • The 3 never-open rows: mark blocked / referenced-by-ID, never opened for content.

9Integration classification & SME sign-off gate

Classify each legacy integration before authoring a contract

Do not assume a 2025 integration survives directly in 2026. For LiteLLM, Qdrant, Redis, LightRAG, classify first:

StateMeaning & action
CURRENT REQUIREDRequired by current architecture/placement → author a real current contract.
INDIRECTDocling reaches the capability via another current service/gateway → do not invent a direct client contract.
LEGACY CANDIDATEUseful historically, not yet approved for current design → keep in provenance/verification list.
RETIREDNo current role → lesson only.

Example: if current architecture has Docling send processed content through another service that owns Qdrant, do not author a direct Docling→Qdrant contract merely because one existed in 2025.

SME sign-off rule

  • A 2025 SME review is historical evidence, never 2026 sign-off.
  • Record a current SME in reviewed_by only if the current specialist contract exists and the review actually ran.
  • If a required current SME contract is missing, mark the section SME REVIEW REQUIRED and report it as a dependency (specialists are being reconstructed capability-first, policy P-AGENTS).
  • The draft may still be returned, but it does not earn "multi-SME pass" until required reviews exist.

10Docling ↔ model-serving boundary

Docling is the document-processing service (conversion / extraction / OCR). Do not describe core Docling conversion as "served by vLLM."

- Docling performs document conversion/extraction/OCR.
- Where a Docling workflow requires an LLM, use the current model-gateway
  contract (e.g. LiteLLM routing to approved backends) IF current architecture
  calls for it — classify that integration per §9.
- Do NOT make vLLM a dependency of core Docling conversion unless the current
  design explicitly requires GPU acceleration on Docling's assigned host.

Omit "Blackwell toolchain pins" from this Docling pilot unless the current Docling design actually requires GPU acceleration — that is a fleet/model-serving concern and must not silently become a Docling requirement.

12Compactness rule

Compactness is part of the experiment. No historical chronology; no copied task sequences; no defect narratives longer than the constraint + provenance; no duplicated install/validation prose; prefer tables for integration contracts and verification items. If the document exceeds roughly 6,000–8,000 words, explain in the pilot report what could not be safely condensed.
