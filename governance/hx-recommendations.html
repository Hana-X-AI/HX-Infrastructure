R1

Install SMART monitoring across the fleet

do firstpackage install
Why

Not one drive in the fleet has SMART monitoring. smartmontools is absent on all sixteen machines, so no drive can report a pending failure. Eleven hosts run a single device with no redundancy, where a drive failure is a total host loss, and three of those (hxs-11, hxs-14, hxs-15) run aftermarket iDsonix units whose endurance and firmware history are not known from vendor records.

Do

Install smartmontools fleet-wide and enable smartd with email or log alerting. This is the cheapest risk reduction available and needs no design decision.

R3

Establish an off-machine copy of the repository

do firstone destination decision
Why

act-005, open since 2026-08-11. The complete discovery record for sixteen machines, the registry, the governance history, the hooks and the risk register exist on one workstation. Local commits are history, not a backup. The blocker was that hanax-ai/HX-Infrastructure on GitHub is taken by an unrelated project.

Do

Pick any destination — a differently-named GitHub repository, a private remote, or an external drive. The destination matters far less than having one.

R4

Make the control-plane laptop reliable before relying on it

do firstconfig + adapter
Why

Verified on the host: hxs-cp has no Ethernet hardware at all — Wi-Fi is not a fallback, it is the only path — and its lid switch is at systemd defaults, so closing the lid suspends the machine. It is the only access path to the fleet and the machine every deployment runs from.

Do

Set HandleLidSwitch=ignore in logind.conf, and add wired networking through its Thunderbolt 4 port. If the laptop ever leaves the building, separate the control-plane deployment key from the human workstation key first — the control-server document already calls for this.

R5

Put the idle storage to work as shared fleet storage

worth doingno hardware
Why

Storage is inverted. Every data-bearing service sits on the smallest disk in the fleet: Postgres and Redis, Docling, n8n, Open WebUI and Crawl4AI each write to a 238.5 GB boot device with about 210 GB free, no second drive and no free bay. On a single-device host a full disk stops the host, not just the service. Meanwhile hxs-1 holds roughly 11 TB unallocated and hxs-2 a further 1.2 TB.

Do

Export hxs-1's unallocated 3.6 TB NVMe and 7.3 TB HDD over NFS as shared fleet storage — model cache, deployment artifacts, and a backup target for the database and workflow hosts. Scope it to model cache, deployment artifacts and backup snapshots only.

Constraints

Never put live database files on NFS — not the Postgres data directory, not Qdrant storage. That is a corruption risk, not a performance one. Three coordination points before acting: v0.3 puts backups on an external observability box, so pick one home for backups rather than splitting them; v0.3 also earmarks hxs-1's 3.6 TB NVMe as the escape hatch if Qdrant vectors outgrow hxs-4, and the same device cannot be committed to both, so decide its primary job first; and hxs-1 is the reasoning GPU host, so making it the fleet's NFS server puts an I/O dependency on the most performance-critical machine. Acceptable at dev/test scale — eyes open.

R7

Decide whether the test host needs virtualization

worth doingfirmware change
Why

hxs-15 is assigned QA, regression, integration testing and agent-workflow validation, and it is the only host in the fleet that does not expose VT-x (iss-011). Container work is unaffected; anything hypervisor-backed cannot run there.

Do

If testing needs VMs, enable Intel VT-x in the HP P21 firmware and re-run the collector to confirm. If it does not, record that so the constraint stops being re-raised.

R8

Give the largest host something to do

considerplanning
Why

hxs-1 is the most capable machine in the fleet — 24 cores, 128 GB, 32,752 MiB of VRAM, the only PCIe-4 platform — and its only assignment is a reserved slot for a model that has not been released. You have said this is fine for now; noted here so it stays visible.

Do

The coder-versus-reasoning host question is benchmark-gated in Phase 3: v0.3 records hxs-2 as the PCIe-3 host, and the swap is only considered if measured decode throughput falls below an acceptable bar. R5 would also give hxs-1 a useful job in the meantime.

R9

Close out the quarantined regression suite

considerone reboot
Why

iss-010. Norton quarantined the suite; the trigger surface has been removed and it passes 153 of 153, but it still runs under a temporary filename because the canonical path is held by a delete-pending lock. .claude/AGENTS.md names the canonical path in its verification list.

Do

Reboot the workstation, then rename the file back. If the path is still denied afterwards, the block is a Norton rule rather than a stale handle and needs clearing in its Security History.

Resolved

Settled since this document was written. Kept for the record rather than deleted.

R2

Resolve the LiteRAG / LightRAG naming conflict — resolved

resolveddecided 2026-08-13
Why

The two documents disagree. The original Hana-X spec used both names interchangeably; the validation findings state that LightRAG (HKUDS) is the real product and call LiteRAG a misnomer, citing that project's env.example, API-server docs and issue #2233. Configuration keys such as LIGHTRAG_VECTOR_STORAGE follow whichever is actually correct.

Outcome

LightRAG is correct, decided 2026-08-13. All references corrected in v0.3.

R6

Reconcile the architecture documents — resolved

resolveddone 2026-08-13
Why

There are now two copies of the same architecture. hx-stack-alignment-v0.1-frozen.html is the frozen v0.1 baseline the validation pass was run against; fleet-architecture-candidate-v0.1.html carries your applied decisions and is therefore no longer v0.1. The validation pass then produced seven further changes for a v0.2. Three documents currently describe the same fleet differently.

Outcome

Done. v0.3 is the current architecture, with the owner decisions applied; the intermediate v0.2 is retired; the frozen v0.1 is kept as the immutable baseline.
