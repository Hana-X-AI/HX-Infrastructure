ll-031 2026-08-13
Lesson

Do not re-derive a fact from evidence when an authoritative record already holds it. Evidence is noisy by nature; the authoritative record exists precisely so the fact does not have to be guessed twice.

Evidence

Normalizing the 15 pre-work records needed each server IP. Extracting it from the terminal paste looked obvious and was wrong on 4 of 15: hxs-2 and hxs-3 returned the subnet 192.168.50.0, hxs-5 returned the gateway 192.168.50.1, and hxs-7 returned an unrelated 192.168.50.115. Every one of those addresses appears legitimately in its paste. SERVER-REGISTRY.md had the correct value for all fifteen.

Applied

The documentation standard now requires the IP in a pre-work record to come from the registry, never from the paste. More generally: when a script must fill a field, name the authoritative source for that field before writing the extraction, and if there is no authoritative source, that is the finding.

ll-030 2026-08-13
Lesson

A comparative claim is only true of the set that existed when it was written. In a record set built incrementally, every superlative and every uniqueness claim silently rots as later records arrive, and nothing in the record itself signals that it has.

Evidence

Closing the "documented and comparable" gate condition surfaced 27 stale or false cross-host claims across 13 of the 15 discovery records. hxs-6 claimed the newest firmware in the fleet; hxs-8 is newer, and hxs-8 in turn claimed to be second newest. hxs-6 claimed to be the only host with Secure Boot; hxs-7 also has it. hxs-4 claimed the smallest memory and smallest storage; three later hosts beat it on both. Batch-membership notes counted four or five members where six now exist. All were accurate on the day they were written.

Applied

Write comparative claims with their scope attached — "of the four GPU hosts", "of the six-unit batch" — rather than "in the fleet" or "so far", which quietly expand as the set grows. Before accepting a set of records as comparable, re-verify every superlative against the complete set; a scan for only, newest, smallest, largest and so far finds them cheaply. Treat this as a required step whenever an incrementally-built record set is declared complete.

ll-029 2026-08-13
Lesson

Batch identity does not imply configuration identity. Two machines from the same production batch, with consecutive serials and identical hardware, can still differ in firmware settings — and that difference is invisible unless the same field is collected from every host and compared across the fleet.

Evidence

iss-011: hxs-15 is the sixth member of the 8CG8170Sxx batch and matches hxs-5, hxs-9, hxs-10, hxs-11 and hxs-12 in CPU, memory, integrated graphics, storage class and firmware revision. It is the only host in 15 where VT-x is not exposed. Nothing about its model, serial or hardware predicted it. It surfaced only from a fleet-wide comparison of the one field that all 14 other records also carried.

Applied

The value of a uniform collector is the comparison it makes possible, not the individual record. Before accepting a record as unremarkable because the host belongs to a known batch, diff its fields against the batch. Treat "same as the others" as a claim to be checked, not a default.

ll-028 2026-08-12
Lesson

A change made for a non-functional reason can still change behaviour. Run the tests after cosmetic and defensive edits, not only after logic edits.

Evidence

Splitting the destructive literals for iss-010 was meant to be purely textual, but @("mk" + "fs", "wipe" + "fs") does not build a 7-element array: in PowerShell the comma operator binds tighter than +, so it evaluates as "mk" + ("fs","wipe") + "fs" and collapses to one joined string. The deny-rule coverage check silently had nothing left to check. Only running the suite caught it.

Applied

Parenthesise each element when concatenating inside an array literal. More generally, treat "this edit cannot affect behaviour" as a claim to be verified by the suite, not an assumption that licenses skipping it.

ll-027 2026-08-12
Lesson

Test data that mimics an attack will be treated as one. A file full of destructive command literals is indistinguishable from a destructive script to a scanner that reads bytes rather than intent.

Evidence

iss-010: Norton 360 quarantined the regression suite. Its 14 verbatim destructive commands existed solely to prove the Phase 1 guard denies them, but combined with redirected-stdio process spawning and temp-file writes they read as a disk-wiping script. Nothing in the file was malicious and nothing needed removing.

Applied

Destructive literals in test data are assembled at runtime from fragments, so the token never appears verbatim while the assembled string still reaches the code under test. Coverage is unchanged. Where a security guard is tested by feeding it real attack strings, expect the test file itself to be scanned as hostile and design for it.

ll-026 2026-08-12
Lesson

A hostname is a claim by the host, not an identity. Confirm identity with serial and machine ID before trusting a name, especially across cloned or imaged machines.

Evidence

Two physically distinct EliteDesk 800 G3 units both reported hxs-9. They were separated only by system serial 8CG8170SW8 against 8CG8170SXM, and by their machine IDs. A pre-work record showing hxsa@hxs-9 prompts was initially read as a copy-paste error from the previous server; it was actually correct, and the machine really was misnamed.

Applied

Where a host's reported name conflicts with the intended one, treat serial and machine ID as the deciding evidence, write no discovery record, and raise it. Recorded as iss-009.

ll-025 2026-08-12
Lesson

Never name an output file from a value the remote host controls, unless the name is also made unique by something you control. A collision destroys the earlier file with no error.

Evidence

hx-collect.ps1 named its output <hostname>-facts.txt. The host at .209 reports itself as hxs-9, so collecting it silently overwrote the genuine hxs-9 collection from .208. Only the raw facts file was lost, because the discovery record had already been written, but nothing warned.

Applied

Output is now <hostname>-<last-octet>-facts.txt, and the script prints a note when it overwrites an existing file.

ll-024 2026-08-12
Lesson

"Read it first" means before every other action, not in the same batch as them. A gating step run concurrently with the steps it is meant to gate has not been run at all.

Evidence

ll-014 created step 0 of the discovery skill after the hxs-3 GPU miss. Two servers later, on hxs-5, the pre-work file was opened in the same batch as network probes of two candidate addresses. The file already stated the address, the account and SUDO_NOPASSWD=yes on lines 12, 68 and 78. Nothing needed probing, and one of the two probed addresses was pure inference from a numbering pattern. The failure was announced as "following step 0" while not following it, which is worse than skipping it openly.

Applied

Step 0 now reads "before contacting the target in any way. Not in the same batch as other calls. Not concurrently." It names the address, account and privilege state as facts the file supplies, and forbids probing for them or inferring an address from a pattern.

ll-023 2026-08-12
Lesson

Kernel messages from the open-source driver are a trustworthy VRAM source. Verify the method when the authoritative source finally becomes available.

Evidence

nouveau reported 16376, 16311 and 8151 MiB across the fleet during Phase 1 discovery. When nvidia-smi became available it returned exactly the same figures for every card. The governance rule requiring a kernel message that names the value as VRAM produced correct results with no vendor driver present.

Applied

The kernel-message method stands as the Phase 1 VRAM source. Where an independent authority later appears, compare and record the agreement rather than silently replacing the earlier value.

ll-022 2026-08-12
Lesson

An open-source driver failing to initialize hardware is not evidence that the hardware is faulty. Test the vendor driver before touching the machine.

Evidence

Two MSI 1462:5351 cards in hxs-2 aborted nouveau initialization with -22 across multiple boots and a full upgrade. Under nvidia-driver-580-server-open both initialized immediately as RTX 5060 Ti with 16311 MiB each. The physical card-swap work planned in act-008 was never needed and closed unperformed.

Applied

Where a vendor driver exists and is authorized, run that test before scheduling hardware handling. It is faster, reversible, and does not risk damaging working parts.

ll-021 2026-08-12
Lesson

When two variables are confounded, design the test that separates them in one move rather than the test that is easiest to reach.

Evidence

The obvious next step was removing one card from hxs-2 — but MSI 1462:5351 had only ever run in pairs and only in that host, so card and host stayed confounded whatever the result. Moving one card into the known-good hxs-4 separates them in a single step.

Applied

act-008 specifies the cross-host swap, and states what each outcome proves before it is run.

ll-020 2026-08-12
Lesson

A matching PCI device ID does not mean a matching card. Record the subsystem ID, which identifies the board partner and the VBIOS, not just the chip.

Evidence

Two hosts were described as having "the same GB206, PCI 10de:2d04", and the difference between working and failing was assumed to be one card versus two. The subsystem IDs showed otherwise: the failing host runs MSI 1462:5351, the working ones run PNY 196e:143e and MSI 1462:5371. The only failing model is MSI 1462:5351, on both instances.

Applied

Subsystem ID is now recorded for every GPU in every discovery.md. Comparisons across hosts use it, not the device ID alone.

ll-019 2026-08-12
Lesson

An owner-initiated change is also an experiment. Record what it ruled out.

Evidence

A full package upgrade and reboot of all four servers left both GPU faults completely unchanged, and the kernel stayed at 7.0.0-28-generic so nouveau never changed version. That single action eliminated stale packages, a transient boot-time race, and driver version as explanations, and it cost nothing.

Applied

When the owner changes host state, re-collect and state explicitly which hypotheses the change eliminated, rather than only noting that the fault persists.

ll-018 2026-08-12
Lesson

A plausible hypothesis with a real supporting pattern can still be wrong. Run the test before acting on it, and report the refutation as prominently as the theory.

Evidence

The Above 4G Decoding theory fitted every visible fact: both faults on the only two 2016-firmware hosts, -22 consistent with MMIO exhaustion, modern boards unaffected. The diagnostic confirmed Above 4G is disabled and every BAR sits below 4G, then refuted the theory outright — hxs-3 works with the identical 256 MiB BAR1. The real failure is GSP firmware initialization. Acting on the theory would have meant a firmware change that fixes nothing.

Applied

act-007 records the refutation in full. A correct-looking cause that survives only because it was never tested is worse than an open question.

ll-017 2026-08-12
Lesson

State a hypothesis as a hypothesis, and name the evidence that would settle it. Circumstantial correlation across a small fleet is a lead, not a finding.

Evidence

Both GPU faults occur on the only two hosts with 2016 firmware, while both hosts with 2025 firmware run two GPUs each. That pattern suggests an Above 4G Decoding / MMIO exhaustion cause, and -22 is consistent with it — but no BAR evidence has actually been collected.

Applied

act-007 records it explicitly as a hypothesis with the confirming test attached. Hardware conclusions are not written into a discovery.md until measured.

ll-016 2026-08-12
Lesson

A filter written for one purpose will silently exclude evidence for another. The collector's kernel-log filter targets GPU memory, so it cannot see PCI enumeration failures, which is precisely the evidence needed when a GPU does not appear.

Evidence

Investigating iss-007 and iss-008 produced no BAR or resource errors from the collected output. That absence was an artefact of the vram|gddr|nouveau|nvidia filter, not evidence that no errors occurred.

Applied

Fault investigation uses a purpose-built diagnostic (hx-gpu-diagnose.sh), not the discovery collector. Never read "the collector found nothing" as "nothing is there".

ll-015 2026-08-12
Lesson

Read all of what a tool collected, not just the field being hunted. A narrow extraction filter discards facts the collector correctly captured.

Evidence

The GPU chip identity NVIDIA GB206 was present in both hosts' kernel output, and the nouveau initialization failure on hxs-2 (Device allocation failed: -22) alongside it. Both were missed by grepping only for vram|gddr, and both are more informative than the fields that were extracted.

Applied

Extraction filters are for finding a starting point, not for deciding what matters. Scan the surrounding context of any section that answers a key question.

ll-014 2026-08-12
Lesson

Read the human pre-work record before collecting, every server, not only when told to. It is an independent second source, and the value is in comparing it with the collected facts rather than in either one alone.

Evidence

hxs-3 was recorded as having one GPU because the operating system enumerates one. The owner knew two were installed. The discrepancy was caught by the owner, not by the process, and it turned out to be a real hardware fault (iss-007). hxs-2's pre-work happened to corroborate its collection, but only because that file was read by chance.

Applied

discover-server skill now makes reading and cross-checking pre-work step 0. Device counts are compared explicitly, and a truncated pre-work file is reported before collection begins.

ll-013 2026-08-11
Lesson

Look upstream of a missing fact before working to obtain it. The unreadable value is often a symptom of a larger condition that matters more than the value.

Evidence

GPU VRAM could not be read on hxs-1. The cause was that both GPUs run nouveau with no CUDA driver installed — which also means the host cannot serve a model at all. The driver, not the number, was the finding.

Applied

Report the upstream condition first. Resolving it usually resolves the missing fact for free.

ll-012 2026-08-11
Lesson

Record the source of every measured fact alongside the value. A number without its provenance cannot be audited, and invites a plausible substitute when the real source is missing.

Evidence

Same VRAM work: two candidate sources disagreed in principle, and only one was legitimate.

Applied

discovery.md states VRAM and VRAM source as separate fields.

ll-011 2026-08-11
Lesson

A PCI base address register is an address-space aperture, not physical memory. BAR size must never be recorded as GPU VRAM, and the Resizable-BAR "BAR1 equals VRAM" heuristic is not evidence.

Evidence

A VRAM probe was drafted that offered BAR1 as corroboration. Corrected by governance/reports/Claude Prompt - Discover GPU VRAM Without NVIDIA Drivers.md.

Applied

VRAM is taken only from a kernel message that names it as VRAM or framebuffer memory, or from a sysfs VRAM attribute. Otherwise recorded as unavailable with the model and PCI ID preserved.

ll-010 2026-08-11
Lesson

Check whether a remote name is already taken before planning to push to it.

Evidence

The intended GitHub repository name held an unrelated public project with its own history and an open pull request.

Applied

act-005 stays open pending a destination decision. Nothing was forced.

ll-009 2026-08-11
Lesson

Policy contradictions surface at first contact with real hardware, not during review. Three documents had been reviewed repeatedly without anyone noticing the address ranges would exclude the first server.

Evidence

iss-006: hxs-1 at .200 fell outside the documented server range on the day it was discovered.

Applied

Resolved by owner amendment. Expect the remaining 14 discoveries to surface similar contradictions; record them rather than quietly conforming.

ll-008 2026-08-11
Lesson

A guard that inspects command text cannot tell a quoted example from a real invocation.

Evidence

The Phase 1 guard denied a commit whose message described a RAID fix. Correct behaviour, surprising in the moment.

Applied

Pass commit messages through a file. Do not weaken the pattern to make prose easier to write.

ll-007 2026-08-11
Lesson

sudo -n in a collector fails silently and takes required facts with it. The non-root dmidecode fallback returns a banner and no data, which reads like a collected result.

Evidence

First hxs-1 collection lost manufacturer serial, BIOS detail and the whole DIMM layout without any visible error.

Applied

Collector needs a non-root fallback to /sys/class/dmi/id/*, and a supplementary root pass where firmware facts are required.

ll-006 2026-08-11
Lesson

The ! prefix has no controlling terminal, so anything needing an interactive prompt fails there. Redirecting a script into ssh also consumes the stdin that the password prompt would use.

Evidence

Two failed discovery attempts; the second sent the script's opening comment lines as password guesses.

Applied

Interactive authentication runs in the operator's own terminal. Automation-facing work needs an authentication method that does not prompt.

ll-005 2026-08-11
Lesson

PowerShell mangles scripts piped to a remote shell. Get-Content yields an array of lines and the pipeline rejoins them with \r\n, so a byte-perfect LF script arrives at Linux bash full of \r.

Evidence

Remote bash failed with $'\r': command not found while the local file contained zero CR bytes.

Applied

Transfer scripts base64-encoded, or use a shell whose redirect is byte-exact. Never diagnose the file before checking the transport.

ll-004 2026-08-11
Lesson

Verify the repository can accept a commit before relying on it for history.

Evidence

iss-005: the baseline was committed with CRLF already in the objects while core.autocrlf and core.safecrlf were both true, so every subsequent commit was refused. Nothing had been committed since, so it went unnoticed.

Applied

.gitattributes disables end-of-line conversion. Commit early enough to surface this class of problem.

ll-003 2026-08-11
Lesson

Do not infer live tool behaviour from documentation or from a test fixture. The subagent test supplied the very field whose existence was in question, so it validated its own assumption.

Evidence

iss-002: only a live run proved the matcher is honoured and that the payload really carries agent_type and last_assistant_message.

Applied

Verify against a live run before hardening. Fixtures confirm shape, not reality.

ll-002 2026-08-11
Lesson

An untested guard pattern is an unguarded path. Test coverage existed for 1 of 13 blocked categories, and the untested ones included the most destructive.

Evidence

iss-004: the RAID rule could never match, because \b finds no word boundary between a space and a leading dash. Array creation was permitted for the entire life of the guard.

Applied

Every guard category now has a blocked case and a read-only allowed case.

ll-001 2026-08-11
Lesson

A syntax check is not an execution test. bash -n and PowerShell parse checks were treated as proof the automation worked; neither the regression suite nor the discovery collector had ever actually run.

Evidence

iss-003: the suite deadlocked on its second hook call and had never completed. The collector's first real execution was against hxs-1, weeks after it was declared verified.

Applied

Suite now runs to completion and reports a result. Treat "parses" and "passes" as different claims.
