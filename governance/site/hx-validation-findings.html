Research & Validation Findings

Six focused threads checked the frozen Architecture Candidate v0.1 against current (August 2026) runtime behavior and compatibility — to validate the mapping, not redesign it. The verdict: the architecture holds. Nothing forces a re-layout. The pass did surface seven concrete corrections to fold into a v0.2 before the roadmap — one of them (LiteLLM's datastore) is a real blocker if left as-is.

Changes to fold into v0.2 — ordered by how much they bite. None of these move a workload to a different host; they change how a host's service is configured.

  1. blocker  LiteLLM needs PostgreSQL, not SQLite. LiteLLM's schema is Postgres-only; pointing it at SQLite hangs the proxy on startup. Its virtual-key, spend, and rate-limit features simply don't work without Postgres. Point hxs-8's LiteLLM at the existing hxs-9 Postgres (a dedicated litellm database). The spec's “LiteLLM + SQLite” is not viable.
  2. revisit  gpt-oss-20b fits a single 16 GB card. Its MXFP4 weights are ~13 GB. The TP=2 decision on hxs-3 still works, but it buys lower latency at a PCIe cost with little upside — the original Option B (one card for gpt-oss, second card free for experimental inference) is fully viable. Worth re-confirming now that we know it fits on one.
  3. tune  Coder-32B is on the slowest platform. hxs-2 is the 2014 PCIe-3 host, and a TP=2 32B does an all-reduce every layer — PCIe is the bottleneck there. It fits, but cap --max-model-len ~16–24K and expect PCIe-limited decode. If either big model should sit on the one PCIe-4 host (hxs-1), it's the coder, not the reasoning model — a topology question for v0.2.
  4. serve-with  Embeddings + reranker via TEI/Infinity, not vLLM. On hxs-4's 8 GB card, run Text-Embeddings-Inference (or Infinity) — purpose-built, lighter, dynamic batching — rather than vLLM for BGE-M3 / Nomic / bge-reranker.
  5. guardrail  LightRAG storage is immutable after first ingest. The backend choice and the embedding model + EMBEDDING_DIM are frozen once documents are indexed; a dimension mismatch silently corrupts the store. Pin the embedding model and dimension, and validate one round-trip, before any bulk ingest.
  6. note  Mem0 specifics. Mem0 OSS keeps history in SQLite (Postgres-for-history isn't native), needs its own Qdrant collection distinct from RAG, and its graph memory is now Platform-only (removed from OSS). Our graph lives in LightRAG anyway, so this is fine — just don't plan on Mem0 graph memory self-hosted.
  7. harden  MCP servers are unauthenticated by default. Docling / Crawl4AI / n8n / Mem0 / FastMCP servers ship no auth and bind 0.0.0.0. Standardize on Streamable HTTP and front every networked MCP server with a reverse proxy enforcing a bearer token / mTLS + Origin allow-list, bound to the LAN interface.

01GPU serving & model fit

Verdict: the fit holds, with a toolchain pin and two topology nuances. Critically, no tensor-parallel group mixes GPU generations — hxs-1 is an Ada pair, hxs-2 and hxs-3 are Blackwell pairs, hxs-4 never pools — so the “don't mix arches in one TP group” rule is already satisfied.

04Bare-metal venv isolation

Verdict: the no-Docker, one-venv-per-service approach is sound — cross-service Python conflicts are structurally impossible. The only shared surfaces are the NVIDIA driver, GPU VRAM, and a few root-level system libs.

Where this leaves us

Candidate v0.1 survives validation intact — every host keeps its role. The seven changes above are configuration and sequencing corrections, not a re-layout. The natural next move is a small v0.2 that folds them in (most importantly, LiteLLM → Postgres), after which the phased roadmap — foundation → platform services → inference → retrieval/RAG → agents/MCP → applications → test/demo → hardening — can be written with each phase backed by what was validated here.
