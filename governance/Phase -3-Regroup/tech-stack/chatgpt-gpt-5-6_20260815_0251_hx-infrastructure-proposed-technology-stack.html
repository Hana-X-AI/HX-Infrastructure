Proposed Technology Stack

A technology-only view of the HX platform: what belongs in the stack, the role each component should play, how the layers relate, and which choices remain conditional. This deliberately excludes server assignment, deployment topology, implementation sequence, and installation detail.

Status: PROPOSED TRUE-NORTH STACK · Date: 2026-08-15 · Revised: 2026-08-15 03:05 ET · Prepared by: ChatGPT / GPT-5.6
Scope: development, testing, and demonstrations; self-hosted; full-stack capability valued above production-scale optimization.
Evidence basis: current owner decisions, consolidated repository, fleet architecture v0.3, runtime acceptance evidence, service designs and review verdicts, joint reconnaissance, prior capability recons, and the Granite Docling reconnaissance completed 2026-08-15.
Executive conclusion. HX should be a governed, self-hosted AI application platform—not merely a cluster of model servers. Its center is nine deliberately separated planes: governance and execution control; systems foundation; edge and traffic; AI inference; retrieval and knowledge; agents, memory, and MCP; data and state; experience and automation; and observability and recovery. The stack is coherent when each technology owns one clear job and does not quietly become a second authority for routing, memory, execution, or truth.

How to read the stack

FOUNDATIONAL / DECIDED is an owner-ratified direction or durable project standard. PROPOSED CORE belongs in the target platform; an item marked IN BY DEFAULT remains in the architecture unless a materially superior replacement or evidence-based exclusion emerges. CONDITIONAL is a real stack need with an unresolved product, model, or configuration choice. ROADMAP has credible value but should not be treated as current platform authority. DEFERRED is intentionally later. OUT / SUPERSEDED should not appear as target-state architecture.

True-north architecture principles

One authority per concern

One traffic plane, one durable-memory authority, one registry/governance truth, and one execution-control model. Integration must not create shadow authorities.

Capability before placement

Define the service contract and accepted use first. Hardware placement, deployment order, and optimization follow later.

Evidence-bounded acceptance

A runtime is accepted for a specific client, task, context envelope, and access path—not “accepted” in the abstract.

Open interfaces, replaceable components

Prefer OpenAI-compatible model APIs, MCP for tools, PostgreSQL/Redis/Qdrant for standard data roles, and contracts that permit components to change without redesigning the platform.

Native, observable operations

Linux services, isolated environments, explicit configuration, native Bash/SSH automation, tests, logs, and reproducible evidence are the baseline.

Dev/test realism without production theater

Exercise the complete stack and meaningful controls, but avoid premature HA, orchestration complexity, and a broad hardening program before the platform works.

The proposed stack by platform plane

1 · Governance & Control

Git-centered, specification-driven operating system for the project

FOUNDATIONAL / DECIDEDGit + GitHubsdd-core patternMarkdown authoritiesdark-mode HTML reviewsClaude Codeagents · skills · hooks

Role: hold architectural truth, decisions, contracts, policies, evidence, tests, actions, issues, and lessons; route AI agents to the correct authority; enforce boundaries before commands are executed.

Proposed shape: repository-native specifications and governance remain authoritative; human reviews are rendered as polished HTML. Claude Code is the primary AI execution environment, augmented by specialist agents, reusable skills, and fail-closed hooks. Git history and tests provide provenance.

Boundary: AI tooling may propose and execute authorized work; it may not redefine owner decisions, silently widen acceptance, or mutate servers during planning.

2 · Systems Foundation

Simple, inspectable Linux service foundation

FOUNDATIONAL / DECIDEDUbuntu ServersystemdPython virtual environmentsBash + SSH/SCPPowerShell control scriptschronylocal DNS/FQDN

Role: provide the common operating substrate, service lifecycle, time, naming, secure operator access, and repeatable fleet administration.

Operating model: one isolated environment per Python service; one explicit systemd unit per long-running service; absolute interpreter paths; native configuration and logs. The validated fleet-control baseline is Bash over SSH/SCP with explicit host mapping and verification modes.

Boundary: this is deliberately not an Ansible stack and does not require Docker, Kubernetes, or another orchestration authority.

3 · Edge & Traffic

Separate human ingress from model-traffic authority

PROPOSED CORENGINXOmniRouteOpenAI-compatible APIsLiteLLM SUPERSEDED

NGINX role: user-facing reverse proxy, TLS termination, path routing, and controlled ingress. It is the web edge, not the model-routing brain.

OmniRoute role: the narrow, governed AI traffic plane—model endpoint registry, routing, policy, access mediation, and observability for model calls. It should become the only approved path for remote consumption of otherwise local runtimes.

Boundary: OmniRoute routes traffic; it does not own agent orchestration, durable memory, model acceptance, or general MCP execution. LiteLLM remains historical/reference evidence and must not survive as a competing target gateway.

Unresolved: the exact edge/agent mechanism by which OmniRoute fronts loopback-only runtimes. That is a later architecture decision and measurement problem, not a reason to broaden runtime bindings now.

4 · AI Inference

Two runtimes with intentionally different jobs

PROPOSED COREvLLMOllamaHugging Face ecosystemQwen familygpt-oss family

vLLM role: strategic high-throughput and higher-context serving for primary reasoning, coding, and agent models through an OpenAI-compatible surface. It is preferred where explicit context enforcement, batching, tensor parallelism, and production-style serving behavior matter.

Ollama role: bounded local utility inference, rapid model evaluation, and simple loopback services. It is complementary to vLLM, not a universal backend. The measured Qwen3.5-9B workload is accepted only for bounded local use and explicitly refused as a Claude Code backend under the observed context behavior.

Model layer: Qwen remains the primary family for reasoning, coding, and utility roles; gpt-oss remains a candidate for agent/tool execution. Exact models, quantizations, and context envelopes remain workload decisions, not permanent platform identities.

Boundary: no runtime receives broad acceptance. Every workload needs a model/runtime/device/client acceptance record with explicit exclusions and reversal criteria.

5 · Retrieval & Knowledge

Document knowledge, vector search, graph retrieval, and code intelligence remain distinct

PROPOSED COREQdrantLightRAGDocling + Granite Docling 258MADOPT WITH LIMITSCrawl4AITEI or InfinityBGE-M3 / NomicBGE rerankerCode-Graph-RAG

Qdrant role: vector storage and similarity search for governed collections. Collection ownership and embedding dimensions must be frozen before first ingest.

LightRAG role: human, document, governance, and domain knowledge retrieval with graph-enhanced context. It remains the general knowledge plane.

Docling + Granite Docling role: high-quality PDF and office-document parsing, structure recovery, and normalized content production. Granite Docling 258M is HX's preferred embedded Docling VLM for scans, complex reading order, tables, equations, code, and other visually difficult pages. It remains inside the Docling service boundary and is not a general-purpose vision endpoint or an OmniRoute-served conversational model. The conventional Docling pipeline remains the faster benchmark control and operational fallback for clean born-digital material until a representative HX corpus determines the default-routing policy.

Granite Docling acceptance: ADOPT WITH LIMITS. Pin and verify the model revision, prefetch its artifacts, validate DocTags before ingestion, bound page time/output/retries, and measure fidelity plus CPU/GPU performance against the conventional pipeline. Exclusion requires a demonstrated fidelity, reliability, licensing, or operational failure—not preference alone.

Crawl4AI role: web acquisition, extraction, and cleaning for ingestion pipelines.

Embedding/rerank role: TEI or Infinity should serve BGE/Nomic embeddings and BGE reranking through a purpose-built, batchable inference surface. The final serving runtime and exact embedding model/dimension remain conditional.

Code-Graph-RAG role: future structural source-code intelligence—AST, calls, imports, and data flow. It complements rather than replaces LightRAG and should first be piloted on known code-heavy repositories such as jcode and OmniRoute, with read-only exposure.

6 · Agents, Memory & MCP

Orchestration, durable memory, and tool exposure are separate capabilities

PROPOSED CORELangGraphFastMCPcustom Hana-X MCP servicesMem0 · IN BY DEFAULTStreamable HTTP

LangGraph role: stateful workflow and agent orchestration, durable checkpoints, structured human interrupts, resumability, bounded iteration, and capability composition. The migration/review methodology is proven; the current service design remains parked until its failed review conditions and topology decisions are resolved.

FastMCP role: standard implementation framework for exposing governed Hana-X capabilities through MCP. MCP services should wrap bounded functions such as document conversion, crawling, retrieval, or infrastructure intelligence—not become an uncontrolled parallel execution plane.

Mem0 role: proposed-core durable user/agent memory service with its own storage, retention, and deletion boundary. Mem0 is in the architecture by default. It may be replaced or excluded only if a materially superior technology emerges or evidence establishes a significant architecture, fidelity, operational, licensing, or security conflict. It must not duplicate LangGraph checkpoints or LightRAG knowledge, and its graph-memory function is not part of the proposal.

Boundary: LangGraph owns orchestration state; Mem0 owns durable user/agent memory; LightRAG owns document/domain knowledge; MCP exposes tools; OmniRoute owns model traffic. None inherits authority from another.

7 · Data & State

Durable relational state, fast ephemeral state, and narrowly scoped local state

PROPOSED COREPostgreSQLRedisSQLite — narrow use only

PostgreSQL role: platform state, identities/configuration/audit, service-owned schemas, and durable LangGraph checkpoints. Each service receives explicit database/schema ownership and least-privilege credentials.

Redis role: cache, queues, pub/sub, sessions, and short-lived coordination—not authoritative durable business or agent state.

SQLite role: permitted only for genuinely local, low-concurrency, service-owned history where portability is valuable. It is not a substitute for shared platform state and must not re-enter through a gateway assumption already disproven.

Boundary: Qdrant is vector state, PostgreSQL is relational/durable application state, Redis is ephemeral coordination, and object/file artifacts need explicit backup ownership. These stores are not interchangeable.

8 · Experience & Automation

Human interface, agent-aware UI, and workflow automation

PROPOSED COREOpen WebUICopilotKitAG-UIn8n

Open WebUI role: primary ready-made chat and model interaction surface for development, testing, and demos.

CopilotKit + AG-UI role: custom agent-aware application experiences, streaming state/events, and embedded copilots where Open WebUI is not the product interface.

n8n role: deterministic workflow automation and external-system integration. It coordinates business/process workflows; it does not replace LangGraph for stateful agent reasoning.

Boundary: UI and automation clients consume governed APIs. They do not bind directly to unprotected model runtimes or become sources of architecture truth.

9 · Observability & Recovery

Metrics, dashboards, logs, exporters, and tested recovery

PROPOSED COREPrometheusGrafanaLokinode_exporterDCGM exporterbackup/snapshot tooling

Role: collect host, GPU, service, model, and application telemetry; support capacity decisions and troubleshooting; retain searchable logs; verify backups and restores.

Position: observability is part of the proposed platform, even though detailed integration and the broader security/hardening program are deliberately later. Backup tooling and retention targets still require explicit selection.

Boundary: observability measures and reports. It must not silently become a configuration authority or a substitute for acceptance tests.

What is explicitly not in the proposed target stack

Ansible

PERMANENTLY OUT

Native Bash/SSH is the validated fleet-control baseline. Do not retain Ansible in plans, agents, procedures, or compatibility language.

LiteLLM as target gateway

SUPERSEDED

Historical architecture evidence only. OmniRoute is the proposed traffic-plane authority; running both as peers would create routing and policy ambiguity.

Kubernetes

NOT JUSTIFIED

The dev/test/demo environment does not presently need a cluster scheduler, HA control plane, or a second operational substrate.

Docker as a platform dependency

NOT REQUIRED

Current HX direction favors bare-metal services with virtualenv and systemd isolation. A vendor utility container may be evaluated case by case, but containers are not the organizing principle.

Direct network-exposed Ollama

REFUSED

Ollama’s local endpoint remains loopback-only. Remote use must traverse the governed traffic plane after its mechanism is defined and measured.

Premature production machinery

DEFERRED

Broad HA, multi-tenancy, service mesh, and exhaustive hardening are not current prerequisites. Add them only when a demonstrated need creates value.

Recommended true-north statement

HX-Infrastructure is a self-hosted, specification-governed AI platform for development, testing, and demonstrations. It uses native Linux services and Bash/SSH operations; NGINX for TLS termination, path routing, and controlled human ingress; OmniRoute for governed model traffic; vLLM and Ollama for distinct inference classes; LangGraph for orchestration; Mem0 for durable user/agent memory; FastMCP for bounded capability exposure; PostgreSQL, Redis, and Qdrant for clearly separated state roles; LightRAG, Docling with Granite Docling 258M as its preferred embedded VLM, Crawl4AI, and purpose-built embedding/rerank serving for knowledge workflows; Open WebUI plus CopilotKit/AG-UI for user experience; n8n for deterministic automation; and Prometheus, Grafana, and Loki for operational visibility. Claude Code, jcode, and future read-only code intelligence support the engineering process under repository-enforced authority.

Final recommendation

Adopt this as the proposed technology inventory, not yet as an implementation authorization. It is broad enough to exercise the complete Hana-X platform and disciplined enough to avoid duplicate planes. The next architecture work should convert each proposed-core component into a concise capability contract: purpose, owned state, interfaces, dependencies, exclusions, acceptance evidence, and reversal criteria. Placement and sequence should remain separate until the complete-stack reconnaissance and true-north reconciliation are finished.

Provenance and caution. This synthesis privileges current owner rulings and repository policy over older fleet-architecture wording. Consequently, OmniRoute supersedes LiteLLM; the measured Ollama workload does not overwrite the broader target inference design; the parked LangGraph design is not treated as implemented; and legacy placement statements are not reproduced. Current upstream facts were not used to pin versions in this technology-only proposal; all versions and compatibility claims remain implementation-time verification items.
