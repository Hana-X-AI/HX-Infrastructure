3. The good: capabilities worth preserving

STRONG Evidence-first operating culture

The repository repeatedly separates discovery, configuration, validation, and acceptance. It records why a conclusion was reached, what disproved an attractive hypothesis, and which evidence class supports a claim. The 33 lessons learned are unusually concrete and operational.

Evidence: GOALS-AND-OBJECTIVES.md; governance/logs/lessons-learned.md; governance/policy/ai-runtime-acceptance-contract.md sections that remain intact.

STRONG Fleet discovery is comprehensive and comparable

Fifteen server discovery records exist and are marked complete. The registry contains approved roles, hardware summaries, FQDNs, and lifecycle state. Discovery records preserve as-found evidence and explicitly separate later driver changes.

Evidence: 15 servers/hxs-*/discovery.md records; registry claims 15/15; consistent section template; zero actual per-server configuration.md files.

STRONG Proven migration/distillation method

The legacy-mining workflow has a pinned source ledger, per-row provenance, separate-context capability review, secret discipline, and a valuable distinction between method success and design acceptance. The resolved ledger hash matches the pinned value.

Verified manifestv3.1resolved.jsonl SHA-256: 64eb356f5b22d39c4705e2babb48a16fe6a20e3fa4d5747cba6ed7516c64cd59.

STRONG Active and packaged hooks are synchronized

All eight active PowerShell hook files are byte-identical to their packaged copies. All 25 JSON files parse. Both shell scripts and all four JavaScript utilities pass syntax checks.

Static verification only. PowerShell runtime execution was unavailable in the review environment and is not claimed.

STRONG Authority boundaries are conceptually mature

Docling is kept as parsing rather than retrieval; LightRAG owns retrieval; Mem0 owns durable memory; LangGraph is an orchestrator rather than memory, retrieval, routing, or MCP authority; OmniRoute is intended as the traffic plane. Those boundaries are the right architectural direction even where implementation details remain unsettled.

4. The bad and the ugly: material findings

Severity below reflects potential impact on the next phase, not criticism of the work that produced the repository.

HIGH F-01 — The authoritative AI runtime contract is visibly corrupted

governance/policy/ai-runtime-acceptance-contract.md contains an incomplete profile row, dangling backticks, missing project names, broken provenance sentences, an unfinished non-adoption bullet, and sentence fragments. tests/ai-runtime/README.md contains related provenance corruption. The damage is consistent with the repository’s own warning against regex-based term removal.

  • Line 126 begins | ` live later.
  • Line 128 says the experimental classification applies to ` with no workload name.
  • Line 164 ends It does not adopt `.
  • Lines 170–184 contain broken snapshot, upstream, license, author, and runtime descriptions.

Impact: a policy file used by tests and future runtime decisions cannot be treated as semantically authoritative until restored from a known-good source and re-reviewed.

HIGH F-02 — The repository enforces two incompatible lifecycle models

GOALS-AND-OBJECTIVES.md and SERVER-REGISTRY.md define Phase 2 as repository consolidation and Phase 3 as server implementation. README.md, CLAUDE.md, servers/AGENTS.md, and the final suggested step in start-up/session-resume.md still describe Phase 2 as server configuration.

Impact: agents can follow the closest instruction file and reach a different conclusion about whether server mutation is authorized.

HIGH F-03 — The phase guard releases configuration controls too early under the current constitution

hx-phase1-guard.ps1 stops guarding when the registry’s Phase 2 status is READY, IN PROGRESS, or COMPLETE. Its regression suite explicitly proves that READY releases package installation and other mutations. But Phase 2 now means consolidation; server mutation belongs to Phase 3.

Impact: the code faithfully enforces the old lifecycle, not the current one. This is a control/authority mismatch, not a documentation typo.

HIGH F-04 — Two principal runtime gates do not match the only workload schema

hx-capacity-gate.ps1 and hx-workload-commission.ps1 expect fields such as execution_modes, capacity_gate_result, storage_gate, model_acquisition, server, and revision. None exists in qwen35-9b-ollama.json. The scripts retain DS4/SSD-streaming assumptions while the only workload is an Ollama Qwen3.5 commissioning record.

Impact: the named gate/commissioning commands are not credible for the current workload. The 22-invariant suite checks for source substrings and file presence but does not validate schema compatibility or execute these paths. A green invariant run could coexist with unusable gates—exactly the P-A failure pattern the repository says it prevents.

HIGH F-05 — Current architecture and the fleet registry disagree in two load-bearing places

  1. The registry assigns LiteLLM to hxs-8/hxs-9, while owner decisions say LiteLLM is superseded by OmniRoute.
  2. The registry assigns hxs-4 Qwen2.5-3B plus embeddings/reranking, while runtime acceptance records a commissioned Qwen3.5-9B on the 8 GB GPU. iss-017 correctly records this as unruled.

Impact: the registry is the placement authority, yet current service designs must work around known stale assignments. Foundational architecture cannot safely build on both interpretations.

HIGH F-06 — A real host mutation lacks its required as-built configuration authority

hxs-4 was commissioned with Ollama and Qwen3.5-9B, including a systemd configuration and model acquisition, but there are no per-server configuration.md records anywhere. Evidence exists in the workload JSON, operational HTML report, and action log, but the repository contract says configuration.md is the as-built authority after implementation.

Impact: the repository’s strongest documentation invariant—discovery versus configured state—is not actually complete for its first live AI runtime.

MEDIUM · ADJUSTED F-07 — Two accepted risks have passed their own review trigger X · adjusted

risk-001 and risk-002 remain accepted, but each expires for review at the Phase 1 gate or before Phase 2. Phase 1 is complete and Phase 2 opened. The risk register therefore violates its own acceptance window.

Severity rationale: the original HIGH rating is superseded by the joint brief's MEDIUM rating. F-07 concerns stale decisions about bootstrap credential strength and local credential-file permissions; it is not evidence of a live credential disclosure or a tracked secret value. The expired review triggers still require an explicit owner ruling, not silent continuation.

The snapshot retains extensive DS4 material in governance/operations/hxs3-workload-placement.md, runtime prompts/reports, and log history. Lessons learned assessment

The 33 lessons are one of the repository’s best assets. They cover test failability, host identity, evidence provenance, hardware diagnosis, source authority, transport behavior, secret-safe reporting, and the danger of unscoped comparative claims. They should be retained, not rewritten. The regroup should add only genuinely new generalized lessons:

  • Schema compatibility is a gate: source-text assertions do not prove a gate can consume the current workload definition.
  • Lifecycle changes are cross-cutting migrations: renaming Phase 2/3 requires updating contracts, hooks, tests, startup guidance, and generated pages as one atomic change.
  • Absolute cleanup claims require repository-wide proof: “zero references” must be backed by a scoped scan and must distinguish historical references from future-facing authority.
  • Generated human views are release artifacts: a log update is incomplete until its presentation copy is regenerated and checked for ID parity.

8. Recommended regroup sequence

This is a planning recommendation, not authorization to edit the repository or deploy infrastructure.

  1. Freeze execution authority for the regroup. Continue planning and review, but do not start new server implementation until the lifecycle and runtime contract are coherent.
  2. Restore corrupted source from known-good history. Recover the AI runtime contract and README from the last intact commit or reconstruct them from accepted decisions with explicit review. Do not repair by guessing missing names.
  3. Ratify one lifecycle. Decide the current status of repository consolidation and define the next phase. Then update the constitution, README, CLAUDE instructions, registry vocabulary, server contract, startup handoff, hooks, and regression tests atomically.
  4. Reconcile the registry. Rule hxs-4’s durable workload, replace or annotate LiteLLM entries with the approved OmniRoute target state, and clearly separate approved placement from commissioned exceptions.
  5. Establish OmniRoute as a governed plane. Create the service/authority contract only after confirming its exact narrow role and loopback-fronting mechanism. Preserve the rule: traffic plane, not memory, agent, or governance authority.
  6. Repair runtime gates against the current schema. Either adapt the gate/commission scripts to the Qwen workload schema or archive the stale DS4-era gate family. Add a known-failing schema-compatibility test.
  7. Request the owner's hxs-4 as-built ruling. Ask whether the commissioned exception requires a configuration.md. No configuration record may be owed until the later implementation phase; do not create one unless the owner records that ruling.
  8. Adjudicate logs and risks. Close or reclassify act-015/iss-016, review expired risk-001/risk-002, preserve valid open issues, and normalize only statuses that genuinely need it.
  9. Regenerate human-facing governance. Require ID parity between Markdown and HTML and make the dark/night presentation the default for regroup artifacts.
  10. Run the full verification suite on the authoritative checkout. Use a Windows/PowerShell-capable environment, restore the canonical remediation filename after reboot, verify Git commit/branch state, and retain the run evidence.
  11. Owner synchronization gate. Review the repaired baseline together before selecting the first next-phase implementation package.
