2 · Findings

M-01
A successful retry is unrepresentable in the canonical result envelope
BLOCKER

Two rules in the schema's allOf are jointly unsatisfiable for the most common retry outcome:

rule 1:  if status == "completed"   then error must be null
rule 4:  if retry_count == 1        then error must be an object

An envelope with status: "completed" and retry_count: 1 therefore has no valid form. Executed against jsonschema 4.26 (Draft 2020-12), full matrix:

status      retry   error=null   error=object
completed     0         VALID          .
completed     1           .            .      <-- no valid representation
partial       0         VALID        VALID
partial       1           .          VALID
blocked       0           .          VALID
blocked       1           .          VALID
failed        0           .          VALID
failed        1           .          VALID

Three sources in this same commit require exactly that combination:

  • Charter §14: "Every retry gets a new run_id, preserves the original evidence and includes the classified failure." On a successful retry, status is completed and rule 1 forces error: null — so the classified failure cannot be included.
  • Mermaid diagram E: alt Retry succeeds → Max->>Claude: Integrated evidence. An explicitly diagrammed success path.
  • Rendered SVG E: preserves it — Retry succeeds? → Evidence.

There is no reading of §14 that escapes this. If the retry envelope resets retry_count to 0, the counter becomes meaningless and the classified failure still cannot be carried on a completed envelope.

Consequence. Charter §17 test 15 — "A transient/format retry occurs at most once with a new run ID" — can only ever be written against a failed retry. The implementation will either emit an envelope that fails canonical validation on its most common success path, or silently drop the retry provenance to stay valid.

Recommended fix (preferred). Separate the failure that caused the retry from the current terminal error. Add a nullable retry_reason object carrying class and native_message, keep error meaning "why this envelope is not completed", and rewrite rule 4 to constrain retry_reason instead of error. This satisfies §14's "includes the classified failure" without breaking rule 1's clean invariant.

Minimal fix. Scope rule 4 to non-completed statuses: if retry_count == 1 AND status != "completed". Cheaper, but loses the retry provenance on success — which is the evidence §14 asks for.

M-02
The schema cannot prevent self-certified independent review
HIGH

Charter §13 names the schema "the only contract for … independent review", and §17 test 13 requires that "An implementer cannot self-certify independent review." Executed:

agent = "max", validation.independent_reviewer = "max", status = "completed"
  -> VALID

JSON Schema 2020-12 cannot compare two sibling property values, so this constraint is not expressible in the canonical contract and must live in the validator. That is fine — but the schema says nothing about it, so a reader who takes §13 literally will believe the contract covers a guarantee it cannot.

Recommendation. Follow the pattern the receipt schema already uses well: add a $comment naming the out-of-band rules (independent_reviewer != agent, and scope_observed being self-reported and therefore requiring external corroboration), and amend §13 to say the schema is the only contract for structure, with named runtime rules layered on top.

M-03
Four live as-built assertions survive the OmniRoute reconciliation
HIGH

Present tense, unmodified by this commit, in hx-omniroute-architecture-decision-litellm-replacement…html:

OmniRoute is deployed only on the trusted HX network.
… is not exposed directly to the public Internet.
API authentication remains enabled for HX clients.
OmniRoute service credentials are scoped to gateway needs.

These contradict the commit message — "No server contacted or deployment performed" — and the document's own footer, which states it is "not an assertion that OmniRoute is installed."

This is the same defect class as P1-01: a document asserting as-built state that no evidence supports, inside a phase whose rule is that nothing is deployed. The reconciliation pass correctly fixed adjacent language (HX client → HX conformance harness; the version pill downgraded to Source snapshot … exact commit unproven from ZIP) but left these four. Recommend converting to conditional form — "when deployed, OmniRoute must be reachable only on the trusted HX network" — which preserves the security requirement without asserting state.

M-04
Max's authority is silently broadened, and Agent Zero disappears, in both OmniRoute documents
MEDIUM

Charter §2 and the roster both scope Max narrowly: "sole task dispatcher and sole integration coordinator for OmniRoute"; roster scope column "OmniRoute repository ecosystem". Both OmniRoute documents drop the qualifier — integration prompt line 62 and architecture decision line 155 read "Max is the sole dispatcher and integrator", unqualified, inside a document that opens "You are Claude Code operating in the canonical HX-Infrastructure repository."

Additionally, "Agent Zero" and "Jarvis" appear zero times in either OmniRoute document, while charter §1 places Agent Zero at authority rank 1 and §6 requires CLAUDE.md to "identify … Agent Zero as final human authority." The OmniRoute docs instead assert "CLAUDE CODE OWNS USER INTENT."

Charter §1 also states "No agent may approve its own architectural authority." A dispatch document that broadens its own dispatcher's scope and omits the human authority is the shape that rule exists to prevent. Recommend restoring the OmniRoute qualifier and the Agent Zero authority line in both.

M-05
The knowledge-review receipt is absent from the dispatch gate it was designed for
MEDIUM

The charter's canonical receipt example is OmniRoute-scoped ("task_id": "OMNI-YYYYMMDD-NNN"), and §17 test 5 requires that "A missing, stale, forged, cross-task or empty knowledge receipt blocks execution." The integration prompt is the OmniRoute dispatch document. Its TASK PACKET enumerates 18 mandatory pre-dispatch fields — including knowledge output and return schema — and does not include a knowledge-review receipt. Neither OmniRoute document references either schema; grep -ci "receipt" returns 0 for both.

Charter §3: "This is both an instruction and an enforced gate. An agent assertion is not proof of review." The prompt currently encodes the assertion and omits the proof.

On the skip. Copilot reported: "The OmniRoute architecture-decision receipt finding was skipped. Direct inspection confirmed that the named document contains no receipt contract." The literal statement is true and independently verified — zero occurrences, in both documents, not just the named one. But confirming that a control is absent does not dispose of a finding that the control is missing; it substantiates it. I could not read the original finding text, so I cannot rule on its intent — if the finding asked "should this document carry a receipt contract?", the answer from §3 and §17-5 is yes, and it remains open.

M-06
Diagram H deviates from its Mermaid source in two ways
LOW–MEDIUM

Copilot's claim that "the rendered SVG appendix now matches the Mermaid control flows" is substantially correct — I compared all 8 diagrams and 7 are faithful, including diagram E, whose exact fidelity matters most for M-01. Diagram H is the exception:

  1. Two nodes merged. Mermaid has P7["8. Read-only pilot"] --> P8["9. Bounded worktree pilot"]; the SVG renders one box, 8–9. Bounded pilots. These are distinct governance gates — one performs no mutation, the other mutates a worktree — and charter §18 keeps them separate as items 9 and 10.
  2. Branch labels dropped. Mermaid has Q -->|"No"| P1 and Q -->|"Yes"| P7. SVG H contains neither label, so the reader cannot tell that a failed negative test loops back to stage 2. Diagrams B and D do carry their Yes/No labels, so this is an inconsistency, not a rendering convention.

There is also a three-way count drift worth reconciling once: charter §18 has 11 stages, Mermaid H has 10, SVG H shows 9. Mermaid merges charter items 5 and 6; the SVG then merges Mermaid items 8 and 9.

M-07
Contract declared canonical, enforced nowhere — and correctly so, for now
INFORMATIONAL

No hook, test, or agent definition references either schema. The only referencing files are the three governance documents in this commit plus the schemas themselves. Nothing validates against them.

This is not a defect — charter §18 puts canonical schemas at rollout gate 2 and enforcement hooks at gate 7, so the ordering is exactly right, and Copilot's decision to stop at charter level pending Phase 0 preflight is the correct call. It is recorded here only so that "the canonical schemas are the sole contracts" is read as a design commitment rather than a live control. Today an agent can emit any shape at all and nothing objects.

Two further points worth noting while the schemas are still cheap to change: "format": "date-time" is annotation-only in Draft 2020-12, so "review_completed_at": "banana" and a year-2099 timestamp both validate. The receipt schema's $comment discloses this correctly and names the runtime rule — that is the right pattern, and M-02 recommends copying it into the envelope schema.

5 · Recommendations, in order

  1. Fix M-01 before anything consumes the envelope schema. Preferred: add nullable retry_reason and re-scope rule 4 to it. Add three schema fixtures to the eventual test suite — completed+retry 0, completed+retry 1, failed+retry 1 — so the matrix is asserted rather than assumed. This is cheap now and expensive after producers exist.
  2. Add the $comment block to the envelope schema (M-02) naming the constraints that must live in the validator: independent_reviewer != agent, and scope_observed corroboration. Amend charter §13 to say "only contract for structure."
  3. Convert the four as-built assertions to conditional form (M-03). Smallest edit with the highest truth value in this commit, and it closes a Phase 3 rule violation.
  4. Restore the OmniRoute scope qualifier on Max and the Agent Zero authority line (M-04) in both OmniRoute documents.
  5. Rule on M-05 — whether the OmniRoute dispatch path owes a knowledge-review receipt in its TASK PACKET. §3 and §17-5 imply yes; the owner should confirm rather than an agent inferring it.
  6. Re-render diagram H (M-06) with 8 and 9 separate and the Yes/No labels restored, and reconcile the 11/10/9 stage count once across charter and appendix.
  7. Merge the F-01 fix into the evidence branch, or rebase it, so the Meta-Agent workstream stops building on the blanket ignore rule. This is the structural item; it does not block the schema fixes.

What I deliberately do not recommend

  • Do not build hooks or tests yet. Copilot's decision to stop at charter level pending Phase 0 preflight and installed-feature verification is correct and should stand. The charter assumes specific Claude Code capabilities (a dedicated Tier-1 entry point without Agent/Task, PreToolUse denial semantics, SDK callback timeouts); §4 and §17-11 already require verifying those against the installed version rather than assuming them.
  • Do not switch the ignore rule to **/. Unchanged from the earlier ruling — the one-level form is documented and sufficient.
  • Do not treat the schemas as live controls. Nothing enforces them yet, and the rollout order makes that correct.
