Severity reflects impact on the next phase, not criticism of the work. Three findings carry the owner's Phase-3 adjustments and are marked accordingly.

High severity

HIGH Lifecycle authority is split across documents X F-02

GOALS-AND-OBJECTIVES.md and SERVER-REGISTRY.md define Phase 2 as consolidation and (formerly) Phase 3 as server implementation. But README.md, CLAUDE.md, servers/AGENTS.md, and the final step in start-up/session-resume.md still describe Phase 2 as server configuration. Verified: README.md:17 "Phase 2: Role Configuration"; README.md:29 "configuration.md is created only in Phase 2"; CLAUDE.md:30–34 "When Phase 2 begins for a server: configure only the approved role; create configuration.md." The new Phase-3 regroup model adds a third vocabulary unless reconciled.

HIGH The phase guard releases mutation controls on consolidation state X F-03

hx-phase1-guard.ps1 stops guarding when the registry's Phase 2 status is READY, IN PROGRESS, or COMPLETE, and its regression suite proves READY releases package installs and other mutations. Under the current model, Phase 2 means consolidation and server mutation belongs to a later phase — so the guard now opens the door in a phase where no server change is authorized. This is a control/authority mismatch, not a typo. Combined with the finding above, an agent reading CLAUDE.md could believe it may configure servers now, with the guardrail already open. This pair is the single most consequential risk in either review.

HIGH The authoritative AI-runtime contract is corrupted C+X F-01

governance/policy/ai-runtime-acceptance-contract.md contains an incomplete profile row, dangling backticks, missing project names, and broken provenance sentences (around lines 126–184). tests/ai-runtime/README.md carries related damage. The pattern matches the repository's own warning against regex-based term removal. A policy file consumed by tests and future runtime decisions cannot be treated as semantically authoritative until restored from a known-good source and re-reviewed.

HIGH Two runtime gates do not match the only workload schema C+X F-04

hx-capacity-gate.ps1 and hx-workload-commission.ps1 expect fields (execution_modes, capacity_gate_result, storage_gate, model_acquisition, server, revision) that do not exist in qwen35-9b-ollama.json. They retain DS4/SSD-streaming assumptions while the only workload is an Ollama Qwen3.5 record. The 22-invariant suite checks source substrings and file presence, not schema compatibility — so a green invariant run can coexist with unusable gates. That is exactly the P-A failure the repository says it prevents.

HIGH Registry and current architecture disagree in two load-bearing places C+X F-05

(a) The registry assigns LiteLLM to hxs-8/hxs-9, while owner decisions supersede LiteLLM with OmniRoute. (b) The registry assigns hxs-4 Qwen2.5-3B plus the embedding/rerank plane, while runtime acceptance records a commissioned Qwen3.5-9B on the 8 GB GPU; iss-017 records this as unruled, and the accepted endpoint is loopback-only and unreachable by its named client. The registry is the placement authority, yet designs must work around known-stale assignments.

HIGH The hook installer is not idempotent C NEW

claude-hooks/apply-hooks.ps1 deduplicates only the original five hook groups. Re-running it can add the two newer guards — hx-permanent-policy-guard.ps1 (Ansible deny) and hx-authority-edit-guard.ps1 — a second time, duplicating PreToolUse groups. ("Idempotent" means safe to run more than once with the same result.) The regression suite never invokes the installer, so the gap is uncaught. Requires a new tracked issue and an idempotency regression test. This defect was found by Claude and confirmed as fully valid; it remains in the consolidated set unchanged.

06New lessons to record

The existing 33 lessons are an asset and should be retained, not rewritten. The regroup adds these generalized lessons, each earned in this cycle:

  • Schema compatibility is a gate. A source-text assertion does not prove a gate can consume the current workload definition.
  • Lifecycle changes are cross-cutting migrations. Renaming a phase requires updating contracts, hooks, tests, startup guidance, and generated pages as one atomic change.
  • Absolute cleanup claims require repository-wide proof. "Zero references" must be backed by a scoped scan that distinguishes historical mentions from current authority.
  • Generated human views are release artifacts. A log update is incomplete until its HTML copy is regenerated and checked for ID parity.
  • Observed project evidence overrides a stale knowledge prior. A model or fact dated inside the project record is not made doubtful by an older training cutoff. (Earned by Claude's Qwen3.5 skepticism, now removed.)
  • Scope every absence claim. "Not present in this snapshot" is not "does not exist." (Earned by the softened externally-located-assets finding.)
