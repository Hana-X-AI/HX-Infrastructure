Tech-Stack Alignment — Hana-X on the Real Fleet

The Hana-X Solutions Architecture, mapped onto the fifteen physical hosts the fleet actually has. Placements are constrained by the hardware inventory: four GPU hosts (not thirteen), a 16 GB ceiling per graphics card, and the control-plane laptop's limits. This is a development and test environment — single-tenant, low concurrency, no production user base hammering it — so single instances without failover are appropriate by design. The software stack is unchanged from the spec; what changes is where each piece runs and how it is isolated. SERVER-REGISTRY.md remains authoritative on hardware.

What was corrected. The original spec assigned GPU-accelerated vLLM inference to Servers 3–9 (seven hosts) and described 13 GPU workers. The fleet has only four GPU hosts — hxs-1 through hxs-4. All model serving is consolidated onto those four, and the CPU hosts carry the data, gateway, orchestration, ingestion and frontend layers.

The GPU hosts each hold a distinct AI function. hxs-1 is the reasoning flagship, hxs-2 is coding, hxs-3 is the agent-intelligence node — agent execution plus the LightRAG graph and experimentation headroom — and hxs-4 is the retrieval & utility node, co-locating Qdrant with the embedding and rerank models. Qdrant and LightRAG used to sit on CPU hosts; moving them beside the GPUs that feed them freed hxs-10, which now serves the web frontends.

The control plane runs nothing. hxs-cp is a Wi-Fi-only laptop with 15.8 GB of soldered RAM — the fleet's most fragile node. It keeps the control-plane designation only; no services run on it. Its spec services move onto reliable wired fleet hosts (NGINX ingress on hxs-5, the LiteLLM gateway on hxs-8, platform state on hxs-9). The laptop is just the operator's terminal for reaching the fleet.

Isolation is per-service virtual environments. Per the no-Docker mandate, every Python service runs bare-metal in its own dedicated virtualenv — vLLM, Docling, Crawl4AI, LangGraph, Mem0 and the MCP servers each get an isolated environment so their conflicting dependencies never collide on a shared host.

Sized for dev and test, not production. One instance of each model and a single Qdrant is exactly right here — with no large user base hammering the platform, failover and horizontal scale are deliberately out of scope. Some CPU/RAM/storage contention on shared nodes (e.g. Qdrant beside the utility models on hxs-4) is acceptable, since maximum throughput is not the goal.

GPU serving tier — the four GPU hosts

hxs-1 and hxs-2 pool their matched card pairs via tensor-parallelism into a single ~32 GB unit per model. hxs-3 now pools its matched pair the same way (TP=2, decided). hxs-4's pair is mismatched (16 GB + 8 GB), so it never pools — its cards are independent slots. Note that hxs-3 and hxs-4 also host data services (LightRAG and Qdrant respectively) on their CPU/RAM/NVMe, beside the models that feed them.

Model menu — what actually fits

Six model roles cover the pipeline in the spec's Flows A and B. Every large model is 4-bit quantized; a 32B model at half-byte-per-weight is ~16 GB of weights, which exceeds a single 16 GB card and forces tensor-parallelism across a host's two GPUs. (Qdrant and LightRAG are data services, not models — see the tier tables.)

CPU service tier — the eleven small-form-factor hosts

Everything that is not GPU inference, placed by matching workload to hardware. The user-facing edge is split across three nodes — NGINX ingress on hxs-5, the LiteLLM API gateway on hxs-8, and the web frontends (Open WebUI + CopilotKit / AG-UI) on hxs-10. The RAM-sensitive CPU services (Postgres + Redis, Docling, the LangGraph runtime) sit on 32 GB hosts; the three 16 GB hosts carry only light work — crawling, MCP services, and the LiteLLM gateway. FastMCP has its own home off the dev box.

Notes & open items

hxs-3 GPU topology — closed

Decided: gpt-oss-20b uses both cards at TP=2 for maximum tool-calling context. The single-card alternative (leaving one GPU free for experimental inference) is set aside.

Qwen 3.8 27B is unreleased

Its slot on hxs-1 is sized for a 27B dense model at 4-bit (~14 GB weights, fits 32 GB with room for context). If it ships as MoE, larger, or needs a specific quant, re-confirm the fit on launch day before committing the host.

No dedicated monitoring node

Observability & backup was dropped by decision for this dev/test environment; hxs-8 now runs the LiteLLM gateway instead. That host's 477 GB disk is left as spare capacity — the natural place to reinstate metrics, logs, or snapshots later if wanted.

Retrieval co-located with its models

Qdrant now sits on hxs-4 beside the embedding and rerank models it serves, on a dedicated 476.9 GB NVMe — embed → store → rerank on one host. LightRAG sits on hxs-3 beside agent execution, with the 1.8 TB SSD as its graph-data device. Both GPU hosts have ample RAM (32 / 66 GB) for these services.

Control plane runs nothing

Per direction, hxs-cp holds the control-plane designation but runs no services: ingress on hxs-5, gateway on hxs-8, state on hxs-9. The laptop is the operator's terminal — removing the fleet's biggest single point of failure.

Isolation via per-service virtualenvs

No Docker. Each Python service gets its own virtualenv, so vLLM, Docling, Crawl4AI, LangGraph and Mem0 never share a dependency tree. Residual caveat: a venv isolates Python packages but not the host NVIDIA driver — where two GPU services share a host, pin them to compatible CUDA/torch wheels.

No redundancy — by design

One instance of each model and one Qdrant, each on its own host, with no failover. For a single-tenant dev/test environment that is the intended trade-off, not a gap — capacity goes to coverage, not high availability.
